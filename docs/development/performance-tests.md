# 性能・復旧試験

Clutch-CSの性能試験は、同じ結果を得られたことと資源使用量を合わせて確認します。処理を省略したり、失敗を成功へ読み替えたりして得た速度を改善として扱いません。ディスク書込みの削減を優先し、メモリ削減によるCPU・処理時間の悪化も確認します。

## 実行

```powershell
dotnet build Clutch-CS.slnx -c Release
dotnet test tests/ReArtWord.Contents.BackgroundService.Integration.Tests -c Release --no-build --filter "Category=Performance" --logger "console;verbosity=detailed"
dotnet test tests/ReArtWord.Contents.BackgroundService.Unit.Tests -c Release --no-build --filter "JsonAllocationTests"
dotnet test tests/ReArtWord.Contents.BackgroundService.Unit.Tests -c Release --no-build --filter "SteadyWorkflowHistoryIoTests" --logger "console;verbosity=detailed"
```

共通アナライザーを有効にしたReleaseを使用します。性能用のコレクションは、同じ試験ホストの他fixtureと並列実行しません。各試行は固有のクラスターID、ループバック接続、`.work/performance` または `.work/integration` 内の固有ディレクトリを使います。本番ワークフロー・外部API・本番の保存先は参照しません。失敗時にも所有CoreServiceとHTTP待受を閉じ、調査用の保存先と計測JSONを残します。

大きい履歴で同じ差分・読取り試験を行う場合は、`CONTENTS_PERFORMANCE_HISTORY_SCALE=16` を指定すると最大4,096件・約64MiBの過去本文へ増やせます。1〜64倍を受け付け、割当・書込みの上限は増やしません。実行後はこの環境変数を解除してください。準備に必要なディスク量と時間は履歴数に応じて増加します。

定常的な実行診断の保存には `CONTENTS_PERFORMANCE_JOURNAL_SCALE=100` で約4.6GB・9.9万件の合成履歴・266基準点を用意できます。1〜100を百分率として受け付け、未指定時は小さい新規DBで実行します。各ケースで試験専用の一時DBを生成・破棄するため、本番DBのコピーや既存保存先の指定は不要です。準備費用は計測区間へ含めません。

`CONTENTS_PERFORMANCE_JOURNAL_ROUNDS` は300実行の測定回数で、既定3回、指定範囲3〜20回です。時間差の確認では10回へ増やし、最初の2回を除いて比較できます。GCの世代別回数も記録します。結果JSONはテスト出力にも残り、`CONTENTS_PERFORMANCE_LABEL` で比較版を区別できます。実行後はこれらの環境変数を解除してください。

## 検証する負荷

### Dashboardの初回履歴取得

Dashboardの計測系列は、ClientHost・画面とも6分・最大121点に制限します。概要表示のために圧縮済みリソース履歴や全期間のDBを読み直しません。全クラスターの初回表示では各ピアの系列を取得するため、点ごとに項目名・単位・GPU名などを繰り返すJSONは、ピア数と保持点数に応じて大きくなります。IO・NWの追加もこの配信量と復元費用を増やします。

対応する画面は`/client/dashboard`と`/client/dashboard/batch`へ`compact=true`を指定し、項目説明を共有する`sampleSeries`を受け取ります。採取ID・時刻・値は全点を保持し、NIC、実体、取得不能理由、項目順などの変更位置では系列を分けます。少数点や構成が頻繁に変化する場合は通常形式を使います。既存の差分カーソルと保持上限は維持し、追加の履歴ファイルやCoreService照会は作りません。

未指定の旧画面には通常形式を返し、新画面も通常形式を読み取れます。

`DashboardSampleSeriesTests`、`DashboardCompactTelemetryTests`、`DashboardCacheTests`で、JSONの往復、欠測、構成変更、旧形式、差分、再起動を確認します。`DashboardHistoryTransferPerformanceTests`は、27Peer・各25項目を1／40／121点へ増やし、送信側の変換・JSON化・受信側の復元を合わせて5巡測定します。

2,000回の更新でも表示系列が121点以内に収まることを別に確認します。

```powershell
dotnet test tests/ReArtWord.Contents.BackgroundService.Client.Tests -c Release --no-build --filter "DashboardHistoryTransferPerformanceTests" --logger "console;verbosity=detailed"
```

ブラウザー上の計測では、専用の状態ディレクトリを使う ClientHost とブラウザーを起動し、ループバック HTTP から模擬観測を返します。保持点数ごとに新しいブラウザーコンテキストで複数回測り、応答本文の容量、PC カードが表示されるまでの時間、全グラフの描画時間を記録します。描画点数、欠測、ブラウザー例外も確認してください。CoreService からの観測取得と、ブラウザーの表示処理は別の計測区間にします。

プロセス試験のメモリ・書込み上限は、小さい固定fixtureがGB単位に膨張する回帰を検出するための上限です。本番の汎用容量制限ではありません。保存500msや割当1GB未満といった改善目標を、端末の性能差を無視した合否条件にはしません。個々の時間、CPU、メモリ推移、出力量をJSONに残し、同じ端末・同じ負荷の複数回測定で比較します。

定常診断の試験は WorkflowEngine と SQLite に合成履歴を用意して実行します。ノード数、履歴量、同時実行数を揃えて比較してください。別 CoreService への配送・ファイル保存・周期信号は、実プロセス試験でも確認します。`WorkflowHistoryBlockStorageTests` では、循環領域の再利用、保存形式が混在した場合の読取り、圧縮後の復元と期限削除、欠損・世代不一致、失敗診断の保持を確認します。

定常診断の測定量は `CONTENTS_PERFORMANCE_JOURNAL_SCALE` と `CONTENTS_PERFORMANCE_JOURNAL_ROUNDS` で指定します。変更前後を同じビルド条件で複数回測り、初回の JIT や DB 準備を除いた区間で比較します。実行時間、履歴の保存時間、プロセスの読書き量、CPU 時間、メモリ割当をそれぞれ確認してください。プロセスの I/O は論理量であり、物理ディスクの転送量とは異なります。

履歴の背景圧縮や再参加については、既存の `HistoryArchiveForwardingTests`、`HistoryRetentionProcessTests`、`PeriodicHeartbeatProbeTests` も併用します。長期履歴を増やす試験では、`CONTENTS_ARCHIVE_RECORDS` や `CONTENTS_PROBE_HISTORY_ROWS` の既存設定を使用できます。

HTTP試験は外部生成の待ち時間を再現するものではなく、受信したBinaryの配送・履歴・保存の負荷を確認します。

`PeriodicHeartbeatProbeTests.FrequentSignalsReachAllOutputsWithoutDuplicationAsync` は3 CoreServiceへ50ms周期の64実行を流し、256件の実UDP出力について値・件数・参加状態を確認します。診断保存の500msより短い周期でも、保存をまとめたことによる業務出力の欠落・重複を見逃さないための試験です。

同期の単体試験 `PreparedSnapshotTests` は、32MiBの共通履歴で従来経路との実書出し量・時間・割当量を比較します。固定後の通常書込み、履歴の削除・置換、取消、期限切れ、枠の再利用も検証します。`DifferentialSynchronizationTests` は `CONTENTS_PROBE_CORE` に比較対象のCoreService実行ファイルを指定して旧版の回帰対照を実行できます。

対応前の版では転送容量超過で失敗することを確認し、単に負荷の軽い成功ケースだけを増やさないようにします。

`FileReservationGrowthTests` は、単一ピアの実SQLiteに終了記録を用意し、保持保守の前後で同じ取得・非同期書込み・解放を測ります。復旧記録は正常終了と確認不能を区別し、終了した現役予約だけを回収します。履歴準備と圧縮・削除の費用は通常書込みの計測から分けます。3.3万件の合成履歴を用意し、履歴量に対する割当と I/O の増加を測定します。再実行防止の小さい索引と本文保持量は別に評価します。

複数CoreService・実通信の負荷は上記の3ショット試験で確認します。

`FileReservationRollingTests` は保持中の予約を残して実CoreServiceを再起動します。`CONTENTS_FILE_COMPAT_CORE` へ新しい台帳形式に未対応のCoreService実行ファイルを指定すると、旧版混在→全台対応→旧コーディネーター再参加の切替と実ファイル書込みを検証します。未指定時は現在版同士の再起動試験です。

`IterationValueLifetimeTests` は500要素・合計64MiBを超える中間Binaryを消費し、終了した要素の保持枠を回収できることと、遅い子処理へ元の値を維持することを確認します。

高並列試験では、ピアの誤失効、同じ実体で開始済みの処理の結果照会、TCP送信枠の待機と取消、確立済み接続の再利用も確認します。反復の中間値は、要素のボディとそこから発火した子処理が終わってから解放します。一件の実行回数の上限や再実行防止は維持し、消費済みの値を累積したためだけに64MiBの保持枠を使い切らないようにします。

500 ファイル・80 同時予約の試験では、正常解放と解放確認を失う場合を分け、累積割当、論理書込み、所要時間を比較します。転送したファイル本文の容量とは別に、メタデータ、複製、ジャーナルの費用も確認してください。

TCP 接続の再利用は、3 CoreService に疑似 HTTP 応答を配送して確認します。各ショットの全ファイルが一致すること、HTTP 要求に欠落・重複がないこと、接続待ちが後続の処理を妨げないことを検証します。

`ReceiptInventoryCostTests` は4,096／40,000／210,000件の共有履歴で、初回照合・同じRepositoryでの再照合・Repository再作成後を比較します。21万件は500ファイル×30回/日×7日×予約取得・解放2回に相当し、実行履歴など全種類の総件数ではありません。照合指紋の一致と、照合中にSQLiteの `data_version` が変わらないことも検証します。

旧SQLの更新・削除、本文破損、既存履歴への背景補完は `ReceiptFingerprintTests` で確認します。

指紋索引は、照合時の本文復元を減らす効果と、通常の保存時に索引を書き込む費用を分けて評価します。共有履歴を増やした照合試験と、ファイルの並列保存試験を組み合わせてください。

## 計測値の読み方

- `allocatedBytes` は計測区間中の累積割り当てで、同時使用メモリではありません。Repository試験ではテストプロセスを測ります。別プロセスのCoreService割り当てを、この値へ含めた扱いにはしません。
- `PrivateBytes`／`WorkingSetBytes` はCoreServiceのその時点の使用量です。強制GCは行わず、実行の各周回と自然な待機を観測します。短時間の試験だけで長期間のリークがないとは断定しません。
- Windowsの `ReadBytes`／`WriteBytes` は `GetProcessIoCounters`、Linuxは `/proc/<pid>/io` の `rchar`／`wchar` です。プロセス全体の論理I/Oであり、ネットワーク・デバイス等も含み得ます。物理ディスクへ実際に書いたバイト数と同一視しません。他OSで未取得の場合はnullを記録します。
- JSONの書出しと結果ファイルの照合は、主な資源計測の後に行います。試験報告の保存をCoreServiceの書込みと混ぜません。
- 保存の計測範囲は管理要求から保存・共有結果までです。ブラウザーの編集差分作成・描画・通信も含む操作感は、別途ブラウザー上で測定します。

主な性能回帰は、実プロセスや SQLite の連携でも起こるため、既存のxUnit結合試験へ計測と資源上限を追加しています。BenchmarkDotNetはまだ依存へ追加していません。単一関数の数%の差を判断する必要がある場合は、JIT・ウォームアップ・複数試行を揃える目的で別のベンチマークとして使用します。結合試験の正しさ・障害境界・I/O確認の代わりにはしません。

## 履歴の圧縮と復旧

`RecoveryStateCostTests` は過去の確定結果を128件・2,048件へ増やし、用途ルーター経由の現在状態確認を10回繰り返します。履歴本文を含めないこと、共有版の一致、割当の上限、DB書込みがないことを検証します。`PeerRecoveryHistoryTests` は実ハートビートを使い、過去本文の破損と現在値・未確定予約の破損で復旧判断を分けます。

`HistorySelectionCostTests` は32KiBの本文を持つ256件・4,096件の保持中履歴を作り、分類完了後の8回の保守についてCPU・経過時間・プロセスI/Oを測る。移行条件を通常の期限条件へ混ぜて索引が使われなくなり、対象外の本文を全走査する退行を、割当だけでなく読取りI/Oでも検出します。計測前のデータ作成・初回分類と、定常時の保守を分けます。

旧形式移行の機能境界は `LegacyHistoryMigrationTests`、予約の混在版対応は `FileReservationSlotTests`、ページ保存後の旧診断本文の除去再試行は `ResourceHistoryStorageTests` で確認します。`HistoryRetentionProcessTests` と `FileReservationRollingTests` は実CoreServiceの再参加・更新・予約を跨いだ境界を確認します。

段階同期は、異なる保持履歴を持つ二つの独立した DB とピアプロセスで確認します。参加側が Ready になるまでの時間、背景同期の件数と完了時間、既存側の稼働継続、共有版の一致、同期中の通常保存の結果を記録します。スナップショットの作成、通信、受信側の取込みは別々に計測してください。

現在のワークフロー定義が片側だけ圧縮領域にある場合も、共有版が一致することと、完了後に全同期を繰り返さないことを確認します。

## 全台停止と保存競合からの回復

`WholeClusterRestartRecoveryTests` は隔離した実CoreServiceを3プロセス起動し、全停止後に準備途中・コミット判断直後・局所コミット後の状態を用意して再起動します。旧保存結果の不一致、同値のファイル予約分岐、待受PC割当の分岐も含め、全ピアのReady、競合・残存準備・背景同期の残件ゼロ、ループバックOSCからPreviewまでを確認します。外部APIや本番ワークフローは起動しません。

`ReplicationPreparationCompatibilityTests` の `CONTENTS_REPLICATION_COMPAT_CORE` には旧CoreService実行ファイルを指定し、新旧双方向の保存・再送・再起動を検証できます。

`RandomizedRestartTests` は7つの独立DB・実CoreServiceを使い、各DBに合成履歴11,008件、38WF（うち36定義は各200ノード）を用意します。333ms間隔の実OSC中継、250ms待機を持つ手動ワークフロー、クラスター共有の状態データの書込み、配置変更の保存を続けながら、最大2台ずつの部分停止と全7台停止を行います。停止順、再起動順、操作間隔は固定seedから生成し、2つのseedを直列で検証します。

停止は試験の子processだけの強制終了であり、OSの電源断・本番サービス操作・外部API呼出しは行わない。

保存負荷は確認済みの編集元の版を維持し、結果不明の要求は元結果の照会だけを行います。別ピアから古い版を読み直して別編集を継続すると、再起動による履歴矛盾とは異なる正当な内容競合を作るため、この条件を混同しません。停止中に失われ得るUDP、未受理、受付後の結果不明も区別します。復帰後は全7Peerの連続Ready、背景同期完了、競合なし、共有版一致、残存準備なし、確認済み状態データの全DBでの保持、旧要求照会と重複出力なし、新しいOSCの到着までを確認します。

`.work/integration/restart-<seed>-<固有ID>/p0/random-restarts.json` に順序・元要求・結果・実到着値・プロセス別CPU／メモリ／論理I/Oを、失敗時にも保存します。履歴本文は合成した小さい値であり、物理電源断時のディスク障害は別途検証します。

再起動試験では、停止中の UDP 損失と復帰後の通信を区別します。Ready への復帰、背景同期の完了、共有版の一致、未完了操作の解消、出力の重複がないことをそれぞれ確認します。

`PreparedSynchronizationCostTests` は準備中の受信側へ同期本文を繰り返し書き出さないこと、`ReplicationCommitTests` は判断と本文の原子的保存・失敗時ロールバック・確認待ち索引の巡回を検証します。`RecoveryReceiptCostTests` は本文検査と小さい結果索引を同じDBで比較し、指紋・同期参照の一致、書込みゼロ、旧索引の有限単位の補完を確認します。

本文列の式索引はSQLiteの増分BLOB書込みを妨げるため使わず、確認待ちの索引表を通常保存と同じ取引で更新します。

復旧スナップショットの測定では、現在状態と後送する履歴の件数を記録し、読取り中に書込みが発生しないことを確認します。旧索引の補完費用は別区間で測ります。

## 準備待ち・担当競合の再読取り

準備本文の再読取り抑制では、`SqlitePreparationCacheTests` で大きな準備を保持したまま指紋照会・共有版照会を反復し、初回検査後の累積割当と論理I/Oを計測します。本文はキャッシュに保持せず、最大256件の内容版・指紋・共有分類だけを再利用します。内容版は同じ取引の小さい派生表から読み、実在する準備キーとの照合を維持します。新規・変更・30秒経過では元本文を検査し、削除は待機期限を待たず反映します。本文列の式索引は使用しません。

`SourcePcAssignmentRetryTests` は、同じ再試行待ちの間に担当本文・競合集合を再取得しないことと、変更を観測した際に読み直すことを対象とします。待機解除には共有本文の全体ハッシュを計算せず、保存先の小さい変更世代と参加実体・選択条件を使用します。リソース値に依存する選択や、安価な世代確認に未対応の媒体では従来の再照合を維持します。

`SqlitePreparationScaleTests` は、合成診断履歴を1,000・10,000・50,000件へ増やし、合計2MiBの準備4件を保持します。同じDBで、従来の全準備本文復元と、確認済み指紋・共有版の照会を30回ずつ比較します。準備・履歴投入と計測結果の出力は測定外とし、経過時間、累積割当、CPU、論理I/O、自然なGCの直近ヒープ量を記録します。履歴は一件約1KiBの合成本文であり、大きなファイル本文を含む同期は別の負荷条件で確認します。

強制GCやOSキャッシュの破棄は行わない。

電源予定は `HostPowerScheduleProcessTests` で、異なる実プロセスのクラスターとSQLiteを使用します。停止コマンドを試験ファイルへの記録へ置換し、Magic Packetの宛先をループバックの試験所有ポートへ固定します。全予定の先行受付、送信元の最後の操作、オンライン対象のWoL省略、停止中対象への代送、再起動後の二重実行防止を確認します。実PCの停止・起動や実NICからのブロードキャスト送信は別の実機試験として扱います。

## 状態データの継続アクセス

`StateAccessGrowthTests` は実SQLiteに40WF・各200ノードを保存し、共有状態データの過去確定記録を約3千／3.3万／9.6万件へ増やして、各段階で一日相当の2万read・3千writeを実行します。書込みは因果情報の付与、現在版確認、比較交換を含みます。DB準備と計測JSONの保存は測定外です。ネットワークを介した複製やワークフロー実行時間は含みません。

状態データ変更の購読通知はメモリ上だけに保持し、表示のために別履歴を追加しません。現在値はワークフロー終了時に削除せず、共通の確定記録・再実行防止の保持方針は維持します。`StateRetentionTests` はSQLite／JSONで120回書き換え、履歴保持0日の設定と3年後相当の保守処理を使って、現在値の保持、別保存先への復元、期限切れ操作の再実行防止、不要な購読通知がないことを確認します。本番の保持設定をこの試験で変更することはありません。

長期運用の試験では、保存期間、保持する履歴量、通常時と集中時の要求数をそれぞれ指定します。論理時刻による保存期限の確認と、実プロセスを使う再起動・再参加の確認を組み合わせます。模擬 API では本文、遅延、失敗を制御し、ファイル予約の解放、I/O、自然な GC 後のメモリ使用量、処理時間の増加を確認してください。

### 保持境界の反復と実通信

`RetentionCyclePerformanceTests` は日次件数を縮小し、実SQLiteに要求24件、終了済みファイル操作8件（取得・解放の2記録）、実行診断4件、共有状態データ更新1件を毎日追加します。非圧縮7日・総保持30日の保守を1,095日分繰り返し、60／90／365／730／1,095日目の本文数・削除索引・DB使用量と、固定1,000回の現在値読取りを比較します。

時計注入に対応しない保存APIについては、この試験自身が生成した未分類行の記録時刻だけを論理日に合わせます。OS時計・本番DBは変更しません。

これは保持方針を反復する試験です。3億件のOSC処理を実行した試験ではなく、日次件数を縮小したDB容量から本番容量を直接推定しません。保持中の件数による費用は、共有履歴4,096／40,000／210,000件の `ReceiptInventoryCostTests`、40WF×200ノードと共有履歴の `StateAccessGrowthTests`、大きい保存本文を使う診断履歴試験と分けて測ります。

`AudioWorkloadProcessTests` は3 CoreServiceのうち別ピアでQwen音声ノードを実行し、HTTPの合成応答、WAV取得、ffprobe、ファイル予約と確定保存を通します。7並列のワークフローを2本ずつ3周実行し、さらにHTTP 500・受付後のタイムアウト・同じ保存先への再実行を確認します。外部サービスには接続せず、音声本文はキーごとに識別できる1秒のPCMです。

76生成要求が一回ずつ届き、成功74ファイルと元バイトが一致すること、終了後の現役予約と一時ファイルが残らないことを検証します。ElevenLabs固有の通信契約・媒体形式の試験とは別であり、外部提供元の生成時間やレート制限は再現しません。

`CSharpSourcePerformanceTests` は実ワーカー・実pipeで16KiBの通知を100／1,000／10,000件と増やします。試験側も消費済みBinaryを蓄積せず、各値の順序と内容、CPU・プロセス論理I/O・累積割当・自然なGC・ワーカーの終了を確認します。

ワークフロー後続の独立性、例外、取消、協調停止しないコードの回収は既存の `CSharpSourceTests`／`CSharpSourceWorkflowTests` と組み合わせます。

結合試験の `CONTENTS_TEST_CORE` へ公開済みCoreService実行ファイルの絶対パスを指定すると、その実行物を隔離した設定・保存先だけで起動できます。個別fixtureの明示実行物はこの環境変数より優先します。`CONTENTS_TEST_FFPROBE` には実ffprobeの絶対パスを指定します。本番と同じ物理ホストで測定するときは、試験プロセスの `DOTNET_PROCESSOR_COUNT=2` と逐次実行で負荷を抑えます。

子CoreServiceもこの制約を引き継ぐため、CPU・GC構成が異なる本番と使用量を直接比較しません。

停止境界の `RuntimeRequestExecutorTests` では、空の受付枠・実処理中・保存停止による512件の上限到達を分けます。停止中の新規要求は `Execution.Stopping`、実際の有限枠不足は `Execution.BufferedReceiptCapacity` とし、どちらも副作用開始前の未実行です。開始済みの一件は完了・保存まで待ち、再照会を副作用の再実行へ変えません。
