# クラスターの設定をまとめて移す

[ドキュメント一覧](../README.md)

共通設定とワークフローをZIP形式のアーカイブにまとめ、別のクラスターへの移行や設定の復元に利用できます。保持中のログ本文・履歴を含めるか選択できます。

## 保存される内容

| 対象 | 内容 |
| --- | --- |
| 共通設定 | タイムゾーン、PCグループ、ファイル処理の方針、安全確認、ログ・データの保持設定、ライブ編集など |
| ワークフロー | 通常のWFとレシピの定義、保存版、実際に有効だった版、反映方法 |
| ログ（任意） | クラスター内の各Coreが保持する、書き出し開始時刻までのログ本文・履歴 |

保存版と有効版を分けて保持します。たとえば編集中の最新版が未反映の場合、復元後もその最新版は未反映のまま残り、以前の有効版で動作します。無効だったWFを有効にすることはありません。

PC固有の `contents.toml`、ネットワーク設定、サービス登録、ClientHostの接続・表示設定、アプリケーション登録、シークレットの保存値は含みません。実行途中の状態、過去の実行結果・操作記録、WFが扱うファイル本体も復元対象外です。復元先には、WFで使うノード、スクリプト、ファイル、シークレットなどを別途用意してください。

## WebUIから書き出す

1. 書き出し元のクラスターと、使用可能なCoreを選択してください。
2. Dashboardの **Settings & maintenance** を開いてください。
3. 「クラスターのアーカイブ」で、必要に応じて「保持中のログ本文・履歴を含める」を選択してください。
4. 「アーカイブを書き出す」を押し、ブラウザーでZIPを保存してください。

ログを含める場合は、クラスター内の全参加Coreが `Ready` である必要があります。読み取れないCoreや省略されたログがある場合は、不完全なアーカイブを完成扱いにしません。各Coreで既に削除されたログは含まれません。

WebUIからは書き出しを行えます。取り込みにはCLI、またはセットアップの「修復」を使用してください。

## セットアップから復元する

1. **Clutch-CS-Setup.exe** で「修復」を選択してください。
2. 復元先のクラスターを一つ選択してください。同じ通信経路の、使用可能な対象を指定してください。
3. 「アーカイブから復元する」を選び、ZIPファイルを指定してください。
4. 「復元先にだけあるワークフロー」の扱いを選択してください。
5. 次の画面で取り込み元、追加・上書き・削除されるWF、ログ件数を確認してから実行してください。

| 復元先にだけあるWF | 動作 |
| --- | --- |
| 残す | 同じIDのWFを上書きし、取り込み元にだけあるWFを追加します。復元先にだけあるWFは保持します。 |
| 削除して取り込み元にそろえる | 同じIDのWFを上書きし、取り込み元にだけあるWFを追加します。復元先にだけあるWFは削除します。 |

共通設定は、どちらの場合も取り込み元の設定で上書きされます。**復元したWFは、元の有効状態ですぐに動作します。** 全参加Coreが `Ready` で、設定の競合が解消されている状態で実行してください。

## CLIから操作する

以下では実行ファイルを `contents-cli` と表記します。配布物の `files/cli/ReArtWord.Contents.BackgroundService.CommandLine.exe` に読み替えてください。`--url` は手元のClientHost、`--cluster` と `--peer` は操作先を指定します。

設定とログを書き出す場合は、次のように実行してください。ログが不要な場合は `--logs true` を省略できます。保存先に既存ファイルがある場合は上書きしません。

```powershell
contents-cli --url http://127.0.0.1:5081 --cluster studio-cluster --peer peer-a archive export --file C:\Backups\studio.zip --logs true
```

復元は事前確認と実行の二段階です。まず復元先へZIPを転送し、変更されるWFを確認してください。`merge` は復元先にだけあるWFを残し、`replace` は削除します。省略時は `merge` です。

```powershell
contents-cli --url http://127.0.0.1:5081 --cluster restored-cluster --peer peer-a archive preview --file C:\Backups\studio.zip --mode merge
```

応答の `response.added`、`replaced`、`deleted`、`logEntries` を確認してください。実行する場合は、返された `operationId` と `response.confirmation` をそのまま指定してください。

```powershell
contents-cli --url http://127.0.0.1:5081 --cluster restored-cluster --peer peer-a archive import --id <operationId> --confirmation <confirmation>
contents-cli --url http://127.0.0.1:5081 --cluster restored-cluster --peer peer-a archive status --id <operationId>
```

確認後に設定や参加Coreの実体が変わった場合は、元の計画では開始しません。新しい操作IDで事前確認からやり直してください。書き出し・事前確認には `--operation-id` で操作IDを明示することもできます。

## 結果の確認と中断時の扱い

設定は一つの共有取引で保存し、参加Coreの実際の有効状態まで確認します。ログは設定の反映確認後に取り込みます。結果の `steps` では設定保存、反映確認、ログ取り込みを区別して確認できます。

取り込んだログは、元のID・時刻・発生元を維持して、操作を受け付けたCoreへ保存されます。同じIDのログを重複保存せず、ログイベントの再発火や他のCoreへの転送も行いません。復元後も通常のログ保持設定が適用されます。

通信が切れたりCoreが再起動したりしても、復元を自動で再実行しません。結果が `unknown` の場合は、同じクラスター・Coreと操作IDで状態を確認してください。共有取引と反映状態の再確認には、次のコマンドを使用できます。

```powershell
contents-cli --url http://127.0.0.1:5081 --cluster restored-cluster --peer peer-a archive reconcile --id <operationId>
```

再確認では設定の再適用やログの再取り込みを行いません。未確認の処理が残る場合は成功扱いにせず、操作IDと結果を保持します。設定を確定したか不明な間は、その操作が取得した編集保護を維持します。

## サイズと保存期間

ZIP全体と展開後の内容は、それぞれ最大1 GiBです。設定本文は16 MiB、ログは1断片1 MiB・最大4,096断片です。上限を超える場合は、ログを含めずに設定を書き出し、必要なログは[ログ画面](logs.md)で別途取得してください。

Core上の完成済みZIPと、開始されずに残った転送資材は、24時間経過後のアーカイブ処理終了時に整理されます。ダウンロード中・直近の転送・結果不明の資材は保持し、操作の識別情報と結果記録は削除しません。ダウンロードしたZIPは利用者が管理してください。
