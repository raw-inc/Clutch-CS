# トラブルシューティング

[ドキュメント一覧](../README.md)

まず、問題が「導入」「接続」「処理」「保存・同期」「更新」のどこで起きているか確認してください。
結果が分からない操作は、同じ操作 ID の記録を調べてから再実行するか判断してください。

## 症状から探す

| 症状 | 最初に確認すること |
| --- | --- |
| セットアップが失敗する | 結果画面の「詳細」にある失敗段階、理由、操作 ID |
| 管理画面が開かない | ClientHost の起動状態、待受 URL、ポート番号 |
| PC・クラスターが見つからない | CoreService の起動状態、ClientHost 自身の NIC・IP、ブロードキャスト先、UDP ポート |
| Syncing が続く | 同じクラスターの Ready ピア、同期理由、保存先の容量・権限、TCP・UDP 通信 |
| ワークフローが動かない | 保存版と有効版、実行先 PC、開始条件、入力値、保留理由 |
| 保存できない・競合が出る | Storage status、競合一覧、元の保存操作の結果 |
| ファイル転送が進まない | コピー先の権限、同名ファイル、通信、ファイル予約 |
| 更新が止まった・失敗した | 対象ごとの進捗と元 Updater の結果、新旧プログラムの起動状態 |
| 遠隔画面・ターミナル・通信キャプチャへ接続できない | 対象機能の権限、CoreService の対応状況、ClientHost と CoreService 間の TCP 通信 |

## インストールに失敗した

結果画面の詳細を確認してください。スクリプトで導入した場合は、例外に表示される検証結果 JSON と `installation-result.json` を確認してください。

| 段階 | 確認する内容 |
| --- | --- |
| configuration | TOML の内容 |
| platform | 対象 OS・CPU・期待する版 |
| ペイロード | 配布物の不足・破損 |
| network | NIC と IP アドレス |
| files / permissions | 配置先と設定ファイルのパス・アクセス権 |
| register / recovery / start | サービスの登録・回復設定・起動 |
| ready | 起動したピアの参加状態 |

既存のインストール先がある場合は、新規導入ではなく更新・修復が必要な場合があります。
失敗後に残ったフォルダーを削除する前に、サービス登録と配置済みデータの状態を確認してください。
[保守の手順](maintenance.md)と[手動導入の結果確認](manual-install.md#うまく進まないとき)も参照できます。

## クラスターが見つからない・参加できない

1. 既存の PC で CoreService が起動していることを確認してください。
2. 同じクラスターの全 PC が、同じネットワークに属していることを確認してください。
3. ClientHost の接続設定で、ClientHost 自身の NIC・IP を指定していることを確認してください。
4. ブロードキャスト先、UDP ポート、選択したネットワークの Firewall 設定を確認してください。
5. 同期中の場合は Dashboard の理由を確認し、[同期の上限と再試行](../reference/history-storage.md#再参加同期の上限と再試行)に沿って状態を確認してください。

追加する PC の `initialize` を `true` に変えて参加エラーを解消しようとしないでください。
初回参加と、明示離脱したピアを戻す `cluster rejoin` は別の操作です。

## 処理が失敗した・結果が分からない

[ログを調べる](logs.md)の手順で、ワークフローの実行 ID と対象ノードの記録を確認してください。
外部 API のエラー、送信前の設定エラー、送信後の結果不明を区別してください。

ファイル操作では、OS のアクセス権不足、別の処理による予約、結果不明のまま残った予約を分けて確認する必要があります。
手動で予約を解放する場合は、[終了済み処理の予約を確認する手順](../reference/recovery.md#結果不明のファイル予約を解放する)を使用してください。

## 保存・同期が復旧しない

1. 影響を受けているクラスター・ピア・処理を確認してください。
2. 設定の保存版・有効版、同期理由、未完了の操作 ID を記録してください。
3. 競合一覧で候補を比較し、通常の画面・CLI で解消できるか確認してください。
4. 解消できない場合は、[手動復旧の確認項目と手順](../reference/recovery.md)に沿って対象データを保全してください。

稼働中の DB ファイルをコピーしただけでは、一貫したバックアップとは限りません。
DB の削除、別ピアの DB 全体の上書き、未完了操作の直接削除は、再実行を防ぐ記録も失うため行わないでください。

## 更新の結果を確認する

更新画面の再確認機能から、元の Updater の結果を取得してください。
旧版への復帰が確認できた失敗と、復帰したか不明な状態は別です。

`update.rollbackHealthUnconfirmed` では、新たな更新を始める前に、実際の配置・プロセス・Ready を確認する必要があります。
[旧版への復帰結果を確定する手順](../reference/recovery.md#更新途中の旧版復帰を確定する)を参照してください。

## 復旧後に確認する

- 対象ピアが継続して Ready になっていること
- 保存版・有効版と、ワークフローの待受状態
- 失敗・結果不明・未完了の操作が残っていないか
- 停止していた入力を再開してよいか

Ready を一度確認しただけで復旧完了とは判断せず、処理の継続と残る制限も確認してください。
