## アプリケーションを登録する

登録には、アプリケーション名、実行ファイルの絶対パス、作業ディレクトリが必要です。引数は 1 欄に 1 つずつ指定してください。引数がない場合は一覧を空にして保存してください。

空白・引用符・空文字は入力どおりに渡します。シェルによる変数展開などは行いません。登録後に名前を変えても ID は変わらないため、ワークフローからの参照を修正する必要はありません。

実行ファイル欄の「参照…」は、登録先ホストのドライブ・フォルダーを読み取り専用で開きます。ダブルクリックまたはEnterでフォルダーへ移動し、ファイルを選択して絶対パスを入力できます。手入力、親フォルダーへの移動、更新、次ページにも対応します。ファイル選択だけでは登録保存やアプリケーション起動を行いません。参照には対象CoreServiceのOS読取り権限を使用し、ブラウザーを開いているPCや全体の接続先へ切り替わることはありません。

「管理対象」は起動・停止・再起動を行えます。「監視のみ」は、既存プロセスのPIDと正確なOS起動時刻を指定して観測し、手動操作やスケジュールでも起動・停止しません。

## 起動セッションとウィンドウ

「起動アカウント・セッション」と「ウィンドウ表示」は個別に指定できます。新規登録では、Windows のログインユーザーのデスクトップと「既定（通常表示）」が選択されます。サービスのSession 0はログイン画面のセッションとは別であり、単にコンソール非表示指定を外すだけでは画面アプリを表示できません。

ユーザーのトークンと環境変数を使い、[CreateProcessAsUserの対話デスクトップ指定](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessasuserw)に従って起動します。

| 設定 | 動作 |
| --- | --- |
| Windows: ログインユーザーのデスクトップ | SYSTEMサービスではログイン中のコンソール利用者の通常権限で起動。対話起動中のCoreServiceではその利用者の環境を使用します。未ログインや必要なトークンを取得できない場合は起動を拒否し、SYSTEMへの代替は行いません。 |
| CoreServiceの実行アカウント・セッション | CoreService自身の権限とセッションを保持。Windowsサービスからの起動はSession 0になるため、利用者の画面へは表示されません。 |
| 既定（通常表示） | アプリケーションの通常表示を使用します。 |
| ウィンドウなし | コンソールを作成せず、初期ウィンドウを非表示にするよう要求します。アプリ自身が表示指定を無視したり、後から別ウィンドウを表示することまでは制御しません。 |

Windows以外のOSでは「ログインユーザーのデスクトップ」の自動選択もCoreServiceの現在の実行環境を使用します。画面表示はそのOSのデスクトップ環境に依存します。既存の `launch` 未指定登録は、従来のCoreServiceアカウント・コンソール非表示を維持します。別項目の編集だけで起動ユーザーや表示方法は変わりません。既存の画面アプリをユーザーデスクトップで起動したい場合は、この二項目を選択して保存してください。

手動操作、スケジュール、自動復旧、ワークフローの起動・再起動ノードは同じ保存設定を使います。変更は次回起動から適用します。引数、作業ディレクトリ、PIDと起動時刻による監視は維持し、CoreService再起動時も同じ実体へ再接続します。通常停止では、別のWindowsセッション内のアプリケーションにもPIDと起動時刻を照合してウィンドウ終了を要求し、その後は登録された待機・強制終了方針に従います。

## 自動監視と復旧

「Core稼働中に自動で監視する」を有効にすると、ブラウザーやワークフローを開いていなくてもCoreServiceが監視します。正常終了（終了コード0）と異常終了を分けて再起動の対象にでき、遅延時間と試行上限を指定できます。遅延は最初の再起動にも適用します。新規フォームでは自動監視を無効、再起動対象は異常終了、遅延1,000ms、試行上限3回を初期値にしています。既存登録は自動監視を勝手に有効化しません。

試行回数は、自動復旧を含めてアプリケーションの起動成功を確認するたびに0へ戻します。実行ファイルがない場合や、ログインユーザーが利用できず起動前に拒否された場合は加算しません。起動結果が不明な場合は回数と確認待ち状態を保持し、自動で再送しません。CoreServiceの再起動や、すでに起動しているアプリケーションの再照会だけでは回数をリセットしません。現起動回への安定信号（`process.signal` の `stable`）または「手動で復旧を確認」でも回数をリセットできます。

試行上限は起動成功までの試行に適用されます。OSへ起動を依頼した後の失敗は回数に含め、プロセスが作成されていないことを確認できた場合に限り、設定した遅延後に上限まで再試行します。起動成功後に終了した場合は、次の復旧を新しい試行として扱います。手動停止したアプリは自動復旧しません。CoreService以外から停止する場合は、先に「自動復旧を抑止」を使用できます。終了コードを取得できなかった場合は0とみなさず、監視中の未取得終了を再起動するかも詳細設定で指定します。

CoreServiceが終了しても管理しているアプリケーションを一律には停止しません。CoreService再起動後は保存済みのPIDとOS起動時刻を照合し、同じ実体が生存していれば監視を再開します。CoreService停止中に終了したなど、終了事象そのものを観測できなかった場合は、終了信号や自動再起動を後追いしません。結果不明の起動操作を新しい起動として再送せず、実体確認から解決します。

## 運用ログ

監視の開始、手動・予定・自動復旧による起動の試行と結果は、共通ログへ次のレベルで記録します。LogViewerで全クラスターまたは対象ピアを選び、メッセージコードで絞り込み、詳細の論理名から対象アプリケーションを確認できます。

| 事象 | レベル | メッセージ |
| --- | --- | --- |
| Core起動後・登録更新後の最初の自動監視 | INFO | `Application.MonitoringStarted` |
| OSへ起動を依頼する直前 | INFO | `Application.StartAttempted` |
| OSへ再起動の新しいプロセス作成を依頼する直前 | INFO | `Application.RestartAttempted` |
| アプリケーション起動の成功 | INFO | `Application.Started` |
| 手動・予定・自動復旧による再起動、または自律再起動した後継プロセスの確認 | INFO | `Application.Restarted` |
| 監視中に確定した終了。正常・異常終了と予定停止を含む | WARN | `Application.Stopped` |
| 起動失敗、または起動結果の確認不能 | ERROR | `Application.StartFailed` |
| 復旧試行上限への到達 | WARN | `Application.RecoveryExhausted` |

試行ログは起動完了を表しません。対応する `Started`・`Restarted` または `StartFailed` を確認してください。起動成功はOSプロセスの作成と状態保存の完了であり、アプリケーション固有の準備完了とは別です。

起動・終了ログの詳細には登録ID・論理名・起動回・確認済みPIDと起動時刻・終了コード・予定停止の有無・復旧試行回数を含めます。失敗時は理由コードと未実行／結果不明の区別も保持し、引数や実行パス、例外本文は複製しません。結果不明を「プロセスが起動していない」とは断定せず、実体確認から解決します。

起動済みのスキップ、遅延待ち、ログイン待ち、監視の再接続では起動の成功・失敗ログを追加しません。実行ファイルや起動ユーザーの不足で自動復旧できない場合は、`Application.Automation` に理由を記録し、同じ理由が続く間は重複させません。同じ終了や上限到達の再観測では再記録せず、CoreService停止中の未観測終了は後追いしません。CoreService再起動後の監視開始は新たに記録します。自律再起動の確認待ちでは終了を先に記録せず、後継の確認または待機期限後の終了確定時に記録します。ログ保存に失敗しても、アプリケーション操作の成否は変わりません。

## アプリケーション自身による再起動

「自律再起動の確認待ち時間」を指定すると、旧プロセスの終了後も設定時間だけ後継プロセスを探します。既定の0msは無効です。この間は終了信号を出さず、CoreServiceによる自動再起動も行いません。照合モードは次の2種類です。

| モード | 後継の条件 |
| --- | --- |
| 実行ファイルと引数の一致 | 実行ファイルの絶対パスと、引数の値・順序が一致する |
| 実行ファイルのみ一致 | 絶対パスが一致すれば、引数の変更を許容する |

最後に旧プロセスの生存を確認した時刻より前から存在したプロセスは対象から除きます。Windowsでは観測できた起動セッションも固定し、別セッションの同名アプリケーションは後継へ取り込みません。一意な後継を確認できれば、新しいPID・OS起動時刻・起動回IDへ監視を移し、再起動信号を出します。後継の起動成功を確認した場合も、復旧試行回数を0へ戻します。候補が複数、またはパス・引数の照合が不能の場合は、期限後も自動操作を保留して理由を表示します。

後継がないことを確認して期限に達した場合は、そこで終了を確定し、その後に通常の復旧遅延を適用します。

照合条件と期限は確認区間の開始時に固定します。CoreServiceが確認待ち中に停止して、後継への引継ぎを確認できなくなった場合も、終了を推測して復旧しません。通常稼働中には後継探索を行いません。

Windowsの引数照合は、候補PIDが見つかったときだけ標準の[Win32_Process.CommandLine](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-process)を照会し、[CommandLineToArgvW](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-commandlinetoargvw)で引数へ分解します。

Linuxでは`/proc`を使用します。取得権限がない場合や引数取得に対応しないOSでは、厳密照合を成功扱いにしません。実行ファイルのみの照合は、OSからそのパスを確認できる場合に使用できます。

## スケジュール起動

一回の日時、毎日、曜日指定を選び、タイムゾーンを指定します。既定はUTCで、日時実行ノードと同じ暦計算を使用します。存在しないタイムゾーンや、一意に決まらない夏時間の日時は受け付けません。

起動済みの場合の動作は「スキップ」または「再起動」を指定できます。再起動では通常終了を待つ時間と、終了しなかった場合の「手動対応待ち／強制終了」を明示します。終了を確認できないまま追加起動しません。

日時・曜日指定では、CoreService停止中・メンテナンス中に過ぎた予定は見送り、過去の予定をまとめて実行しません。予定の受付を保存してからOS操作を行い、受付後にCoreServiceが停止しても同じ予定を重複実行しません。手動停止による自動復旧の抑止とは別に、明示登録した次のスケジュールは起動契機になります。

「PC起動時」は、PC起動からの遅延を0〜86,400,000msで指定できます。既定の0msはCoreServiceが運用可能になり次第、正数はOS起動からその時間が経過してから起動します。CoreServiceの準備が遅れて期限を過ぎていても、同じPC起動の未受付分を一度だけ扱います。新規登録、遅延時間の変更、無効からの再有効化は次のPC起動から適用し、保存しただけではアプリを起動しません。

PC起動予定の待機中は監視を続けますが、自動復旧による起動は保留します。前回の起動で異常終了していたアプリも、設定した遅延より前には自動起動しません。同じアプリにPC起動予定が複数ある場合は、最初の予定を処理した後、自動復旧を再開します。手動やワークフローからの明示的な起動は引き続き利用できます。

ログインユーザーのデスクトップで起動する場合、未ログイン時は既定で「ログイン完了を待って起動」です。「その回は起動しない」も選べます。待機中は起動要求や受付記録を繰り返さず、ログイン後に一度だけ受け付けます。CoreServiceアカウントで起動する設定ではログインを待ちません。起動済みのスキップ／再起動は日時指定と同じ方針です。

PC起動の識別子と受付状態を保持するため、CoreServiceの更新・再起動やメンテナンス復帰では同じ起動を繰り返しません。スリープ・休止からの復帰も新しいOS起動とは扱いません。遅延の判定には壁時計ではなくOSの経過時間を使います。WindowsはSystemログのOS起動イベントと`GetTickCount64`、Linuxは`/proc/sys/kernel/random/boot_id`と`/proc/uptime`を使用します。

Windowsで新たなOS起動を伴わない高速スタートアップは同じ起動回として扱います。起動情報を確認できない環境ではPC起動予定の新規登録を拒否し、CoreService起動をPC起動の代わりに使用しません。ほかの日時指定は引き続き利用できます。

## WorkflowEditorからの利用

プロセス操作ノードの「登録アプリケーション」欄では、実行先ホストの登録を論理名で検索して選択できます。選択結果は安定した登録IDとして保存します。複数の実行先候補がある場合は所有ホスト・ピアも表示するため、実行対象の登録に合わせて選択してください。

- `process.start` / `process.stop` / `process.restart`：起動・停止・終了確認後の再起動。
- `process.lifecycle`：起動・停止・再起動に対応した独立の信号と、事象の詳細・PIDを出力する継続監視。
- 起動・停止・再起動・観測・復旧・準備待ち・既存監視ノードには、状態オブジェクトに加えて独立の`pid`出力があります。未確認はnull、終了通知では終了した実体のPIDです。

`process.lifecycle`は監視を開始しただけでは信号を出しません。明示的な再起動操作では旧実体の停止信号と新実体の再起動信号が発生します。自律再起動の確認に成功した場合は再起動信号だけを出し、確認待ち中の旧実体の終了を停止信号として先に流しません。既存の`process.watch`は、そのワークフローの監視・自動復旧設定を引き続き使用できます。

## Windowsの表示を検証する場合

`CONTENTS_TEST_APPLICATION_LAUNCH=1` を設定すると、専用コピーの小さいGUIを使う結合試験を有効にできます。通常の単体試験に加え、SYSTEM・Session 0の実CoreServiceからユーザーのセッションへ起動し、通常表示／非表示、スケジュール、自動復旧、CoreService再起動後の監視、通常終了を検査します。本番の登録やワークフローは使用しません。

SYSTEMで実行するときは、試験プロセスに別セッションへの子起動を禁止するJob制限が付いていないことも確認します。

この環境では `dotnet test`／`dotnet vstest` の仲介経路に終了連動Jobが付くため、SYSTEMの独立した試験プロセスから `dotnet exec <SDKディレクトリ>/vstest.console.dll <結合試験DLL> --TestCaseFilter:FullyQualifiedName~CoreLaunchesAndClosesInteractiveWindowAfterRestartAsync` のように実行します。

CoreServiceやOSのセキュリティ設定を緩めて通す試験ではありません。GUI試験は実際のウィンドウを短時間作るため、表示先の利用時間を考慮して実行してください。
