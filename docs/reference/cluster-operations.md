## 表示用タイムゾーン

Dashboardの「設定・保守」→「表示設定」で、日時表示に使うタイムゾーンを選択します。既定はUTCです。このブラウザーへ保存し、WorkflowEditorのPreview・デバッグ、LogViewer、Dashboardの観測・履歴表示などに適用します。別のブラウザー・Web クライアントアドレスでは個別に設定してください。

LogViewerの日時検索とスナップショットの基準日時も、項目名に表示したタイムゾーンで解釈します。夏時間切替で存在しない日時や二度現れる日時は入力を拒否します。その時間帯の特定が必要な場合は表示設定をUTCに切り替えて指定してください。保存記録・診断用JSONの日時、OSの時計、ワークフローのスケジュールは変更しません。クラスターで共有する「稼働用タイムゾーンID」は別設定です。

## 保存・共有・反映

共有保存の大きな準備要求は、相手の起動実体へ読み取り専用の対応照会を行い、対応と展開上限を確認できた場合だけBrotliで可逆圧縮して送ります。旧版・未確認・圧縮で十分小さくならない本文には従来形式を使用します。展開時は上限、終端、長さ、ハッシュ、元操作IDを確認してから通常の保存準備へ渡します。全固定対象の準備・コミット確認は省略しません。準備要求の送信後に応答を確認できない場合は、別形式で書き直さず元操作の準備状態を照会します。

確定段階は操作IDだけを送り、永続化する内容も変更しません。

- **保存・共有・有効化**は別段階です。自動スナップショットが失敗した場合も本体保存の結果を保持し、新設定の自動反映を保留します。開始済みの一件は元設定・共通運用版・追跡方針を保持します。
- **共通運用設定**の timezone、ファイル競合方針、ファイル内部失敗方針、ホストグループはクラスターで共有します。TOML は明示新規クラスターの初期値とピア固有の起動・NIC・資源許可に使い、通常再起動で共有設定を上書きしません。
- **内容の競合**は影響範囲を表示し、無関係な処理を続けます。保存候補だけの競合では有効版を維持し、有効設定の未解消項目に依存する処理は保留します。候補比較と明示解消は画面と CLI から行い、対象版が変わった場合は再確認します。
- **明示離脱**は自動再参加しません。種類別許可の範囲でローカル保存・実行を続け、結果に「局所保存・未共有」を表示します。再参加後は元の共有版と比較し、非競合の統合、競合の比較選択、ローカル変更の明示破棄を行います。結果不明の固定操作は元 ID を照会します。
- **起動処理**は `service.started` 待受ノードから構成します。各ピア実体のワークフロー・ノードごとに一度発生し、設定の位置変更や役割交代で一回で完了する処理を繰り返しません。`startOnLoad` は待受ノードの待受開始に使用します。
- **部分復元**ではノード集合・サブグラフ・ホスト・ホストグループを明示します。未保存の影響範囲を保存または取消し、復元中はその範囲を編集保護します。対象外の設定や下書きは維持し、結果不明では元操作を照会・回復します。
- **一時安全操作**は人為停止、一時続行、通常判断への復旧を分けます。一時続行は承認時の障害回復または全承認実体の入替で失効し、人為停止は明示解除まで維持します。確認は共通既定・ノードの指定に従い、古い画面の状態でも新しい操作は現担当の受付順に適用します。
- **詳細追跡**は保存済みの通常方針と一時追跡を分け、入力・出力・生通信を選べます。秘密値を除外し、時間や資源圧迫だけでは自動解除しません。「一時追跡を解除して Cluster 停止を要求」は解除共有後に固定実体へ停止要求を送ります。任意のクラッシュ全停止と分断を観測だけで区別したとは扱いません。

ワークフロー共有状態のローカル変更は、再参加後に統合します。統合の直前に参加状態が変わり、共有要求の未実行を確認した場合は、次の参加確認後に同じ更新IDで統合できます。受付後の結果不明や、開始したか確認できない中断は再送せず、ローカル変更と元の操作記録を保持します。

## 結果の確認

ワークフローの一件が失敗・結果不明・未実行で終了した場合、所有ピアはトレース設定に関係なく `workflow.unsuccessful`（ERROR）を記録します。確認済みの取消は `workflow.cancelled`（WARN）です。実行ID（causationId）、定義版、開始・終了時刻、非成功ノードと対象ピア・理由コード・説明を含みます。

`unsuccessfulNodeCount` は失敗・結果不明・取消に加え、`input.unavailable` などの実施できなかった処理も数えます。設定値の供給や分岐非選択など正常な未実行は原因候補から除きます。原因候補は最大16ノード・各8対象に絞り、対象内でも実際の障害を先に載せます。省略数は `omittedNodeCount`・`omittedTargetCount` で示します。説明は各512文字までとし、長すぎる説明は全体を省略します。

個人情報を含む指定のワークフローでは説明を伏せます。入力・出力本体は複製せず、正常終了の記録も増やしません。

ノードのERRORログには、理由コードに加え `data` にノード実行ID、定義版、結果と説明を記録します。例外で終了した有限ノード・待受ノードでは `data.exception` に例外型、説明、スタックトレース、HResult、内部例外を残します。ノード自身が例外を失敗結果へ変換するC#／Python／JavaScript、AI、HTTP、ファイル操作・転送でも、実行ピアに `node.exception` を記録します。

スクリプトの結果値へ例外本文を追加することはありません。ワークフロー実行基盤の例外は終了ログにも同じ形式で保持します。内部・集約例外は親を含め最大8件、説明は各2,048文字、スタックは各16,384文字、全体は合計32,768文字以内です。上限超過の自由文は一部分だけを切らず全体を省略し、`Truncated` で省略を示します。例外の任意Data、入力・出力、ローカル変数は収集しません。

登録済み秘密値は既存の共通ログ境界で伏せ、個人情報を含む指定のノード診断は通常ログに本文を残しません。

調査時はLogViewerでワークフロー・実行ID（`causationId`）を絞り込み、所有ピアの終了ログと、実行先ピアのノードログを確認します。別の信号から派生した子実行が失敗した場合は、子の終了ログの `parentExecutionId` から元の一件へ辿れます。ForEach内のノードログは同じ一件に結び付き、並列要素の個別呼出しは `data.executionId` で区別します。

スクリプトに小さい `maxBytes` を設定している場合、失敗診断もその出力量制限へ収めます。詳細が入らない場合は `Truncated` と省略理由を残し、診断の増量だけで確認済みの失敗を「結果不明」へ変えません。

AIの `ai.incomplete` では、取得できた範囲で処理段階、接続先ホスト、NIC・ローカルIP、HTTPステータス、ソケットのエラー種別・OSエラー番号を確認できます。AI・HTTPの通信例外には型とスタックを追加しますが、要求・応答本文やURLのパス・クエリが混ざり得る例外本文は含めません。`ai.incomplete` だけでは外部サービスが要求を受理したとは判断できず、送信済みか不明な要求を暗黙に再生成しません。

終了ログは実行の取消トークンとは独立して受付を試みます。保存先の障害は元の処理結果へ伝播させず、既存の有限ログキューと欠落統計で扱います。プロセス強制終了やOS停止により終了処理自体が実行されない場合まで、ログの永続化を保証するものではありません。

Dashboardの「ワークフローの活動」と「直近ログ」は上段の状態カードと共通の背景・余白で表示します。ワークフローは設定した表示名を使い、ホバーで元のIDを確認できます。名前の照会は表示中のワークフローだけに絞り、本文を取得せず最大30秒保持します。未取得の名前はIDで表示します。

失敗、未実行、結果不明を分けて表示します。副作用が始まったか不明な操作は、新しい ID を作って自動再実行しません。要求 ID と元操作 ID を保持して照会してください。入力・出力・待機には有限の件数/byte 上限があり、上限到達を正常完了として隠しません。ファイルの補償に成功しても、すでに送った通信や実行した外部プロセス・AI 処理まで取り消したことにはなりません。

ワークフロー・スナップショット・実行履歴・ログの一覧は件数とバイト上限を持つページで取得します。大きなワークフロー本文は保存版・有効版を固定し、断片の位置と全体ハッシュを検査してから編集に使います。実行結果の詳細を保持・返却できない場合も、確認済みの成否と対象別理由は要約に残します。ログ検索時の省略は対象と理由を表示し、保存済みの元ログを削除しません。

ログ検索では各ファイルに含まれるイベント時刻の最小・最大を索引に保持し、検索範囲や最新ページへ入らない古い本文の読取りを省きます。保存時刻では判定しないため、遅れて届いたログも対象になります。時刻索引がない既存ファイルは最初の完全な読取りでメモリ内の索引を補完します。検索だけのためにファイルや永続索引を書き直すことはありません。同時刻のログは識別子で順序を固定し、ページの重複・欠落を防ぎます。

LogViewerの検索範囲は、接続先の選択有無にかかわらず「観測可能なすべてのクラスタ」が既定です。「選択中のPeer」へ明示的に切り替えることもできます。接続先の選択自体は変更しません。全クラスターでは、Web クライアントが観測した各ピアの保持ログを日時順にまとめます。同じクラスター内に転送された同じログは一件にまとめ、クラスターが異なる記録は区別します。取得不能・部分結果の取得先は未確認として表示します。

クラスター列と詳細・ワークフローへの移動先は、検索後に選択中のクラスターが変わっても取得元を維持します。トレース・保持設定を変更する場合は接続先を選択してください。

「直近の履歴のみ検索する」は既定でONです。一定日数で区切るのではなく、現在非圧縮で保持されているログだけを対象にし、圧縮済み本文を展開しません。OFFにすると保持中の圧縮履歴も対象になります。切替時は先頭ページから検索し、次ページと自動再取得もその条件を維持します。画面を開き直すと既定に戻ります。管理API・CLIでは `uncompressedOnly: true` で同じ限定検索ができます。

既存の要求との互換性のため、この項目を省略したAPI検索は圧縮履歴も含めます。

**.logで保存** と **ZIPをダウンロード** は、現在のフォームの検索範囲・日時・レベル・ピア・ワークフロー・ノード・関連ID・本文・非圧縮限定の条件を使用します。画面でまだ開いていない続きのページも対象です。開始時の観測先と検索終了時刻を固定し、処理中に届く新着を追い続けません。検索途中のログ削除・保持期限超過を止めるスナップショットではありません。

`.log` はUTF-8の単一ファイルです。先頭の `Request` に検索条件と取得先、各ログに表示用の本文と詳細JSONの `record`、末尾の `Summary` に件数と取得結果を記録します。日時は画面の表示タイムゾーンで出力します。取得できなかった範囲は `Summary` の `unconfirmedSources`、詳細の省略は各 `record` の `omission` で確認できます。ClientHostは全件をメモリや一時ファイルへ保持せず、取得した分から送信します。

ZIPには `logs-00001.txt` / `logs-00001.json` のように番号の対応するペアを格納します。テキストはUTF-8で、`{DATE} [{LEVEL}] {Workflowの論理名} {Nodeの論理名} {本文}` の一件一行形式です。日時は画面の表示タイムゾーンとUTCオフセット付きで出力し、改行等は `\n` のようにエスケープします。定義に名前がない場合や取得不能・削除済みの場合はID、対象を持たないログは `-` を使用します。

名前は出力時点の保存定義から取得し、当時の名前とは限りません。JSONは元のログ・クラスター・取得先・解決した名前・名前の保存版・詳細省略情報を保持します。個人情報等の取り扱いは通常のログ検索と同じです。

`request.json` に検索条件・取得先、`summary.json` に件数・未確認の取得先・詳細省略件数・名前の代替件数・出力上限への到達を記録します。取得できない範囲や省略がある場合は画面にも部分結果と表示します。全ピアから返ってきた同一クラスターの同一ログは一件にまとめ、別クラスターの記録は区別します。

ClientHostはZIPと全件JSONを一時保存せず、取得した分から圧縮してブラウザーの標準ダウンロードへ送ります。一ペアは最大1000件か元ログJSON約1MiB、取得先別の先読みは合計約16MiBのJSON予算、管理通信は最大2件並列です。ZIPの索引も無制限に増やさないため最大4096ペアとし、続きを残した場合は `summary.json` の `partLimitReached` と部分結果表示で明示します。必要に応じて日時等を絞り直してください。

同じClientHostで同時に送信するログファイルは、形式を問わず一件です。接続断・画面離脱・取消・30分の期限・ClientHost停止で検索と送信を止め、未完了の出力を成功扱いにしません。未開始の受付は2分、完了状態は最大8件・15分で解放します。出力ファイルはサーバーに残らないため、再保存は新しい検索として開始します。

自動再取得は既定で無効です。5・10・30・60秒から選ぶと、確定した検索条件で最新の先頭ページを再取得します。取得完了から次の間隔を待つため、遅い照会を重ねません。全取得先が応答できない場合は直前の結果を保持し、未確認表示にします。詳細を開いたログは更新中も保持します。前後のページへ移動すると自動再取得を無効にします。ページ移動中は検索条件・取得先・検索終了時刻を固定し、新着は再検索時に取り込みます。画面を離れると検索と自動再取得を停止します。

## 用途別保存と保存不能時の扱い

各ピアの保存先には、そのPCのローカルディスクを使用してください。CoreServiceはローカル固定ディスク上のSQLiteにWAL（書込みログ）を使用し、各コミットの同期書込みを維持します。接続はCoreServiceの稼働中に再利用し、終了時に解放されます。ネットワークドライブなど、ローカル固定ディスクと確認できない保存先ではWALへ切り替えません。

保存ファイルをコピー・移動する場合は、その保存先を使用するCoreServiceと更新処理を停止し、保存ディレクトリ全体を扱ってください。`state.db-wal` が残っている場合は確定済みの変更を含むことがあるため、`state.db` だけを取り出したり、付属ファイルを削除したりしないでください。

用途別の保存方式と障害時の扱いは、起動前の TOML で指定します。次は設定を JSON、実行状態などの既定を SQLite に保存し、設定保存に失敗したときも明示候補を使用する例です。

```toml
[storage]
directory = "data-peer-a"
backend = "sqlite"

[storage.purposes]
configuration = "json"

[storage.availability]
maximumItems = 256
maximumBytes = 1048576

[storage.availability.configuration]
saveFailure = "UseUnsaved"
# fallbackBackend = "Sqlite" # 別媒体への候補保存も事前指定する場合

[storage.availability.runtime]
offline = "LocalUnconfirmed"
```

未指定では保存失敗時に `KeepConfirmed`、切断中は `LastConfirmedReadOnly` です。内部データを切断中は一切利用させない場合は `Unavailable`、端末内の未確定変更を許す場合は `LocalUnconfirmed` を指定します。ワークフローのオフライン下書きは独立した編集機能です。`processes` と `diagnostics` に候補採用・切断中編集を指定すると、起動時に拒否します。

設定・内部状態では、保存不能時に有効版を維持するか、明示した候補を使うかを選べます。未保存のまま有効な版と復旧可能な版を分けて表示し、代替媒体は事前に指定した場合だけ使用します。プロセス操作や診断値を、候補の採用によって実施済み・観測済みにはしません。

画面下部の「保存状態」から、各ピアが通知した未保存有効・未保存候補・ローカル未統合の件数と、接続先の Saved／Effective／Recovery を確認できます。画面が表示できたことや保存要求の受付だけでは、永続保存済みとは扱いません。容量上限や確認不能により値を返せない場合も、正常な null 値と区別します。

詳細な境界は [保存不能・切断時の内部候補](../../src/ReArtWord.Contents.BackgroundService.Infrastructure/Persistence/Availability/README.md) と [用途別保存](../../src/ReArtWord.Contents.BackgroundService.Infrastructure/Persistence/Routing/README.md) を参照してください。

## 通信と遠隔実行

クラスターの生存通知は、内部照会のタイムアウトや一時的な保存失敗で永久停止しません。参加条件を確認できない間は参加不能を通知し、条件回復後に同じ実体で再参加します。生存通知はプロセス実体内の順序番号を持ち、遅れて届いた古い状態で新しい離脱・参加状態を巻き戻しません。CoreService と ClientHost は同じ版で配置してください。

管理UDPは通常の要求をMTU 1500内のパケットへ分割します。同じ配送が処理中なら受信処理を増やさず、再送時も作成済みパケットを利用します。永続受付の待機は保存先の短周期定期照会を行わず、受付・完了通知を共有します。更新と遠隔ノード実行で照会だけが一時的に欠測した場合は、元の要求IDを読み直します。応答不明を根拠に副作用を新しい要求として再実行せず、確認期限・取消・実体消失を区別します。

対応するCoreService間の保存・実行・ファイル予約とその照会は、CoreService起動中に同じTCPポートを使う専用受付を優先します。クラスターに指定したNIC・IPv4へbindし、送信元IP、双方の起動実体、接続許可、本文上限を検証します。受付ポートは起動時に確保し、既存UDPの参照専用照会で発見します。OSのファイアウォールではCoreService実行ファイルのTCP受信も許可してください。生存通知と画面通知は既存UDP、全体同期やFileTransferはそれぞれの専用経路を維持します。

旧版への配送、TCP受付の未対応、接続・ハンドシェイクの失敗は従来UDPへ戻します。要求本文の送信を始めた後の切断はUDP再送せず、元の要求・準備・確定記録の照会で判断します。TCP接続成功そのものをファイル書込みや共有保存の成功とは扱いません。

送信は実行要求8件、保存・参照16件、元結果の照会8件、受信はそれぞれ16件・8件・8件の独立した枠で制限します。対応するCoreService間では本文を確保する前に受付区分を識別し、処理待ちが結果照会や保存段階を塞がないようにします。旧版との接続では従来のフレームを使用します。待機中の取消は未送信のまま終了します。TCP接続後の受付待ちは通常要求の確認期限を使い、一時的な混雑を短い接続タイムアウトと混同してUDPへ集中させません。

同じ既知ピア実体から確認した要求・応答も生存観測へ反映しますが、Syncing・Unavailableなどの状態を通信だけでReadyへ昇格させません。

完全な応答を確認したTCP接続は、同じピア実体へ再利用します。Web クライアント側の待機接続は最大64本で、15秒を超えた接続、実体・接続許可・アドレスが変わった接続、切断済み接続は送信前に作り直します。受信側は最大256接続を保持し、本文を確保・処理する枠は受付区分ごとに制限します。旧接続は通常要求の枠を使用します。30秒間入力のない接続は閉じます。本文受信と応答送信の期限は実処理の待機時間と分離し、処理終了後の応答を期限切れの受信トークンで捨てません。

ファイル予約の取得・解放・確認、および全対象操作の退避・復元・解放は、元要求の永続受付後に短い応答待ちで通信枠を返します。完了前なら呼出側は同じ要求IDの結果だけを照会します。調停待ちの全件が通信枠を占有して後続の受付期限まで消費することを防ぎ、受付済み操作は受付期限を過ぎても元の保存確認まで追跡します。新しい要求IDで同じ副作用を再送することはありません。

遠隔実行の受付・完了は、要求IDごとの現在値をSQLite／JSON媒体へ耐久CASで保存します。受付記録自身には、汎用の操作履歴・保存先履歴を重ねて作りません。開始前と完了後に保存し、内容の不一致の検出、予約との排他、再起動後の同じ要求IDでの結果照会に対応します。保存結果が不明な要求を暗黙に再実行しません。

管理通信のNIC確認は同じOS観測を共用し、構成変更通知で直ちに再検証します。通知されない物理断も最長約1秒で再確認します。
