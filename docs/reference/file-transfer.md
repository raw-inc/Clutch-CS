## FileTransfer (クラスター)

1. ヘッダーの`FileTransfer`から`Cluster · Host ↔ Host`を開き、共通の「転送クラスタ」を選択、または「自動」のまま、左右のホスト（PC）を選択してください。同じPC上の複数ピアは一つの候補にまとめます。「自動」では、左右の PC に共通する利用可能なクラスターが ID 順に一つ選択されます。明示したクラスターに属さないホストや、共通クラスターがない組合せでは転送を開始しません。
2. シングルクリックで項目を選択し、ドライブやフォルダーはダブルクリックで開いてください。フォルダー名にフォーカスした状態でEnterを押して開くこともできます。`↑ Up`で親へ、`Drives`でドライブ一覧へ戻れます。パス欄に直接入力してEnterで移動することもできます。閲覧は対象CoreServiceのOS読取り権限で行い、リンクを通る参照は拒否します。コピーとワークフローのファイル操作も、対象CoreServiceのOSアクセス権の範囲で行います。既存の`[files].roots`は設定互換性のため読み取りますが、これらの操作範囲は制限しません。WorkflowEditorのパス選択もドライブから参照できます。内部の更新stagingなど専用領域の検証は維持します。
3. チェックしたファイル・ディレクトリを転送ボタンで相手側の開いている場所へコピーしてください。項目を相手側のフォルダーや開いている場所へドラッグしても追加できます。移動ではなくコピーで、空フォルダーも維持します。
4. 転送完了を検出すると、左右で開いている転送先フォルダーだけを自動更新します。読み込み中または項目選択中は更新を保留し、操作が落ち着いてから反映します。コピー中にも次の項目を追加できます。共有転送キューに128件ごとのページで進捗を表示し、他画面でもフッターの`FileTransfer`に進行中・待機中の総数を表示します。

同じホストの代表ピアは、参加可能な候補の優先度・連続参加開始時刻・ピア ID の順で選択されます。選ばれたCoreServiceのOSアクセス権を使い、権限不足や転送失敗で別ピアに切り替えません。クラスターやホストの変更で実体が変わると、古いファイル選択を消してドライブ一覧から開き直します。コピー追加前にも起動実体を再確認します。

このクラスター選択欄はFileTransfer専用画面のものです。ワークフローの`file.transfer`ノードは常に所属クラスター内で実行し、クラスターを指定する設定は持ちません。

キューの所有者は**コピー先のCoreService**です。すべてのClientHostが発見したピア側のキューを集約し、別PCからも受付内容と進捗を共有します。同じピア群を発見するネットワーク設定を各ClientHostへ設定してください。特定PCのブラウザー、画面、接続選択やClientHostの存続には依存しません。宛先CoreServiceごとに受け付けた順で処理し、別宛先への転送は独立して実行できます。

キューは宛先CoreServiceのdata配下へ保存します。CoreService再起動時には待機中の要求を復元し、開始済みだったコピーを`Unknown`として保持します。開始済みコピーを自動で繰り返しません。元ピアの起動実体が変わった待機要求も、別実体へ付け替えず失敗とします。

転送のクラスター・ピア・起動実体・元パス・宛先はキュー登録時に固定します。元ピアが再起動した場合に別実体へ付け替えません。既存の同名項目は上書きせず、リンクを通る操作も拒否します。分割内容と全マニフェストを検証してから宛先へ確定します。確定要求後に応答が失われた場合は、元の永続操作の結果を期限内で照会します。照会しても確認できない場合は`Unknown`として残し、宛先を確認してから次のコピーを開始してください。新しい操作IDで確定を自動再実行しません。

宛先CoreServiceごとに待機キューは32件、一件の列挙上限は10000項目、完了履歴は最大100件・1時間です。転送片は対応CoreServiceとのTCPでは最大1MiB、従来の管理経路では最大32KiBで、大きなファイルの全体をメモリへ読み込みません。ClientHostは最大256ピアを観測し、通信断時には前回値と確認不能なピア数を表示します。キュー表示中・転送中・結果不明・照会失敗時は約2秒周期で確認します。

画面からの参照が5秒間なく、取得済みキューが空または全件終了している場合は約10秒周期に抑えます。他Web クライアントから追加された転送の背景表示には、その分の遅れが生じます。転送本体の実行間隔は変えません。切断したピアのキャッシュも1時間・最大512実体で回収します。成功後は転送用の一時状態を削除します。通信断で削除できなかった一時状態や結果不明の状態は、確定済みファイルとは区別して残る場合があります。

FileTransferのホスト間キューとブラウザー中継は、対応するCoreServiceとの間で固定NIC・固定起動実体に対するTCP接続を使います。一回限りの32バイトトークンは15秒で新規接続を締め切り、CoreServiceは同時8接続、各フレームは3MiB、ファイル片は1MiBまでに制限します。本文の転送開始後に切断した場合は別方式で暗黙再送せず、既存の段階保存と全体SHA-256検証で確定前の内容を保護します。

TCP受信には既存のネットワーク方針に沿ったCoreService実行物へのLAN内許可が必要です。未対応先や接続前の未到達時は従来の32KiB経路を使います。確定処理は従来の永続受付を通し、TCP経路から直接確定しません。

### 転送先CoreServiceが別のネットワークも使う場合

既定ではCoreService自身の`[cluster]`のNIC・IP・ブロードキャスト範囲で転送元を発見します。同じNIC上の異なるUDPポートは、ClientHostの実発見結果をもとにコピーの期間だけ監視します。異なるNICやブロードキャスト範囲が必要な場合は、**宛先の CoreService 自身の**設定に追加します。ClientHostや他PCのInterface IDをコピーしません。

```toml
[transferQueue]
networksFile = "transfer-networks.json"
```

`transfer-networks.json`は以下の形式の配列です。1～32個の重複しないNIC・ポートを指定します。

```json
[
  {
    "interfaceId": "このCoreのLAN用Interface ID",
    "bindAddress": "192.168.1.10",
    "broadcastAddress": "192.168.1.255",
    "port": 47740
  }
]
```

通常はこの追加設定は不要です。このピアへのGUIコピー受付だけを無効にする場合は`[transferQueue] enabled = false`を指定します。

## FileTransfer (Browser)

`FileTransfer`内の`Browser ↔ Host`は、ブラウザーを開いている端末と選択したホストの間の転送です。クラスター画面と同じ左右ペイン、選択・移動・コピー・ドラッグの操作を使います。Terminalと両FileTransferの操作バー・パネル・文字サイズはDashboard／RemoteDesktopと共通の配色に合わせています。転送の詳しい説明は「転送の使い方」を開くと表示されます。

1. クラスターを自動または明示指定し、ホストを選択してください。ドライブ・フォルダーはシングルクリックで選択、ダブルクリックまたは Enter で開いてください。単一クリックでフォルダーへ移動しません。
2. 「ローカルフォルダーを選択」から、この端末のフォルダーを選び、ブラウザーの読取り・書込みを許可してください。利用できるのは選んだフォルダーとその配下だけです。フォルダーハンドルを永続保存せず、画面を離れると参照を破棄します。許可が拒否・撤回された場合は列挙・書込みを続けません。
3. 左右の項目を複数選択し、相手側へコピーボタンで転送してください。フォルダーや開いている場所へのドラッグも使えます。空フォルダーを含むフォルダーの双方向コピーに対応します。ローカルのパス欄は選択フォルダーからの相対パスで、`..` による外への移動を認めません。
4. 転送履歴へ進捗・完了・失敗／未確認・未実行を表示します。中止ボタンで残りの処理を止められます。転送先と選択項目は開始時に固定し、実行中は選び直せません。完了後に左右の一覧を再取得します。
5. フォルダーAPIが未対応、または許可しない場合も、左側の通常のファイル選択でアップロードできます。ホスト側のファイルの「ダウンロード」はブラウザー標準の保存を使います。

フォルダー選択には対応ブラウザーとsecure contextが必要です。許可は利用者が押した選択ボタンから要求し、画面を開いただけでは要求しません。[File System Access仕様](https://wicg.github.io/file-system-access/)に従い、ブラウザーが許可した範囲でのみ処理します。

端末との転送中は画面を開いたままにしてください。ブラウザーが所有するローカルフォルダーを使うため、クラスター転送のようなCoreService所有の永続・共有キューとは寿命が異なります。一回の選択・フォルダー列挙は最大4096項目、階層は32段、画面の転送履歴は直近128件です。

ホストへのフォルダーコピーは既存の段階保存へ格納し、全体の検証後に確定します。ホストから端末へのコピーはファイルごとにストリーム書込みを確定するため、中断したフォルダーには完了済みファイルや空の項目が残る場合があります。既存の同名項目を検出した場合は上書きせず停止します。ブラウザーAPIは他アプリケーションとの原子的な新規パス予約を提供しないため、同じ保存先を別アプリケーションで同時に変更する場合の完全な排他は保証しません。

書込み確定の結果が不明な場合は削除・自動再試行をせず、保存先の確認を促します。

ブラウザーからClientHostへは最大2MiBのバイナリ転送片を送ります。ClientHostは最大4要求のバッファーをプールし、対応するCoreServiceにはTCPで1MiBずつ中継します。旧CoreServiceやTCPの接続開始に失敗した場合は32KiBの従来管理経路を使います。ハッシュ計算はブラウザーで1MiBずつ行い、ファイル全体をメモリへ読みません。各転送片・最終内容とマニフェストを確認してから確定します。同名宛先は上書きせず、対象ピアの起動実体が変わると停止します。

確定応答が欠落した場合は、同じ永続操作の結果だけを期限内で照会します。確定要求を新しい操作として再送せず、それでも不明なら宛先の確認を促します。正常完了または中止では転送用の段階を破棄します。通信断で破棄できない場合や確定結果が不明な場合は、確認用の段階が残ることがあります。

## フォルダーの作成と削除

両画面の各ペインに「フォルダー作成」と「選択項目を削除」があります。フォルダーを開いてから名前を入力すると、その直下に新しいフォルダーを作成します。同名の項目は上書きせず、パス区切り・親移動・予約名は受け付けません。削除は複数選択に対応し、対象PC・フォルダーパス・項目一覧を確認してから実行します。**フォルダーは内容を含めて完全削除し、ゴミ箱には移動しません。** ドライブ一覧では作成・削除できません。

確認・操作中はホスト切替や転送操作を抑止し、終了後は対象フォルダーの一覧を更新します。複数項目の削除が途中で失敗・結果不明になった場合は残りを止め、確認できた削除件数と理由を表示します。結果不明の操作を自動再送しません。ホスト側は既存ファイルノードと同じOS権限・許可範囲・リンク拒否・競合管理を使います。Browser側の端末ファイルを作成・削除するには、書込みを許可したローカルフォルダーが必要です。通常のファイル選択だけでは端末上のファイルを変更しません。

## 終了済み処理のファイル予約

ノードが終了した際は、失敗・取消の場合も自身の予約を解放します。外部AIの結果不明とローカルのファイルアクセス完了は別々に保持し、ローカル終了を確認できた生成処理は予約を解放します。解放の応答を失った場合も、所有ピアが終了確認済みの記録だけを参照して回収します。元の実行や生成要求は再実行しません。

旧版で残った予約などは、元CoreService実体が既に終了しており、対象ファイルへのアクセス終了を運用者が確認できた場合に限り、所有ピアへ `POST /api/files/reservations/release` を送って明示解放できます。本文は `id`（元の予約ID）、`expectedOwnerInstanceId`（元のCoreService実体ID）、`fileAccessEndedConfirmed: true` です。

通常の管理操作と同じ接続先ヘッダーと一回分の `X-Contents-Request` を使用します。元実体が現在の実体と同じ、所有者が異なる、復旧記録がない場合は解放しません。元の結果不明を成功へ書き換えず、保持中の別処理の予約や実ファイルの内容にも触れません。

## 参照照会と段階保存

転送能力のUDP照会と、従来のUDP経路による読取り専用の参照は、応答の欠測に限って同じ対象実体へ最大3回照会します。相手が返した確定失敗を上書きせず、ファイル確定の副作用を新規操作として再実行しません。TCPで本文を送受信し始めた後の切断は、このUDP照会の再試行へ置き換えません。

同じファイルの各転送片で段階マニフェストを繰り返し保存せず、内容定義が増えた時に保存します。既に書いた範囲へ重なる転送片は、その既存部分が一致することを確認してから未保存の末尾だけを書きます。内容が違う重複を上書きせず、宛先確定前の全内容・マニフェストの検証も維持します。
