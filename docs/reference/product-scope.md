## 1. 目的

Clutch-CS は、複数の PC を連携させる通信・運用基盤です。機器や外部システムから受け取った情報を変換・判定し、必要な PC でアプリケーションの起動、ファイル操作、通信などを実行します。利用者は、ノードを接続してこれらの処理をワークフローとして組み立てます。

接続先や処理内容を設定で変更できるようにし、アプリケーションごとに通信や監視の仕組みを作り直す負担を減らします。新しい機能は、既存のノードと組み合わせて使える形で追加します。

CoreService は各 PC に常駐して処理を実行します。管理画面を提供する ClientHost とは別の実行ファイルとし、画面を閉じた後も処理を続けます。クラスター内で動く CoreService の一つの実体を「ピア（Peer）」と呼びます。ClientHost はクラスターの状態を観測し、管理要求を送る役割です。

## 2. 利用者と管理範囲

| 担当 | 主な作業 |
| --- | --- |
| 開発・設定担当 | 接続先、ワークフロー、監視、復旧、配布を設定・検証する |
| アプリケーション担当 | 必要な入力・出力形式と、アプリケーションの動作を決める |
| 外部システム・機器担当 | 接続仕様、正常な応答、障害時の対応を確認する |
| 運用担当 | 日常の操作と状態確認を行い、復旧できない場合は対象・影響・ログを開発・設定担当へ伝える |

プロセスやファイルを管理する PC と、通信先としてのみ利用する PC は、導入時に区別します。操作できる範囲は、対象 PC の OS アクセス権と機能ごとの設定に従います。

Clutch-CS には利用者アカウントや役割別の権限管理はありません。アクセスできる端末の制限は、OS とネットワークの設定で行います。画面上の端末名や表示名は、共同作業中の操作者を見分けるための情報です。

## 3. 主な利用場面

### 外部信号を複数の PC へつなぐ

受信するピアとネットワークインターフェースを選び、受信データの抽出、変換、条件分岐、状態保持、送信を組み合わせます。同じワークフローの中で、異なる PC に処理を割り当てられるようにします。

各処理の結果は、成功・失敗・未実行・結果不明・取消を区別します。入力が揃わない処理は開始せず、失敗に依存しない経路は続行します。再試行、代替処理、実行前の状態に戻す処理は、利用者が設定した方針に従います。

### アプリケーションを起動・監視する

OS 起動時に CoreService を開始し、登録したアプリケーションをワークフローから起動できます。`service.started` を使うと、ピアが通常の処理に参加した後、そのピア自身を対象に起動時の処理を実行できます。ノードの表示位置の変更や管理役の交代だけで、起動済みの処理を繰り返すことはありません。

アプリケーションの準備完了を待つ構成と、起動後すぐに次の処理へ進む構成を選べます。予期しない終了では、指定した条件・回数・時間の範囲で再起動します。「監視のみ」のアプリケーションは起動・停止の対象にしません。

ファイルの変更、ログ、CPU・GPU・メモリの使用状況も処理のきっかけにできます。警告を送るワークフローとは別に、障害調査に使うリソース履歴を記録します。

### 複数人で設定を編集する

接続中のクライアント間で、定義、配置、選択状態、操作者、未保存の変更の有無を共有します。同じ設定を同時に変更した場合は、現在値と変更案を比較し、採用する内容を選べるようにします。切断中の編集は保持し、再接続時に変更内容を照合します。

画面では「保存済み」「共有済み」「現在有効」を区別します。既定では、保存・共有した設定を次に開始する処理から使います。開始済みの処理は、その開始時に決まった設定を使い続けます。

変更の種類によっては、明示的な反映操作や影響確認を必要にできます。保存時の自動スナップショットだけが失敗した場合は、設定本体の保存結果を保持し、新しい設定の自動反映を保留します。

保存できない場合の動作は、保存先の用途ごとに設定します。未保存の候補を明示的に使う場合も、現在動作中の版と、再起動後に復元できる版を画面で確認できるようにします。

### 以前の設定や状態へ戻す

設定と実行時の状態は、それぞれスナップショットに保存します。ワークフロー全体のほか、ノード、サブグラフ、ホスト、ホストグループを指定して復元できるようにします。

復元対象の未保存編集を保存または取り消し、対象範囲を確定してから復元します。復元中はその範囲の編集を保護し、対象外の設定や下書きは保持します。失敗した場合は、復元前の状態へ戻す処理の結果を示し、戻せなかった箇所を確認できるようにします。外部への送信や機器の動作は、設定の復元では取り消せません。

### 一部の PC が停止した場合も運用を続ける

ピアを自動発見し、優先順位に従って管理役のコーディネーターを選びます。コーディネーターは実行先を指定しない処理の既定の担当です。

各ノードでは、PC の一覧や CPU・RAM・GPU・VRAM の負荷をもとに実行候補を選べます。候補のうち最優先の 1 台で実行するか、候補の全 PC で実行するかを指定します。ファイル、プロセス、NIC などを使う場合は、その処理に必要な環境を持つ PC を指定できます。開始済みの処理の担当 PC は、負荷の変化だけでは変更しません。

停止・分断時は、残ったピアが 1 台の場合と複数台の場合で、停止・続行の方針を分けます。失われた PC に依存しない処理は続けられるようにし、一時停止や強制続行も明示的に操作できるようにします。

再参加するピアは、必要な設定と状態の同期を終えてから通常の処理に戻ります。共有設定に競合がある場合は、その内容を確認して解消します。結果が不明な操作は、元の操作 ID で結果を確認できるようにします。

### 導入・更新・修復する

セットアップでは、必要な環境の確認、ファイルの配置、自動起動の登録、クラスターの選択、起動・参加確認までを一続きに行います。Windows では Install / Update / Repair / Uninstall を対話形式で操作できるようにします。

更新では、選択したクラスターやピアを順に更新します。部分的に失敗した場合の続行・旧版への復帰と、復帰にも失敗した場合の対応を事前に指定できるようにします。稼働中の更新は明示的に許可した場合に行い、残ったピアで必要な処理を続けられることを確認します。

## 4. 機能の範囲

| 分野 | 主な機能 |
| --- | --- |
| ワークフロー | ノードと入出力の接続、条件分岐、フック、状態保持、重複判定、配列の逐次・並列処理、YAML／JSON 定義 |
| 通信 | HTTP REST／GraphQL、OSC UDP／TCP、Art-Net、UDP／TCP、WebSocket、通信に使う NIC とピアの指定 |
| データ | Binary／JSON／TOML／YAML／CSV／Text の変換・抽出、型を指定した値の作成、四則演算、比較、論理・ビット演算、集合の結合・グループ化・展開・分割 |
| ファイル | ローカル・ピア間の読み取り、作成、更新、追記、コピー、移動、削除、ディレクトリ操作、変更監視 |
| プロセス・時間・監視 | 起動・停止・監視・復旧、日時・間隔・曜日・例外日の指定、リソース監視 |
| DB・スクリプト | SQLite／PostgreSQL／Redis への接続、C#／Python／JavaScript の実行と依存パッケージの管理 |
| AI・メディア | テキスト・音声・動画・画像の生成、処理先の選択、内容分類、音声・動画・画像の変換 |
| 運用 | 状態共有、分散実行、停止・分断時の続行、再参加、共同編集、永続保存、スナップショット、導入・更新・修復・削除 |
| 管理・調査 | Dashboard、WorkflowEditor、LogViewer、RemoteDesktop、Terminal、FileTransfer、HostManager、SignalScope、CLI |

標準ノードの設定だけで処理を組み立てられるようにします。コードを記述する処理は、必要なワークフローに追加して使います。利用できる接続先、形式、上限、OS は、各機能の資料に記載します。

管理画面はダークテーマを共通とし、英語・日本語で操作できるようにします。ヘッダーの既定表示は `Clutch-CS`／`WebUI` とし、設定で変更できます。利用者が入力した名前・値・ログ本文・識別子は翻訳しません。

ノードの追加・配線・値の変更・取り消しを短い操作で行えるようにします。設定した選択肢が使えなくなった場合は、保存値を残して修正箇所を示します。既知の型が合わない接続を防ぎ、型を特定できない場合は未確定であることを表示します。

保存されたワークフローが要求するノードの動作バージョンを確認し、互換性がない場合は、開始・復元の前に対象を示します。詳しい動作は[要件定義書](requirements.md)にまとめています。

## 5. 品質と確認方法

連続運転を想定し、通常想定される障害には予防、自動復旧、設定に従った機能の制限で対応します。ログの出力先が使えなくなった場合も、本来の処理は可能な範囲で続行します。保存成功を応答した定義・設定・スナップショットは、1 つのピアの喪失で失わないことを求めます。

一件の入力から完了・停止までを、複数のピアにまたがって追跡できるようにします。API キーなどの秘密値はログやエラーへ出力せず、保存後の通常画面にも再表示しません。個人情報を扱う箇所は明示し、通常のログでは伏字にします。

Windows x64 を主な検証環境とします。Linux x64、Linux Arm、macOS arm64 は、対象機能ごとの対応状況と検証結果を資料に記載します。外部サービスや機器を使う場合は、実際の接続先で正常時・障害時の動作を確認します。

設計上の目標は、年間可用性 99.9%、実行担当の喪失後 5 秒以内の利用回復、必要条件が揃ってから 60 秒以内の再参加です。達成状況は、構成・負荷・測定条件と合わせて評価します。試験の方法は[性能試験](../development/performance-tests.md)を参照してください。
