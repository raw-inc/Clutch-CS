# 手動復旧の確認項目と手順

[ドキュメント一覧](../README.md) · [運用時の動作](cluster-operations.md) · [導入と復旧](../guides/manual-install.md) · [更新・旧版復帰](update-process.md)

同期や更新が進まない場合、または結果不明の処理がファイルなどを使用中のままになっている場合の復旧手順です。対象の状態と元の操作記録を確認し、必要なデータを退避してから操作してください。復旧後は、残っているエラーと原因への対応も確認してください。

## 診断コードから確認する

同じクラスターでも、各ピアへ直接照会して比較してください。ClientHostの発見一覧だけで判断せず、`/health` の版・実体・Ready・maintenance、`/api/status` の同期理由・待受・実行中処理・待受ノードキューを確認してください。APIには対象の `X-Contents-Cluster` と `X-Contents-Peer` を付けます。日時はoffsetを残し、表示用タイムゾーンと混同しません。

| 観測 | 意味と次の確認 |
| --- | --- |
| TCP接続は成功するが同期が進まない | 接続成功は、そのポートへの到達確認だけです。更新用TCPと同期用TCPは用途が異なり、固定スナップショットの作成・転送・ハッシュ検証・双方向取込みの完了は別に確認してください。UDPの生存通知・管理応答も確認してください。 |
| `Sync.ResponseUnconfirmed` | 同期の応答を確認できていません。ネットワーク断だけでなく、書出し・照合・保存待ちの遅延も切り分けます。Readyでも別ピアとの未確認が残る場合があります。 |
| `Ready · Background Sync` | 現在の稼働基準は確認済みで、過去本文を補完しています。`historySynchronization.pending/total/problem` を同じ実体から連続して確認してください。割合は件数であり残り時間ではありません。過去本文の補完待ちだけを理由に再起動しません。 |
| `Persistence.HistoryPending` | 元の操作・保存版は存在しますが、本文をまだ取得していません。未実行ではないため、新しい操作IDで再送しません。取得元のReady・元本文の保持・背景の問題コードを確認してください。 |
| `Sync.HistoryConflict` / `Sync.SnapshotChanged` が少数の履歴で反復 | 未取得行のscope・key・取得元・本文ハッシュと、ローカル版の因果情報を照合してください。途中版とその完了版の組を、本物の並行変更と区別します。手動修復が必要な場合は両側の元レコードを保全し、同一要求・後継関係・書込み予約なしを確認した限定スナップショットを既存の取込み処理へ渡します。未取得台帳だけの削除、時刻順の上書き、更新操作の再実行では解消しません。 |
| `Sync.ExportCapacity` | 同期書出しの同時実行枠を確保できません。ディスク容量不足とは別です。進行中・期限切れの同期と、CPU・メモリ・ディスクI/Oを確認してください。 |
| `Sync.Conflict` / `Persistence.VersionConflict` | 競合一覧で対象のscope・key・候補版を確認してください。後者には保存予約との衝突も含まれます。ワークフロー本体の競合か、内部割当などの競合かを分けます。 |
| Fleet Updateが`Deferred` | 開始条件が成立していません。未着手かどうかを対象のattempt履歴で確認してください。全体のFailed表示だけで更新済みピアを再更新しません。 |
| `update.rollbackHealthUnconfirmed` | 旧版へ復元した後の稼働確認が未確定です。実配置・実プロセス・Readyを確認してから、元の更新操作の復帰結果を確定します。 |
| maintenanceの理由が`update.rollbackFailed` | この文字列は通常の更新保留でも使用します。理由だけでロールバック失敗と判定せず、元Updaterのphase・outcome・reasonと実配置を確認してください。 |
| `Cluster.ResponseUnconfirmed` | 外部APIの失敗と断定しません。ノード結果のmessage・出力・ファイル予約を確認してください。AIノードでも、API呼出し前のクラスター内ファイル予約で発生する場合があります。 |
| `Replication.RequiredAcknowledgementMissing` | 共有保存の固定参加者から必要な確認が揃っていません。ノードの実行開始有無、予約ID、各参加者の元操作の準備・確定・取消記録を照合してください。生成APIのレート制限や認証失敗とは、この理由だけでは判断できません。 |
| `ai.networkBindingUnavailable` | 指定NICまたはIPv4を実行先で利用できず、生成APIを送信していません。VPN再接続やDHCP変更後は、PCごとの接続設定と現在のアドレスを照合してください。以前の `ai.incomplete` では、実行結果のNotExecutedとネットワーク設定も確認してください。 |
| `File.Overlap` | 同じホストの同じファイル、または包含するパスが予約中です。実行中の書込みか、以前の結果不明による残存予約かを確認してください。OSのファイルロックや生成APIの認証エラーとは区別します。 |
| `File.ReservationCompatibilityUnconfirmed` | 停止前に旧形式への互換保存を確認できませんでした。保持予約は消しません。旧版へ強制復帰する前に、新版で予約台帳を確認してください。新版ピアが残るクラスターでは、旧コーディネーターの再参加を確認して、保持予約ごと旧形式へ戻します。単独CoreServiceで異常終了後に旧版へ戻す場合は、新版で一度復旧・通常停止してから行います。 |
| 高並列時の接続失敗・HTTP結果不明 | 接続先の失敗だけでなく、実行ホストのTCP接続数・TIME_WAIT・OSイベントも確認してください。WindowsのTcpip 4227/4231は送信ポート不足の手掛かりです。CoreService内RPCは継続接続を再利用し、再利用できない接続の結果不明から副作用を自動再送しません。 |

通常の同期再試行には間隔と期限があります。[同期の上限と再試行](history-storage.md#再参加同期の上限と再試行)を確認し、短い間隔でサービス再起動・保存・自動実行のOFF→ONを繰り返しません。DB容量だけで原因を決めず、変更頻度、保存媒体、履歴・操作記録の内訳、同期段階も照合してください。

## 影響を止めて証拠を保全する

1. 復旧対象、停止してよい入力、残す稼働系を決めてください。更新の最大並列数は運用計画に従います。同じクラスターの復旧は一台ずつ進め、各操作の結果を確認してから次の対象へ移ります。残るReadyが通常更新の参加条件を満たすことを確認してください。
2. 自動入力が状態変更を増やしている場合は、必要な待受ノードだけを一時停止します。停止前にワークフロー ID、ノードID、待受ノード ID、ピア実体、保存版・有効版、自動実行設定、待受状態を記録してください。キューと実行中処理を調べ、受信停止と開始済み処理の取消を分けます。ワークフローの自動実行ON表示だけでは実際の待受を確認できません。
3. 更新・保存・実行の要求は、送信前に操作IDと要求を保存します。応答がUnknownになったら、元の更新・保存・実行結果を照会します。読取り専用照会はやり直せますが、元の副作用が不明なまま新しいIDで再送しません。
4. 影響を受けない管理経路を確保します。同じホストに複数クラスターがある場合、稼働中の管理クラスターのTerminalから、問題のクラスターのWindowsサービスだけを操作できます。対象サービス名、実行ファイル、起動設定、PID、開始日時・実体IDを照合してください。
5. オフライン修復の前に対象サービスを正常停止し、サービス状態がStoppedになった後も、元のPIDの実終了を待ちます。SCMの状態遷移だけではプロセスの終了を保証しません。バックアップ前に別プロセスが同じデータを開いていないことも確認してください。
6. 停止した保存領域を、修復先とは別の場所へ退避し、サイズとSHA-256を記録してください。SQLiteは残存するWAL・SHMも含めて一貫した組として保全し、用途別に別媒体を使用している場合はその設定・保存先・履歴も保全してください。コピー完了とハッシュ一致を確認してから修復します。

稼働中DBのファイルコピーだけを一貫したバックアップとは扱いません。`state.db`を消して同期し直す、別ピアのDB全体を上書きする、未完了の操作・予約・競合を直接SQLで消す方法は使用しないでください。ピア固有の状態や再実行防止の記録を失うためです。

Terminalで保守スクリプトを実行する前に、対象端末のPowerShellの版と実行ファイルを確認してください。Windows PowerShell 5.1だけの端末へ、PowerShell 7の固定パスや専用パラメーターを前提としたスクリプトを送らないでください。呼出元が応答を失っても処理結果を調べられるよう、対象端末にも開始意図と結果を保存します。

### メモリ増加と同期の往復が同時に起きる場合

実行中ノードとキューが空になった後も、同期の書出し・取込みで大量の割当が続く場合があります。private bytesの上下だけでリークと断定せず、短時間のGC・CPUプロファイルと読取り／書込み量を合わせ、全履歴の復元、差分切出し、復旧ジャーナルの再復元を区別します。`Sync.ExportCapacity` の枠数を増やす前に、既存の一回が完了できているかを確認してください。

複数のワークフローを同時に実行すると、保存準備と差分の取込みが重なる場合があります。再現試験では同時実行数、保存先の重複、保持する履歴量を揃え、送信側と受信側のメモリ使用量・取込み時間を確認してください。ファイル保存の `Cluster.ResponseUnconfirmed` も、外部HTTP応答の取得とクラスター内保存確認を分けて確認してください。

共有履歴が大きい場合は、内容を画面へ丸ごと出さず、種類・scopeごとの件数と保存バイト数を集計します。生成ファイルそのものが大きいことと、ファイル予約台帳の各版が履歴へ繰り返し保存されていることは別です。予約台帳に終了未確認の古い所有実体が残ると、その後の取得・解放でも台帳全体の履歴が増えます。元実行結果、取得・解放の確認、所有プロセスの実終了を調べ、下記の明示解放手順で扱います。時間経過や現在のピア一覧だけを根拠に予約を削除しません。

予約台帳の新形式では `file:reservations/active` は全体ガード、`file:reservations:slots` が現在の予約です。ガードにID一覧がないことを、予約が存在しない根拠にしないでください。解放済みの空きスロットは再利用するため残ります。旧版の一覧形式も保持・移行対象なので、復旧では保存形式を確認してから現役予約を数えます。

入力停止後に自然に同期が完了する場合は、その状態を保って修正版を検証します。利用者が自動実行をOFFにしたワークフローを、更新・復旧の一環で自動的にONへ戻しません。性能比較用に稼働中DBから行を分けて読み出したデータは、負荷を再現する隔離資料であり、復元に使える一貫したバックアップとは扱いません。

### 一部の PC で稼働を継続する場合

クラスター全体の復旧を待てない場合は、継続する処理、実行先、必要な共有操作を先に確認してください。参加状態が Ready と Syncing を繰り返す場合は、`ReadySince`、待受の開始時刻、処理の実行結果を時系列で照合してください。一度 Ready になったことだけで、継続稼働できるとは判断しません。

縮退運転に移る場合は、停止するサービスと残すサービスを決め、運用者の判断のもとで一台ずつ操作します。サービス名、実行ファイル、起動設定、PID を照合し、元プロセスの終了と残す処理の継続を確認してください。

停止した PC で実行するノードは利用できません。また、参加者全員の確認を必要とする共有操作は完了しない場合があります。継続できた処理と、同期の状態・残る機能制限を分けて記録してください。

再参加の前に、保全したデータを使って取込みと通常処理への影響を確認してください。再参加は一台ずつ進め、同期と処理の継続を確認してから次へ移ります。

## 停止中の共有状態を合わせる

通常の同期・競合解消が進まない場合に限り、保全した状態と修復対象を照合して行います。その版に対応するリポジトリ API を使い、修復する共有範囲を限定します。

### 相手の共有スナップショットを取り込む場合

信頼する相手から `IDurableRepository.ExportAsync` で共有スナップショットを取得し、転送前後の全体ハッシュを照合してください。停止した対象では `RepositoryFactory` から用途別保存構成を開き、`ImportAsync` で因果関係・操作結果を含めて統合します。相手のDB全体をコピーしてピアローカル状態を置換する操作ではありません。

取込み前の共有状態も保存します。`ImportAsync` が競合なしを返したこと、未完了予約の扱い、ワークフローの保存版・有効版、対象外のデータを確認してからサービスを起動します。現在値だけを一致させて、操作結果や未完了予約を破棄しません。

### 内部の待受PC割当が競合している場合

`execution:source-pcs:<WF ID>` は待受担当の共有記録です。ワークフロー本体の `workflows` と区別します。`/api/conflicts` と `/api/conflicts/detail` で候補を保存し、同じワークフロー・ノード・選択条件版（ChoiceRevision）・対象PC・対象実体を指すか確認してください。候補に記録された古いReady状態だけで、現在の担当が稼働可能とは判断しません。

現行版では、確認可能な同一内容の分岐は共通の版へ統合し、解消済み版に包含される古い候補を除外します。待受PC割当は現在の有効ワークフローと稼働実体から導く内部状態なので、コーディネーターが全候補を指定した通常の共有保存で再選択します。異なるワークフロー定義・状態データ・利用者設定を自動で選ぶ機能ではありません。コーディネーターは、同じ確認条件の失敗を 1、2、4、最大 5 秒の間隔で再試行します。設定・担当プロセス・候補版が変わった場合は、直ちに再確認します。

通常は `/api/conflicts/resolve` で、照会した候補版集合と選択候補を指定します。相手ピアの候補集合が異なり `Persistence.VersionConflict` になる場合は、同じ要求を連打せず元結果と各ピアの候補を読み直します。

停止中のピアを個別修復する場合も、保全済みの候補集合と現在版が一致することを再確認し、`ApplyBatchAsync` / `ResolveConflictAsync` による明示解消で祖先関係を残します。選択条件や実行先が異なる候補を、日時が新しいという理由だけで採用しません。変更は確認済みのscope・keyだけとし、ワークフロー定義のハッシュを前後で照合してください。起動後は他ピアへの同期、競合件数、担当実体、実待受まで確認してください。

### 競合解消後も参加状態が戻らない場合

あるピアの競合一覧が空でも、別ピアには候補が残っている場合があります。各ピアへ直接照会し、実際に候補を保持している保存先を特定します。再起動中の割当と Ready 復帰後の割当が分岐している場合は、ワークフロー・ノード・ChoiceRevision・対象 PC・起動プロセスが同じか、保全した候補で確認してから解消してください。Readyという古い観測値だけを根拠に候補を選びません。

解消済みの共有状態を持つReadyのピアを確保した後も、他のピアがConflictのままの場合は、未解消候補が0件であり、明示離脱中ではないことを確認してください。内容の競合候補がなくなったピアは、識別子の衝突がなければ自動でSyncingへ戻り、実同期を再開します。取込み結果の通知より先に別の取込み・明示解消が確定した場合も、保存時点の古い判定でConflictへ巻き戻しません。候補の解消だけでReadyを強制指定せず、双方向の確認を待ちます。

この自動復帰に未対応の版で状態が残る場合は、対象ピアへ `POST /api/cluster/rejoin` を一度送り、元の要求を記録したうえで、Syncingから実同期を経てReadyへ戻ることを確認してください。原則として1 ピアずつ復帰を確認し、同期書出し枠が不足している間に再参加要求を繰り返しません。停止中の明示解消では、選択した値だけでなく両候補の因果情報も保持します。

保存済みの古い候補を再取込みして競合が復活しないこと、解消結果が相手へ伝播することを複製上で確認してから、同じ対象・期待版だけに適用します。

Readyへの復帰と `Sync.SourceInstanceUnavailable`、`Sync.ExportCapacity` などの診断解消は別に観測します。以前の実体に対する診断が残る場合も、稼働復旧だけで同期が完全に正常化したとは報告しません。

### 全台再起動後に保存準備または保存結果の不一致が残る場合

共有保存の準備受理後、同期で現在値が先へ進むことがあります。保存処理は、受理済みの変更と因果関係を照合し、後続の現在値を戻さずに元の結果を確認します。異なる並行変更が残る場合は `Unknown / Persistence.CommitConflict` とし、候補を保持します。現在値のCAS不一致だけから、他ピアで完了済みかもしれない元保存を確定失敗へ変えません。

新しい操作はコミット送信前に判断を永続化し、SQLite／JSONの同一保存先では局所コミットと同じ取引で確定します。再起動後は一巡一件ずつ元判断を確認し、コミット決定済みなら元保存の完了、コミット前で実行中でないことを確認できれば、保存処理が取消と予約解放を進めます。一巡の遠隔確認は5秒を上限とし、通信待ちの間は通常の共有保存の排他を保持しません。全体の成功は元参加者すべての同じ結果を照合してから確定します。

これは保存プロトコルの回復であり、外部API・ファイル生成・ワークフローの再実行ではありません。

判断を記録していない旧操作は、他ピアの同じ操作ID・指紋の成功など、保存済みの根拠がある場合だけ自動回復が進みます。期限経過、相手の不在、TCP到達だけでは取消を判断しません。確認不能が5秒以上続くと `Replication.PreparedDecisionUnconfirmed`、元参加者の確認が残る場合は `Replication.RequiredAcknowledgementMissing` を同期診断へ表示します。

通常の短い準備中は同期本文を作り直さず、有限間隔で受付可能になるのを待ちます。

旧版が残した空の `Failed / Persistence.VersionConflict` は、同じ操作ID・指紋の成功と、競合のない現在値までの祖先関係を証明できたときだけ補完します。元結果の種類・理由と双方のハッシュはローカル操作履歴へ残します。明示取消・内容不一致・期限切れは補完しません。手動復旧でもこの区別を維持し、根拠のない結果の上書きや予約の一括削除を行いません。

## 更新途中の旧版復帰を確定する

対象の `job.json`、`journal.json`、インストール先マニフェスト、実際の稼働状態を保存します。旧Updaterがまだ動いている間は、手動で入替・復元・別の更新を重ねません。

元の結果が `Interrupted / Unknown / update.rollbackHealthUnconfirmed` の場合は、旧版のReadyと新しい実体を確認してから、installation外のUpdaterへ `--confirm-restoration` を指定します。

確認JSONの項目と実行条件は[更新・旧版復帰](update-process.md)を参照してください。この操作では、Updater が元ジョブ、互換性のある旧版の全ファイル、起動プロセスと稼働状態を照合します。ファイルの入れ替えや再起動は行いません。終了コード1と `update.failedOldReleaseRestored` は「更新は失敗したが旧版復帰は確定した」結果です。新バージョンへの更新成功へ読み替えません。

その後に元の更新保留の所有者を確認して解除し、必要なら新しい更新計画を作ります。旧操作と新操作の関係を記録してください。元のFleet Updateに失敗・Deferredが残る場合も、別操作で更新した対象の成功結果を対応付け、全体表示だけで判断しません。

Fleetのプレビューは発見中の全対象を固定する契約なので、その `targets` 配列を手作業で一部に減らして再送しません。未完了分だけを更新する場合は、元操作が未着手または旧版復帰確定であることを確認し、対応するクラスターの `POST /api/updates/start` で対象 `peerIds` を明示します。

配布元ピアが実際に読める検証済みのペイロードとマニフェストを指定し、残るReadyの過半数、同一ホスト・クラスターの更新排他、元のmaintenance解除を確認してください。同じ共有クラスターの復旧対象は1 ピアずつ更新します。

開始後に並列数を減らす場合も、保存済みの要求を直接書き換えません。必要なら更新を配信しているClientHostだけを停止して新規配信を止め、開始済みの独立Updaterは継続させます。同じClientHostの保存領域から元操作を復元・再照会し、開始済み全対象の結果、Ready復帰、maintenance解除を確認してから未着手分へ進みます。最大1へ変更する場合は対象を一つずつ明示し、その成功と復帰を確認してから次を開始します。

元のFleetに残る中断・Deferredと、継続操作の実際の成功結果を対応付けて記録してください。

受付時に `Client.RequestUnconfirmed` が返った場合も、元の操作IDを照会し、未登録と確認できるまで別要求へ切り替えません。入力検証で拒否された場合と、送信後の結果不明を区別します。

### 停止後のディレクトリ切替がアクセス拒否になった場合

`Interrupted / Unknown / update.operationUnconfirmed.IOException.80070005` となり、サービスが `Stopped`、元Updaterも終了している場合があります。旧版の `service` と新版の `candidate` が残っていても、切替が完了したとは限りません。その操作のバックアップ、各配置のマニフェスト、サービスの実行ファイルを照合してから復旧方法を選択してください。

`80070005` はアクセス拒否です。これだけで権限不足やウイルス対策ソフトなど、拒否元を断定しません。現行のディレクトリ切替は共有違反（32・33）だけを回数を制限して再試行し、このエラーは自動再開しません。手動切替で復旧できたことと、拒否の発生原因に恒久対策が入ったことを区別します。

1. 元のFleet操作、対象のattempt・操作ID、`job.json`、`journal.json`、Windowsサービス状態、UpdaterのPID・開始時刻・実行パスを保全してください。対象CoreServiceが応答しない場合は、同一ホストの別クラスターに属する稼働中CoreServiceのTerminalから確認できます。応答不能を理由に更新要求を別IDで再送しません。
2. 対象サービスが実際に停止し、その操作のUpdaterも終了していることを確認してください。PIDだけでなく実行パス・開始時刻・ジョブを照合してください。Updaterが継続中、サービスが停止途中、または別の更新が進行中なら手動での切替は行わないでください。
3. `job.json` のinstallation、candidate、backupを絶対パスへ解決し、対象クラスターの明示した更新root内であることを確認してください。各ディレクトリの有無、マニフェストの版、全掲載ファイルのサイズとSHA-256を照合して記録してください。ワークフロー・設定・DBは更新root外の既存データを維持します。

| 確認できた配置 | 復旧時の扱い |
| --- | --- |
| installationは旧版、candidateは新版、対象backupは未作成 | 両版の全ファイルが一致した場合に限り、旧版をその操作のbackupへ退避し、candidateをinstallationへ移動して対象サービスだけを起動します。各移動直前にも元と先を再確認してください。 |
| installationは新版、backupは旧版、candidateは存在しない | ファイル切替を繰り返さず、新版の実プロセスとReadyを確認してください。 |
| installationがない、版が想定外、ハッシュ不一致、backupとcandidateの関係が不明 | 自動継続せず実配置を調査します。検証済みの旧版へ戻す場合も、現在のDB形式と旧版の互換性を確認してください。 |

手動移動でも失敗した場合は、その時点のディレクトリ配置を保存します。旧版の退避後に新版の配置が失敗した場合、installationが存在せず、元のbackupが残っていることを再確認してから、その旧版を復元できます。存在するinstallationへの上書きや、未確認backupの削除は行いません。

起動後は、実サービスのPID・OS開始時刻と `/health` の実体が一致すること、新版のbuildVersion、Ready・participating、同期診断を確認してください。installationとbackupの全ファイルも再照合してください。Readyでも元の操作IDが `maintenance` に残ることがあるため、通常処理の復帰まで確認が必要です。

手動切替を実確認できた場合は、その保留の所有操作IDと現在実体を指定し、管理通信の `updates.local.release` で元の保留だけを解除します。これは公開HTTPの復旧APIではありません。解除後のhealth・待受を再照会し、保留が残る、または所有IDが違う場合は追加更新へ進みません。

`--confirm-restoration` は旧版の `update.rollbackHealthUnconfirmed` 専用なので、このエラーで新版を手動適用した結果の確定には流用しません。

元Updaterの `Interrupted / Unknown` やFleetの `Unconfirmed` は成功へ書き換えず、手動切替・ファイル照合・新実体・保留解除の証跡を別に保存します。未着手分は `Queued` のまま残ることもあるため、`Deferred` と合わせてattemptが空であることを確認し、残るReadyの過半数と同一ホスト・クラスターの排他を保って、対象を1 ピアずつ明示したクラスター更新で続行します。

元のFleet全体や更新済みピアは再実行しません。

最後に、各CoreServiceの版・Ready・保留解除・同期残件と、更新前後のワークフロー保存版・有効版・自動実行設定・待受を照合してください。Web クライアント更新を伴う場合は配信資材のハッシュと一時更新タスクの解放も確認してください。最終報告では自動更新の成功件数、手動復帰した対象、別操作で完了した未着手分を区別します。

## 結果不明のファイル予約を解放する

ファイル保存を伴うAI・メディア・ファイルノードでは、ノードの `fileReservation` 出力を確認してください。予約ID、所有ピア・実体、コーディネーター、範囲、取得・解放操作の結果を保全してください。`Cluster.ResponseUnconfirmed` が返っても、予約取得が後から成功している場合があります。元の予約操作を照会し、外部生成の再実行とは分けて扱います。

予約の取得・解放・確認は、通常の配送待ち期限を超えても、同じ要求IDと内容の実行記録を読み取り、進行中なら完了を待ちます。受付期限は処理完了の期限ではなく、進行中と確認できる操作を経過時間だけで打ち切りません。呼出元の取消、元の実体喪失、継続した照会不能は区別して終了します。処理の再送や別IDでの再取得は行わず、元の実体喪失、確定した失敗、照会不能を成功と扱いません。確認できない場合も元の予約情報を保持し、以下の解放判定へ渡します。

全対象ファイル操作の退避・補償・解放も同じ読取り専用の結果照会を使用します。

共有保存の準備応答を失った場合は、元の同じピア実体に残る準備指紋を読み取り、要求内容と一致する場合だけ準備済みとして進めてください。準備の再送・新規予約は行いません。未準備、中止済み、内容不一致、実体変更、照会不能は成功へ読み替えず、必要な参加者も減らしません。旧版がこの照会に未対応の場合も、確認できたことにはしません。

予約取得の応答が不明でも、ノード本体をまだ実行していない場合は、その事実を `fileExecutionStarted: false` として保存します。元の予約の確定を確認できた場合だけ解放し、未確認なら `File.ReservationConfirmationPending` を残します。所有ピアは10秒周期でも現役予約に対応する復旧記録を確認し、確定後に自動解放します。同じパスの次回競合を必要とせず、1巡は最大30秒で次回へ継続します。

過去の全復旧履歴を毎回読みません。元のノード結果を成功へ変えたり、生成を暗黙に再実行したりはしません。実アクセス終了を確認できない処理や、開始状況を記録していない旧履歴は、警告の文字列だけから未実行と推測しません。

全固定参加者に同じ予約操作の `Persistence.Aborted` が残り、有効予約にも当該ノード実行IDが存在しない場合は、その予約を追加で解放する必要はありません。準備指紋が空の取消記録は、準備が保存される前の取消を示します。他の参加者の一致する指紋、元の予約ID、未実行記録と合わせて判断し、指紋が空という理由だけで成功や安全な再実行を推測しません。

生成そのものがSucceededでも、`fileReservation.release` に解放のUnknownが付く場合があります。生成を再送せず、まず出力ファイルのサイズ・SHA-256と元の解放操作を照合してください。全固定参加者に同じ解放操作・内容指紋のSucceeded記録があり、有効予約から当該実行IDが消えていれば、実解放と応答確認の遅延を分けて記録してください。保全したUnknownの履歴を成功に書き換えたり、存在しない予約を強制解放したりしません。

生存通知が届いていても、管理要求やファイル予約の応答まで届いているとは限りません。通信量、断片の欠落、対象の処理待ちを調べ、元の操作結果を照会します。通信が回復した後も、結果不明の操作を別のIDで再送しません。

明示解放APIは `POST /api/files/reservations/release` です。記録を所有するピアを指定し、bodyに `id`（FileLease.Id）、`expectedOwnerInstanceId`（元の所有実体）、`fileAccessEndedConfirmed: true` を渡します。これは、元CoreServiceの停止などによりファイルアクセス終了を確認した後の復旧用です。通信から見えないだけで停止したと断定しません。

現行実装は同じ稼働実体に対するこの明示解放を拒否します。

実行中ノード・キューを確認し、必要なら対象CoreServiceだけを正常停止して元プロセスの終了を確認してください。再起動後は異なる実体であることを確認してから、保全した旧実体の予約を解放します。解放も結果不明なら返却された元の操作IDを照会します。解除しても元ワークフローのUnknownをSucceededに変更せず、失敗後の残り要素や外部APIを暗黙に再実行しません。

## RemoteDesktop・Terminal・SignalScopeの接続障害

接続が切れた場合は、対象の機能だけが終了したのか、CoreService 自体が停止したのかを確認してください。サービス状態、PID、実体ID、`/health` を照合し、補助プロセスやブラウザーの表示だけで判断しません。

接続単位の障害は `Session.Failed` に記録されます。セッション識別子、機能名、発生段階、例外型を確認してください。認証情報、シェル入力、キャプチャ本文は診断へ記録しません。通常の取消や、次のフレームを受信する前の正常切断は、途中で欠けたフレームやタイムアウトと区別します。

Terminal の表示接続が切れても、所有する PTY が動作している場合があります。再接続して元のセッションを確認し、新しいシェルから同じコマンドを実行し直さないでください。RemoteDesktop と SignalScope でも、残っている取得セッションと接続先を確認してから再接続します。

CoreService が停止している場合は、接続エラーに加えて起動・稼働基盤のログも確認してください。メモリ不足、アクセス違反などを、再接続だけで回復したものとして扱いません。再現試験では対象を隔離し、不正な接続の終了後も CoreService の稼働と他の接続が維持されることを確認してください。

## 復旧完了の確認

- 対象ごとの版、ピア ID、新しい実体、Ready、maintenance解除を確認してください。複数回の観測で実体とReadySinceが変わらず、SyncingとReadyを往復しないことを確認してください。Readyと同期診断の解消は別々に記録してください。
- ワークフローの保存版・有効版・有効無効・定義ハッシュを基準と照合してください。利用者が編集中に加えた変更は、緊急復旧で古い状態へ戻しません。
- 停止した待受ノードを元のノード単位で再開し、各待受が一つだけListeningであることを確認してください。開始要求が遅れている場合は元要求と状態を照会し、重複して開始しません。
- 待受ノード一覧に終了済みのFailed履歴が残っている場合は、現在の `sourceFailures` と分けて確認してください。同じワークフロー・ノード・ピア・設定版で、その失敗より後に開始したListeningが一つだけあることを照合し、過去の失敗を現在の待受停止と数えません。履歴自体は消しません。
- 未処理キュー、実行中ノード、待受ノード失敗、未解放予約を確認してください。デバッグ試験は対象と回数を決め、元の実行を追跡します。AI生成などの副作用を成功確認のために何度も再送しません。
- CoreServiceとは別に、ClientHostの実プロセス・版・配信中UI資材と、元Updaterの完了結果を確認してください。起動直後の確認が更新完了より先に走った場合は、元操作の結果を再照会してから検証をやり直し、別の更新を開始しません。更新用の一時Web クライアント、Terminal、一時タスクは、所有する更新が終了したことと識別子を照合して片付けます。

運用記録には、元の失敗結果、実施した復旧、バックアップとハッシュ、停止・再開した対象、最終状態、未解決の診断を残します。大量の業務データ・秘密値を文書へ複製しません。

## 障害別の確認例

次の表は、復旧時に確認する内容と作業の順序をまとめたものです。操作を始める前に、対象の状態と元の操作記録を照合してください。

| 状況 | 確認する内容 | 復旧の進め方 |
| --- | --- | --- |
| 同期が進まず、共有状態に競合が残る | 双方の版、競合候補、未完了操作、保全したデータ | 対象を停止・保全し、必要な共有範囲だけを取込みます。相手の DB 全体で置き換えません。 |
| 更新が中断し、新旧どちらの版が動いているか不明 | 元ジョブ、各配置のマニフェスト、ファイルのハッシュ、実プロセス | ファイルの配置を確定してから対象サービスを起動します。旧版への復帰と、新版への更新成功を区別します。 |
| ファイルを生成する処理が結果不明になった | 元の実行結果、生成済みファイル、予約の所有実体、取得・解放の記録 | 完了済みのファイルを保持し、元の操作を照会します。生成処理を確認目的で繰り返しません。 |
| 複数の処理が重なるとメモリ使用量や同期待ちが増える | 同時実行数、履歴量、メモリ・CPU・ディスクの使用量 | 必要な入力だけを停止し、条件を揃えた隔離環境で再現します。負荷を下げるために稼働中の履歴を直接削除しません。 |
| 一部の PC だけで処理を継続する必要がある | 残す処理と実行先、共有操作に必要な参加者、停止対象 | 縮退時の制限を確認して対象サービスだけを停止します。処理の継続と、クラスター全体の同期回復を別々に確認してください。 |

復旧結果には、実施した操作、確認できた状態、残っている制限を記録してください。処理の一部が動作したことを、クラスター全体の正常化や未確定操作の成功として報告しないでください。
