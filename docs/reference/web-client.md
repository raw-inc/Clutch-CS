## 試験的な機能

Dashboard の「設定・保守」から、試験的な機能をブラウザーごとに常時有効にできます。選択は同じWebUIの全画面に適用されます。初期値、保存範囲、URL指定との関係は[設定手順](../guides/web-client.md#試験的な機能を有効にする)を参照してください。

## 表示言語

GUI の既定表示は英語です。画面上部の言語メニュー（Language）から日本語へ切り替えられます。表示言語はこのブラウザーに保存し、ワークフロー名・設定値・ログ本文は変更しません。

## Dashboard

Dashboard は左端の **All clusters** で観測中のクラスターを集約し、**Selected cluster** タブで選択クラスターを確認できます。各ホストの CPU・RAM、GPU ごとの使用率と専用 VRAM の使用量・容量・割合、選択 NIC の OS 通信速度、ワークフローの完了頻度と直近ログを表示します。同じ PC を複数ピアとして観測しても PC 数を増やしません。

Windows の GPU は標準性能カウンターとアダプター情報で AMD／Intel／NVIDIA の対応アダプターを観測し、明示設定した `nvidia-smi` の温度・メモリも利用できます。共有 GPU メモリは専用 VRAM と分け、内蔵 GPU の専用領域は OS の予約メモリである場合があります。CPU 温度の取得先がない場合や初回・欠測・カウンターのリセット時は、0 で補いません。

概要はバックグラウンドの最新実測を読むため、画面更新で再採取や履歴全体の書込みを行いません。

PC healthの電源マークはReadyで発光し、Syncingは円形のアクセスランプ、それ以外は「?」を表示します。Readyの状態テキストはホバー／フォーカスで、それ以外は常時表示します。Ready／Syncingのボタンから **再起動／シャットダウン → 確認** でOSへ一度だけ要求します。応答前に切断した場合は結果不明として操作履歴から照会し、自動再送しません。メニューは外側・同じボタンのクリック、Escape、またはホバー離脱から10秒で閉じます。

OSの操作権限はCoreServiceの実行アカウントに必要です。

オフラインPCは灰色の電源マークと最終計測を保持し、**表示削除 → 確認** で一覧から取り除きます。表示履歴はClientHostのstate内の `dashboard-hosts.json` に保存し、画面再読込みやClientHost再起動でも維持します。これはクラスター・ピアの発見期限とは独立しています。ホスト IDでPCを識別し、保存するクラスター通信NIC（vNICを含む）をWoL用の物理NICとは推定しません。

オフラインPCのメニューから **Wake-on-LANを送信 → 確認** を実行できます。停止前に確認したMACを使い、稼働中のCoreServiceからMagic Packetを送信します。対象NICの選択と条件は[HostManagerのWake-on-LAN](pc-management.md#wake-on-lan)を参照してください。送信完了とPCの起動確認は区別して表示します。

**Peer list／ピア一覧** は接続先を選択せずに開けます。PC、クラスター、ピア、現在状態、実行中のバージョンを表示し、表示中は3秒ごとにClientHostの稼働確認キャッシュを読みます。**All clusters** も同じhealthを使用します。最大128ピアを一ページに表示し、続きを **Next peers** で確認できます。発見した実体と稼働確認が一致しない場合や取得失敗時は、古い版・Ready状態を流用せず未確認にします。

このタブはリソース履歴・ログ・実行一覧を追加取得しません。

CPU／RAMは数値の背景に直近5分の実測グラフを表示します。初回・再読込み時は履歴、以後は未受信点だけを配信し、画面側も同じ時間・件数制限で差分を統合します。health・status・最新計測は一つの参照要求にまとめます。使用率に応じて緑から黄・赤へ色が変わり、採取の間も時間軸が進みます。欠測区間は接続しません。

画面の取得周期とCoreServiceの既定採取周期は3秒で、CoreServiceの採取周期は `[resources].sampleIntervalMilliseconds` で変更できます。CPUのコア数・スレッド数・名称、RAMの使用量／総量をGiBで表示します。専用・共有GPUメモリは同じ形式で使用量／容量・割合を示します。

PC healthの概要は、上段を **CPU / MEM / IO**、下段を **GPU / VRAM / NW** とする2行×3列です。IOのメイン数値とグラフはホスト全体のRead＋Write、NWは物理NICのDown＋Upの合計です。同じ時点の両方向を加算し、どちらかが欠測なら合計も`—`とします。

IOはMiB/s（1 MiB = 1,048,576 bytes）、NWは各数値が1 Mbps以上ならMbps、未満ならKbps（1 Mbps = 1,000,000 bits/s、1 Kbps = 1,000 bits/s）で、小数点以下2桁を表示します。合計の下には`Read 0.00 MiB/s | Write 0.00 MiB/s`、`Down 0.00 Mbps | Up 0.00 Mbps`の形式で内訳を示し、狭い画面では内訳を折り返します。

同じPCの複数CoreServiceは合算せず、仮想NIC・VPNのカウンターも物理NICと二重計上しません。転送量グラフの縦軸は表示期間の実測最大値に合わせて自動調整し、合計数値にホバーすると範囲を確認できます。使用率や帯域飽和の割合ではありません。

転送速度はWindowsでは物理ディスクのPDH合計と、OSが`HardwareInterface`と判定したNICの64bitカウンターを使います。追加プロセス・ドライバーは不要です。Linuxはsysfsの物理NICと、デバイスに対応する全体ディスクをbest-effortで観測します。初回・取得不能・NIC構成変更・カウンターのリセットは`—`とし、確認済みの無通信時だけ0を表示します。未対応OSや旧CoreServiceにも推定値を表示しません。

履歴は既存の採取周期と件数・期間の制限を共有し、機器差分用には前回の一回分だけを保持します。

GPU／VRAMは、専用VRAMの総容量が最大のGPUを表示します。同容量の候補が複数ある場合は、有効なGPU使用率、次に有効な専用VRAM使用量のある候補を優先し、同条件なら識別子順で安定させます。ドライバー更新等で計測不能な識別子が残っても、同容量で計測できる候補を選べます。負荷の高低によって表示先を切り替えたり、同じ型番の複数GPUを名称だけで統合したりはしません。

## ヘッダー・faviconの差し替え

ヘッダーの既定表示は、上段が `Clutch-CS`、下段が `WebUI` です。表示名、ロゴ、ブラウザーのタブアイコン（favicon）は、以下の設定で変更できます。ブラウザーのタブ名は `Clutch-CS` です。

ClientHostの`--state`ディレクトリに`branding.json`を置き、ClientHostを再起動します。既定の保存先はWindowsでは`%LOCALAPPDATA%/ReArtWord/Contents/Client`です。

```json
{
  "contentsName": "My Installation",
  "subtitle": "Control console",
  "headerLogo": "branding/header.png",
  "contentsLogo": "branding/wordmark.png",
  "favicon": "branding/favicon.ico"
}
```

- `headerLogo`は左端のノード図形を置き換えます。
- `contentsName`は上段の文字列と画像の代替テキストを指定します。既定は `Clutch-CS`、1～80文字です。
- `subtitle`は下段の文字列を指定します。既定は `WebUI`、1～80文字です。既存設定で省略している場合も既定値を使います。
- `contentsLogo`を指定すると、上段の文字列の位置に画像を表示します。下段の `subtitle` は残ります。
- `favicon`はブラウザーのタブアイコンを指定します。省略時は`headerLogo`を使い、両方未設定なら同梱のノード図形を使います。小さい表示用に正方形のPNGまたはICOを指定できます。
- 画像はPNG、JPEG、WebP、GIF、ICOで各2MiB以下です。絶対パス、または`--state`ディレクトリからの相対パスを使用します。画像は起動時に読み込み、同じClientHostのすべての画面へ配信します。差し替え後はClientHostを再起動し、ブラウザーを再読み込みしてください。画像の内容に応じて配信URLが変わるため、同じファイル名でも新しい画像を取得します。
- オフラインで設定を取得できない場合は、同梱faviconを使用します。
- 各項目は省略できます。文字列だけ変える場合は`contentsName`だけを指定し、既定へ戻す場合は設定ファイルを削除して再起動します。

## ブラウザーからアプリとしてインストールする

Desktop PWAとして利用する場合は、EdgeまたはChromeでWeb クライアントのHTTPS URL（同じ端末では `http://localhost:5081` または `http://127.0.0.1:5081`）を開き、ブラウザーのアプリインストール操作を使用します。`Clutch-CS WebClient` が独立したウィンドウで起動し、通常の起動画面からDashboardへ進みます。

マニフェスト・アイコン・通信は同じClientHostから配信し、追加ポートは不要です。別のホスト名やポートは別のインストール先として扱います。

マニフェストの `id`・`scope`・`start_url` は `/` に固定します。画面資材の検証済みキャッシュにはマニフェストと192px／512pxのアプリアイコンも含めます。オフライン時は画面を再表示できますが、CoreServiceの操作・最新ログの取得・実行状態の確認には接続が必要です。編集中の画面を自動で新版へ切り替えず、更新時は他のタブとPWAウィンドウを閉じて既存の画面更新手順を使用します。インストール用アイコンは同梱の製品アイコンです。

## ブラウザーの操作記録

ブラウザーの操作記録は、操作 ID ごとに IndexedDB へ保存します。要求と応答、対象のクラスター・ピア、結果の確認先を記録し、切断後も元の操作を確認できるようにします。

操作を送る前に記録を保存できなかった場合は、その要求を送信しません。応答を受け取った後に結果を保存できなかった場合は、元の操作 ID で結果を照会してください。再実行の前に結果を確かめることで、同じ操作の重複を防ぎます。

## Dashboardの状態保持

全体更新の進行中はDashboardに対象と確認済み件数を表示し、WorkflowEditorやRemoteDesktopを含む全画面のフッターにも小さな進捗バーを表示します。別ClientHostから開始した更新も、共通のクラスターへ接続していれば表示されます。配布元のファイルや更新要求は転送せず、進捗要約を各クラスターの最大2つのReadyなCoreServiceへ通知します。通常画面から別ClientHostの更新を再開・再実行することはありません。

進捗の通知が30秒以上途切れた場合は確認不能となり、完了とは扱いません。通知が復旧すれば表示も復旧します。観測はメモリ上に最大32操作、完了済みは5分、未完了は1時間保持します。詳細な配布結果は更新を開始したClientHostに保存されます。変更のない配布マニフェストは画面の周期照会で繰り返し読み込みません。

ClientHostが画面と独立して約3秒ごとに実通信で観測し、各画面へ保持済みのスナップショットを配信します。リロード・タブ移動後も同じClientHostのグラフ履歴を利用できます。状態・版確認は元の受信時刻を保持し、15秒を超える過去値をReadyの証明へ流用しません。ピアの起動実体が変わると旧履歴を破棄します。

保持するリソース履歴は各ピア最大121点・6分間、活動履歴は最大2000件・60秒の完了要約、監視対象は最大256ピアです。稼働・計測は3秒周期で最大8ピア、ログ・実行履歴は独立した10秒周期で最大2ピアを同時照会し、各読取要求の期限は2秒です。遅い応答で稼働確認と履歴取得を一緒に待たせません。発見対象から外れた実体を削除します。キャッシュはメモリ上にあり、ClientHost再起動時は再採取します。ピア一覧と接続状態の取得では履歴・ログを送りません。

ワークフローの活動は、開始時刻によらず直近60秒に完了した実行を集計します。ClientHostはCoreに残っている完了要約をページ単位で取得し、再接続時も同じ範囲を取り直します。ノードの出力サイズは活動の取得件数に影響しません。取得が途中で止まった場合や上限を超えた場合は、一部の範囲であることを表示します。旧Coreでは通常履歴の先頭ページを使用します。Core側の保持上限を超えて失われた結果や、実行中の処理は集計に含みません。

Dashboardの計測照会はCoreServiceの最新標本からCPU・メモリ・GPU・選択NICなど概要に必要な項目だけを受け取り、追加採取や診断履歴の全件取得を行いません。初回・画面再読込み時に渡すグラフ履歴はClientHostが観測した範囲であり、ClientHost停止中の過去をCoreService履歴から補完しません。同期中や通信断で取得できない場合は確認不能として扱い、保持した計測値と稼働確認を区別します。

All clustersとピア listは一巡の照会対象を最大128実体に制限します。All clustersの履歴付き照会は1要求あたり最大4実体・同時3要求に分割し、履歴が蓄積しても一つの大きな本文の受信失敗を全体へ波及させません。ピア listは履歴を含まない軽量な一括照会です。状態・版は応答の実体IDと元の確認時刻を照合し、欠測や古い実体をReadyに置き換えません。

ClientHostの応答時刻と受信後の単調経過時間で鮮度を判定し、閲覧PCの時計差を稼働異常にしません。管理APIはブラウザー・中継で保存しない応答とし、画面資材のオフラインキャッシュからも除外します。

画面更新が反映されない場合は `/ui-update.html` を開き、編集内容を保存・エクスポートした後、同じサイトの他のタブ・PWAウィンドウを閉じて更新します。最新版の起動資材と各ファイルを版付きURLで取得し、ハッシュを検証してから切り替えます。接続設定や保存した定義、ログイン情報を消去する操作ではありません。`Offline ready` は現在の版のキャッシュが利用可能という意味であり、最新版であることの証明ではありません。

更新待ちは右下に `UI update available` と表示します。

DashboardトップのCPU欄は、コア／スレッド数を上、プロセッサ名を下へ表示します。コア／スレッド数は既存の本文色、プロセッサ名は既存の控えめな色を維持します。

## 共通の状態表示とライセンス

Dashboardの折りたたみ式状態表示は、Ready以外で自動展開し、Readyへ戻って0.25秒後から折りたたみます。ホバーとキーボードフォーカスでも展開します。ピア listは状態名を常時表示します。

フッターの「OSS License」から、Clutch-CS の依存ライブラリ、著作権、ライセンス本文を名前順で参照できます。選択式のライセンスには採用した条件を併記します。FFmpeg は別途用意した配布物の条件を確認してください。

Dashboard・ピア list・クラスター更新の日本語表示では、ピア状態のReadyを「正常」、Ready peersを「正常なピア」と表記します。ワークフローのプロセス準備完了とは区別します。
