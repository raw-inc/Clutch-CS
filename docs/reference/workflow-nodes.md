## プレビューノード

`Control` の「プレビュー」(`control.preview`) は入力を表示する終端ノードです。パススルー出力や共通の結果出力を持たず、手書き定義でも後続へ配線できません。ノード上とインスペクターに表示し、ノードの表示領域は拡縮できます。

- 文字列・数値・真偽値・null・配列・オブジェクトはテキストとして表示します。実行前に確定できる値は「静的プレビュー・未実行」、実行後の値にはピア・取得時刻・定義の版を表示します。複数ピアで実行した場合は表示するピアを選べます。
- ノード内の小さな「直近／履歴」ボタンで表示を切り替えます。履歴はCoreServiceが入力ごとに取得するため、画面の約3秒の照会間隔内に届いた値も残ります。同じ値が続いても別のインデックスを付け、「インデックス・時間・値」の表に新しい順で最大50件を表示します。インデックスは各ピアの一時保持期間内の連番で、PC名を添えて表示します。時間は入力を取得した時刻をDashboardの「設定・保守」→「表示設定」で選択したタイムゾーン（既定UTC）へ変換し、`HH:mm:ss.fff`で表示します。時間へのホバーで日付とUTCオフセット、インデックスへのホバーで版を確認できます。「すべてのPC」では複数ピアの履歴をまとめて最大50件に絞ります。
- 履歴も5分で失効するメモリ内の一時情報です。テキストは各行1,024文字まで、画像・音声・動画は形式とサイズだけを保持し、長文の省略と取得失敗を区別します。履歴表示中だけ必要なノードの履歴を取得し、媒体本体を自動取得・再生したり、ワークフロー定義を変更したりはしません。
- バイナリはPNG・JPEG・GIF・WebP・BMP・WAV・MP3・Ogg・FLAC・MP4・WebMの先頭情報から形式を判定します。必要ならインスペクターの「メディア形式」で指定します。画像・音声・動画は「最新のメディアを読み込む」から取得し、音声・動画はブラウザーの再生操作で開始します。ブラウザーが対応しないコーデックや破損したデータは理由を表示します。
- AI生成・メディア変換の生成物 `{ peerId, path, mediaType, sha256, ... }` も受け付けます。ファイル所有ピアを実行先にし、既存のファイルアクセス方針と生成時のハッシュを確認して取得します。URL文字列は文字列表示とし、勝手に外部サイトへ接続しません。
- テキストは最大16,384文字、メディアは1件16 MiBです。CoreServiceはノードごとの最新値を最大128件・本文合計64 MiBまで保持し、5分を過ぎた値は次の照会・更新で失効させます。永続保存やクラスター同期はしません。明示して接続した値は、そのクラスターへ接続できる編集クライアントで参照できます。
- 編集画面は開いているワークフローの先頭64プレビューノードを約3秒間隔で照会します。媒体本体は自動再取得せず、取得IDを固定して分割読取りします。更新・失効時に新旧データを混ぜません。読込済み媒体の取得時刻は別に表示し、閉じる・ノードを非表示にする・画面を離れる操作で再生とBlob URLを解放します。ブラウザー側の媒体保持も8件・64 MiBまでです。

## ProgressBar

「ProgressBar」は出力のない終端ノードです。`total` には総件数、`current` には現在数を入力してください。整数と小数は混在できます。Previewと同様にサイズを変更でき、バー・百分率・現在数/総数を表示します。総数ゼロは0%、現在数が総数を超えたときはバーを100%に留めて実際の数値を表示します。負数・非数値は不正入力として表示し、前回の正常値を今回の値として残しません。

「進捗の集約単位」は、既定の「WFの実行ごと」では同じノードのForEach／ParallelForEachや子発火からの更新を一つのバーへまとめます。同じワークフローを同時に複数回開始した場合は、それぞれを独立したバーとして縦に表示します。「反復の要素ごと」を選ぶと、要素とその子発火ごとに表示を分離します。数値は入力値をそのまま表示し、要素数を暗黙に加算しません。設定を省略した既存ワークフローは「WFの実行ごと」で動作します。

ワークフローの正常終了・異常終了・中断時には、その実行が所有するProgressを表示先のピアから回収します。要素別表示は、その要素の子処理まで終了してから回収します。Previewの履歴とは分けて扱い、完了したProgressの履歴は保持しません。切断などで終了通知を確認できない場合も、最終更新から5分の保持期限で回収します。WorkflowEditorとWFDashboardで同じ実行単位を表示し、複数ある場合は開始時刻と短い実行IDを併記します。

## WFDashboard

`/editor?experimental=true` でワークフロー追加の「新規」を右クリックすると、「新しいWorkflowを作成」「新しいWFDashboardを作成」を選べます。[試験的な機能の常時有効化](../guides/web-client.md#試験的な機能を有効にする)でも同じ操作を利用できます。WFDashboardは同じクラスター内の保存済みワークフロー・サブワークフローにあるPreview、Progress、Button、ToggleButton、値、同時実行制限を参照する操作画面です。

作成後にワークフローとWFDashboardの種類を相互変換することはできません。作成済みのWFDashboardは通常表示からも利用できます。

「参照を追加」で、ノードの論理名、種類名、ノードID、ワークフロー名を検索してカードを追加します。見出しには論理名を表示し、未設定なら種類名を使用します。同じ論理名を持つノードも個別に選択できます。参照先はワークフロー IDとノードID・種類で保持するため、改名しても追従し、削除や別種類への置換時は利用不能と表示します。サブワークフロー内の対応ノードも選択できます。

Button／ToggleButtonの操作は定義タブからの押下と同じ経路を使い、トグルの確定状態は同じ定義の配置からも参照されます。親ワークフローを一律に発火する操作ではありません。Preview／Progressの参照は定義単位で、親ワークフローの配置ごとの履歴を合算しません。WFDashboard自身は参照候補に含めません。

カードは配線や入出力端子を表示せず、次の内容に絞ります。

- Preview／Progressは元ノードの観測結果を表示します。Previewの履歴や媒体の明示取得も利用できます。
- 同時実行制限は、処理中・待機中の件数と、待機順・短い受付ID・実行元ピア・待機時間・残り時間を表示します。待機の取消や設定変更は行いません。
- Button／ToggleButtonは元ワークフローの該当ノードを操作します。設定済みの後続値や接続線は表示しません。保存版と有効版が一致しない場合や、操作先の状態を確認できない場合は押下を無効にします。
- 値は論理名と入力欄を表示します。一行の値はEnterまたは入力欄から離れる操作で確定し、複数行の値は入力欄から離れて確定します。Escapeは未確定の入力を取り消します。確定すると元ワークフローへ保存し、元ワークフローの反映方針に従って有効化します。型や接続は変更できず、入力開始後に元ワークフローが変更されていた場合も上書きせず拒否します。動的な値設定など、固定型として安全に編集できない値は元ワークフローで編集してください。

カード見出しのドラッグで表示順を変更し、上部の「保存」で配置を保存します。別カードの本文、カード間の余白、末尾の空白にもドロップでき、離した位置に挿入します。1列表示ではカードの上半分・下半分で前後を選べます。カードを取り除いても元ノードは削除しません。配置は最大128枚です。通常の表示更新では、元ワークフロー本文や画像・音声のバイナリを定期転送しません。

「コメントを追加」はWFDashboard自身のメモです。普段は文章として表示し、クリックして編集するときだけ入力欄へ切り替わります。Enterで改行、欄から離れると草稿へ確定、Escapeで取消します。「改行を追加」は、それ以降のカードを次の段へ送る配置用カードです。どちらも見出しをドラッグして並び替え、通常の「保存」で配置・本文を共有します。元ワークフローや実行値は変更せず、配置上限128枚にはコメント・改行も含みます。

新しいWFDashboardのタブは既定で左側に追加します。その後はワークフロー／SubWFと混在してドラッグで並べ替えられ、手動で変更した順序を優先して復元します。WFDashboard自体は実行グラフとして扱わず、自動実行や接続線を持ちません。

「参照を追加」の「Stateを追加」では、保存範囲とKeyを指定した表示カードを配置できます。ワークフロー内の値を扱う場合は「WF」、クラスターで共有する値を扱う場合は「Cluster State」を選択してください。元の状態データノードをカードへ複製する必要はありません。表示は初回の現在値と、その後に保存が確定した変更通知で更新し、状態データを定期取得しません。通信断では直近値と切断表示を併記し、再接続時に現在値を確認します。画面離脱・対象変更で購読を回収します。

表示値は読み取り専用です。Binaryは種類とバイト数、JSON・文字列は最大約4KiBの表示を転送し、省略時は明記します。存在しないKeyと、値として保存されたnullを区別します。未保存・未共有の編集候補を確定値へ読み替えません。

## 永続状態データと変更待ち受け

状態データの読取り・書込み・比較交換・削除・重複抑止では、保存範囲を選べます。

- **ワークフロー内で共有**: 同じワークフローの実行をまたいで保持し、クラスター内のピアへ複製します。
- **このPeer内**: ワークフローと実行ピアの組ごとに保持します。
- **クラスタ内の全WFで共有（Cluster State）**: 同じクラスター内の異なるワークフローから、同じKeyの値を参照します。別クラスターや同名のワークフローの状態データとは共有しません。

いずれも実行終了時には自動解放せず、CoreService再起動後も残る永続状態です。明示削除または状態の復元操作で変更します。履歴の圧縮・削除は、現在の状態データの値の自動削除を意味しません。クラスター共有の状態データは個々のワークフローの状態スナップショットには混ぜません。共有の比較更新や離脱中のローカル枝の扱いは既存状態データと同じです。

**State変更待ち受け**は範囲とKeyを固定して待ち受け、永続保存された値が変わるたびに、開始信号と`value`・`key`・`version`・`exists`を出力します。開始時の既存値、同じ値の再保存、比較に失敗した更新、準備のみの未確定更新では発火しません。削除は`exists=false`、保存済みnullは`exists=true`です。

変更時の値を一件ずつ保持するため、処理の遅い後続が現在の状態データを読み直して別の変更値と混ざることはありません。

待ち受けは実行PCを明示します。同じ共有Keyを複数PCで待ち受けた場合は、各待ち受けから発火します。クラスター共通のフックを一つだけ発火させたいときは、実行する PC を一つ選択してください。停止・取消時には購読を解放し、状態データ自体は削除しません。保存前の編集候補は発火対象にせず、共有状態への統合が確定した時点で通知します。

後続が遅い場合も保存を停止させないよう、待ち受けごとに未処理256件・概算8MiBの上限を設けています。超過を黙って省略せず、その待ち受けを失敗として終了します。WFDashboardへの通信待ちはカードごとの最新表示へ集約し、永続保存やクラスター複製を待たせません。ブラウザーとの通信には既存Webポート上のWebSocketを使用します。

## 信号監視と退避

**信号監視**（`control.signalWatchdog` / 信号 Watchdog）は、一定時間信号が来なかったときに退避経路を開始します。既定のタイムアウトは **5,000ms** で、正のミリ秒値を指定できます。ノードの自動開始を有効にすると、ワークフローの自動実行開始時から計時します。最初の生存信号を待ってから計時する方式ではありません。

メイン機の生存信号を受けるOSC／UDP等の「開始Signal」を、信号監視の **生存・再開Signal** へ接続します。**退避開始Signal** はバックアップ機から受信する待受ノードの開始口へ接続してください。バックアップ側待受ノードは、信号監視を経由せず自動開始する配線にしないでください。

- 生存信号を受け取るたびに期限を更新します。途絶えたら一度だけ退避開始信号を出し、途絶えたまま周期発火はしません。
- 同じ入力端子へ信号が戻ると、その退避回から開始した待ち受けだけを正常終了し、再び生存信号の監視に戻ります。次の欠落は別の退避回として扱います。
- すでに受け付けた一回で完了する処理は最後まで継続できます。復帰後に、その処理から新たな待ち受けを開始しようとしても開始しません。別の退避回や無関係な待ち受けは終了させません。
- ワークフローの無効化・監視の停止・取消時にも、所有する退避待ち受けを終了します。終了を確認できない場合は、正常復帰とせず結果不明を残します。

監視先は固定の1 ピア、またはコーディネーターを指定します。通常は監視されるメイン機とは別の PC を選択してください。再起動や監視担当の交代では計時を最初から始め、過去の退避信号を再実行しません。退避経路を実行するCoreServiceは本機能に対応した版へ揃えてください。

監視が保持するのは最新の到着時刻と現在の待ち受け範囲です。生存信号の本文を監視ノード内へ蓄積せず、終了確認の定期照会も操作履歴を書き込みません。通知を取りこぼした場合は背景照会で終了を確認し、他ワークフローの保存・自動開始を照会待ちで止めません。

## 同時実行制限

**同時実行制限**（`control.concurrencyLimit`）をOSC受信などの後に挟むと、重い後続へ進める到達数を制限できます。同じクラスター内の「同じWF ID・同じノードID」で枠を共有し、受信PCや後続の実行PCが異なる場合も合算します。別ワークフロー・別ノードの枠は独立します。

- **同時に処理するセッション数**：既定1、範囲1～1024。
- **待機期限**：既定30,000ms。0は無期限。担当で受け付けた順に空きを待ちます。
- **待機期限を超えた場合**：既定は「この実行を失敗終了」。「上限を超えて進行」も選べます。強制進行も処理中件数に含め、以後の通常待機はその分も空くまで進めません。担当との通信や枠の取得結果が未確認の場合は、強制進行の設定でも後続を開始しません。

任意の`value`を受け取り、そのまま後続へ渡します。`start`は枠を取得した後の開始信号です。Endを省略すると、開始済みの子発火も含めた後続全体が終了するまで枠を保持します。特定の区間だけを制限するには、`scope`を**同時実行制限 End**（`control.concurrencyLimit.end`）の`scope`へ直接接続し、区間の最後の値・完了信号もEndの入力へ接続します。Endより後の処理は枠を占有しません。

開始ノードの共通完了出力も、区間全体の終了後に供給します。

後続の開始信号が別経路から到着する配線も使用できます。データだけが先着した段階の起動待ちは失敗や完了通知にせず、信号が届いた実行が同じ要求のデータを引き継いで枠を取得します。すでに終了した別枝の処理は再実行せず、新たに起動する後続が終了するまで枠を保持します。

正常・異常・取消のいずれでも、開始済みの区間処理を回収してから枠を返します。通信断だけで他ピアの枠を空いたと推測せず、担当交代後も共有済みの占有を引き継ぎます。解放通知を確認できなかった場合は、次の待機時に元の実行が終了したこと、または元のプロセス実体が置き換わったことを確認して回収します。所有元を確認できない間は枠を維持します。

ForEach／ParallelForEach内に配置すると、各要素からの到達もそれぞれ一枠として扱います。区間は独立または完全な入れ子にし、継続待受ノードを区間内へ置かないでください。Progressの「反復の要素ごと」は親のForEachを引き継ぎ、制限区間だけを新たな反復とは扱いません。設定変更は開始済みの実行へ遡及しません。

ノード内には処理中・待機中の件数と待機一覧をコンパクトに表示します。WFDashboardの「参照を追加」から同じノードを配置すると、列を増やしたカードで確認できます。一覧は先頭50件までと全待機件数を表示し、接続状態を確認できない場合は未確認と明示します。入力値やバイナリを転送せず、待機一覧は担当のメモリで管理します。定期的な一覧取得のために履歴や占有状態を書き直しません。担当交代時は待機中の要求が結果不明で終了する場合があります。後続の副作用を暗黙には再実行しません。

## サブワークフローに分離

選択したノードを右クリックして「SubWorkflowに分離」を選択してください。親ワークフローの選択範囲を一つの配置ノードに置き換え、新しいサブワークフロー草稿を別タブへ追加します。子の左上に余白を設けて相対位置・内部配線・設定・サイズを保持します。

- 選択外から入る線と、未指定の必須入力・接続可能な必須設定を公開入力にします。外へ出る線と、未接続の公開可能な出力を公開出力にします。
- 公開名は「ノード名 - 引数名」です。同名は連番で区別します。型・分岐条件・抽出指定・複数の接続先を保持し、親の外部配線を自動再接続します。
- 子草稿を端末へ保存できたことを確認してから親を置き換えます。親の置換は一回のUndoで戻せます。作成した子草稿はUndo後もタブから開けます。
- 親を「保存・反映」すると、参照している新規サブワークフローを依存順に先に保存・有効化します。未指定の必須入力は配置側で指定してください。既存レシピの編集草稿はそのタブから明示的に保存します。
- 待受ノードも分離・再利用できます。ForEachのloop線と同時実行制限のscope線は、開始・終了を片方だけ選択して途中で切り離せません。編集が保護されている範囲や、メニューを開いた後に変わった文書には適用しません。

親ワークフローにあるサブワークフローをダブルクリックすると、**その配置の実効版**を読み取り専用で開きます。内部Preview／ProgressBar、個々のノードの処理中表示を確認でき、内側のサブワークフローも開けます。この画面から値や配線の変更はできません。レシピ定義の編集タブでは実行中表示や実行プレビューを表示しません。親ワークフローの処理中表示を有効にしている場合、内部のいずれかが処理中なら親側の配置ノードを発光させます。

## 生成レシピ

ForEach／ParallelForEachの要素出力をサブワークフローの公開入力へ接続すると、その配置の内部処理も各要素の反復範囲へ含めます。公開入力を直接参照していないC#スクリプトなども要素ごとに実行するため、反復させるだけの追加の開始線は不要です。同じ値が続く場合、レシピ・反復が入れ子の場合、同じレシピを複数配置した場合も、それぞれの反復と配置を区別します。

内部で明示した開始待ちや条件分岐は維持します。未選択の入力から内部処理を開始せず、空配列では実行しません。反復外の共有準備や、設定だけから決まる純粋な値を要素ごとに再実行する変更ではありません。候補からの抽選にはRandomPickノードを使用できます。各回は独立した抽選なので、同じ候補が続くこともあります。

Dataの「配列・辞書の要素を取得（Pick）」は、配列または辞書と0始まりのIndexを入力し、一つの要素を返します。「配列・辞書からランダムに取得（RandomPick）」は、各要素から等確率で一つ選びます。辞書の場合は `{"A":1}` のようなKey-Value一組を返し、キーと値の対応を維持します。辞書の順序は保証しません。どちらも文字列・数値・Object・入れ子配列・nullとPath等の明示型を保持します。

空の配列・辞書、Pickの小数・負数・範囲外Indexはエラーとし、実際のnull要素と区別します。重複する配列値もRandomPickではそれぞれ一つの候補です。「配列・辞書の要素数（Count）」は直下の項目数を返し、空の場合は0になります。

Mathの「乱数を取得（Random）」は、最小値・最大値と整数／小数を設定でき、設定口への接続でも供給できます。既定は整数の0〜1です。整数は両端を含む符号付き64bit整数、小数は最小値以上・最大値未満の有限倍精度浮動小数点数です。上下限が同じならその値を返します。上下限の逆転、整数モードでの小数、非有限・表現範囲外の値はエラーとし、暗黙の交換や丸めをしません。

RandomPick／Randomは保存・型推測では抽選せず、一回の実行結果を複数の後続で共有します。固定された候補や範囲をForEachの各要素で抽選し直す場合は、要素の開始信号を開始入力へ接続してください。再抽選しても同じ値を選ぶ可能性があります。

たとえば候補のDictionary → RandomPick → 値取得 → 音声生成という配線で、音声生成だけがForEachの内側にある場合、選んだ音声はその反復全体で共有されます。文章ごとに音声を抽選する場合は、ForEachの `start` をRandomPickの `trigger` へ接続します。別のボタン押下や別の受信では、候補が同じでも再び抽選します。辞書のキーが異なっても値が同じなら、キーを除いた表示・処理結果も同じになります。

HTTPで画像・ファイルを取得するときは、HTTPリクエストの「応答本文の形式」を`Binary`または`自動判別`にし、「応答本文」をファイル作成／上書きノードの値入力へ接続します。PNG等をテキストへ変換せず元バイトのまま保存します。保存先Pathは後続で明示してください。HTTPステータス、Content-Type、応答ヘッダー、Content-Dispositionの推奨ファイル名は別出力で参照できます。

推奨ファイル名はディレクトリ部分を除き、ヘッダーがなければ空文字です。

既存HTTPリクエストは既定の`従来方式`を保ち、「出力値」はこれまでの`{statusCode,body}`のままです。新形式では同じ出力にContent-Type等と本文の符号化を付加し、Binary本文はBase64で保持します。受け渡し・保存したこの応答を「HTTP応答を解析」へ入れると、HTTPを再送せず本文をJSON／Text／Binaryとして取り出せます。HTTPリクエストの「応答本文」から直接つなぐ場合、解析ノードは不要です。

文字列へ変換済みの旧応答から画像の元バイト列は復元できません。

JSONのフィールドにBase64画像が入るAPIでは、HTTPリクエストの本文形式を`JSON`にし、対象フィールドを「Base64をバイト列へ変換」へ接続した後、ファイルへ保存します。`data:image/png;base64,...`形式も受け取り、そのContent-Typeを別出力へ保持します。標準Base64を対象とし、URL-safe Base64や非Base64のdata URLは暗黙変換しません。復号後の上限は既定16MiBで設定可能です。

不正データは失敗し、不完全なファイルを後続へ送りません。

「音声生成」と「テキスト生成」からサービスごとのレシピを選択してください。API入力の組立て、接続先、必須・任意項目、生成物の扱いは [AI・メディアの利用説明](nodes/ai-media.md) を参照してください。「動画生成」「画像生成」は現在レシピなしです。

## サブワークフロー

サブワークフローは、複数ノードと配線をまとめた再利用レシピです。親ワークフローでは一つのノードとして表示し、実行時には配置ごとの内部ノードと配線へ展開します。「SubWorkflowに分離」で作った定義、または「SubWorkflow 入力」(`subworkflow.input`)／「SubWorkflow 出力」(`subworkflow.output`)がある定義をサブワークフローとして扱います。

**ワークフロータブの名前のすぐ左**に通常ワークフロー／サブワークフローを区別するアイコンを表示します。ワークフロー設定の「公開入出力がなくてもSubWorkflowとして再利用する」で明示指定を変更できます。通常ワークフローへ戻す場合は、この指定を解除して公開入出力ノードも取り除きます。親からの抽出処理は親の明示指定を変更しません。

1. 別のワークフローに入力・出力ノードを置きます。各ノードが一つの公開項目になり、「公開する項目名」と型を指定します。同じ方向の項目名は重複できません。入出力で同じ名前を使うことはできます。
2. 必要なら「デフォルト値を指定する」を有効にし、型に合ったJSON値（文字列なら`"hello"`、数値なら`0`等）を入力してください。公開入力はデフォルトなしなら配置側の必須入力です。明示的に渡されたnullをデフォルトへ置き換えません。nullを許容する型と、引数の省略可能性は別です。
3. 入力ノードの右側から内部処理へ配線し、結果を出力ノードの左側へつなぎます。出力ノードは終端です。入力だけ・出力だけの構成も可能です。
4. 保存・共有して有効化すると、同じクラスターのノード一覧の「SubWorkflow」に、ワークフロー名のレシピが現れます。呼出しノードには公開した名前・型・必須性に対応する入力端子・出力端子が並びます。保存候補だけで未反映のものは公開しません。

配置先の実行計画に入れ子の定義も取り込み、開始済みの一回には後の更新・削除を遡及させません。必須引数不足・型不適合・自己／相互再帰は内部処理の開始前に拒否します。親の取消は展開した内部処理にも伝わり、同じレシピを複数配置した場合の引数・状態・プレビューは分離します。内部処理の失敗をデフォルト値で成功に置き換えません。

公開出力は、対応する内部の値が発生したときに親の後続へ渡します。待受ノードからは受信した各件が流れます。後続を特定の処理の完了で開始したい場合は、その内部ノードの完了端子を公開出力へつないでください。

OSC待受・タイマー等の待受ノードも内部に配置できます。定義の編集画面自体では待受を開始せず、配置先ワークフローの自動入力設定と内部待受ノードの開始設定に従います。定義の変更を反映すると、依存する配置先の次の入力へ反映し、設定が変わった待受を更新します。参照先の削除・不正化では依存する実行を止め、無関係なワークフローは継続します。入れ子は最大8段、展開後は最大4,096ノード・1MiBです。

公開名は128文字以内で、`/`・先頭`$`・共通の端子名`trigger`／`result`／`source`／`execution`／`fileTransaction`は使用できません。

配置ノードをダブルクリックすると、その配置に対応する内部の読み取り専用プレビューを開きます。 実効版の配置がある場合はその実行計画を表示します。未反映の保存済み配置は、ノードを実行せずに保存済み構成だけを表示し、その状態を明記します。実行中の枠発光・Preview値は実効版がある場合に取得します。Preview／ProgressBarと処理中表示はここで確認し、定義の編集画面では実行観測を表示しません。

親ワークフローでは内部のいずれかが処理中なら配置全体を処理中として表示します。選択範囲の分離、コピーと貼り付けは[WorkflowEditorの操作説明](workflow-editor.md)を参照してください。

## If

Controlの「If」は、条件（真偽値）を一度判定し、True側またはFalse側の開始信号の一方だけを出します。各信号を対応する後続の「開始」へ接続すると、If-StartとIfNot-Startを一つにまとめられます。「比較真偽値」は通常データとして条件そのものを出力します。False側の開始信号も、発火時に渡す信号値はtrueです。

文字列・数値・nullの条件はエラーとし、既存のIf-Start／IfNot-Startも引き続き利用できます。

## IsNull

Dataの「IsNull」は入力値がnullの場合に`true`、それ以外は`false`を返します。出力は真偽値なのでIfなどの条件入力へ接続できます。空文字列・`0`・`false`・空配列・空辞書・空バイト列はnullとして扱いません。入力が未到着の場合や入力元が失敗した場合に、勝手に`true`を返すことはありません。

## Null → Default

Dataの「Null → Default」は、「入力値」がnullの場合だけ「null時の既定値」を出力します。false・0・空文字列・空配列・空オブジェクト・空バイト列は置き換えません。選んだ値のPath・Int64・Dictionaryなどの型情報も保持します。既定値を省略するとnullを返します。未到着や入力元の失敗をnullへ読み替えることはありません。非nullの主入力が届いていれば、未選択の既定値が未到着でも主入力を渡せます。

## Button

Control の「ボタン」を配置すると、ノード上とインスペクターから押せます。「ボタンの表示文字列」と「押下時に渡す値」は直接入力または配線で指定します。値の欄は一組から開始し、表示中の値入力が埋まると次の入出力欄を一組追加します（最大64組）。途中の値を消しても残っている配線の番号は変わりません。文字列を実行せず確定できない場合、未入力の場合は既定の「押す」を表示します。

「押下時に渡す値」はPC選択ノードのPC候補も受け取れます。単一PC・複数PC・全PCの候補を対応する「押下時の値」から後続の「実行PC」へ接続し、開始タイミングを明示する場合は押下信号も後続の開始入力へ接続してください。通常の値とPC候補は別の値欄へ同時に接続できます。PC候補は押した回だけ渡し、保存・自動実行・別ボタンの押下で以前の候補を再利用しません。

保存して反映した後に押すと、そのノードを入口に一件の実行を開始します。`value`、`value2`、`value3`…はそれぞれの入力値の型を保って渡し、接続された値の未指定時は `null`、`start` はすべての値に対して一回の押下信号です。`start` を後続の「開始」へ、各値出力を必要な入力へ接続してください。従来の `value` と配線はそのまま利用できます。保存・ワークフロー全体の実行・他ノードからの値参照は押下扱いになりません。

押下は通常の手動実行と同じ操作IDで記録し、通信結果が不明な場合も自動で再実行しません。後続処理中の再押下は別の実行として受け付け、各ノードの重複実行設定を尊重します。通常ワークフローとサブワークフローの定義タブで押下できます。未保存・不正入力・復元中のノードは押下できず、保存版と有効版の一致を確認してから開始します。読み取り専用の配置プレビューでは操作しません。

複数のボタンを「値合流」と「開始Signal合流」へそれぞれ接続し、共通の後続やレシピへ渡せます。同じ押下から分岐した値と信号は、値合流を通っても同じ一件として合流します。押していないボタンや未選択の合流枝は正常な未実行として表示し、エラーには数えません。

開始された処理の必須入力が取得できない場合は、未選択の枝とは区別して入力元の確認を促します。入口のボタンだけが成功していても、ワークフロー全体を成功とは表示しません。

## ToggleButton

サブワークフロー定義上のトグルも操作できます。そこで確定した状態は同じ定義を参照する全配置で共有し、入れ子の配置でも元の定義のノードIDを使用します。値の参照だけでは反転も変更信号の発火も行いません。定義タブからの押下で開始する後続はその定義内の経路であり、すべての親ワークフローを暗黙に発火する操作ではありません。

旧版で配置ごとに保存した状態は、定義側に状態がまだない間だけ維持します。定義側で明示的に切り替えた後は、その確定状態が優先されます。通常ワークフローに直接配置したトグルの保存先は変わりません。展開したトグルは動作契約2を要求し、旧CoreServiceが共有先を無視して実行することを防ぎます。

Control の「トグルボタン」は、`offValue`（OFF時）と `onValue`（ON時）のどちらかを `value` へ渡します。初期状態はOFFです。例えばOFF側へスタブの値、ON側へ本番の値を接続すると、エディター上のボタンで供給する値を切り替えられます。`label` でボタンに表示する文字列を指定できます。

ボタン押下、または `trigger`（切替信号）への開始信号で状態を反転します。反転の保存が確認できた場合だけ `start`（切替時信号）が出ます。`value` の参照・表示・定数の編集では反転せず、信号も発火しません。`isOn` には現在のON状態を真偽値で出力します。手動実行APIから反転する場合は、このノードを入口にして `trigger: true` を入力してください。

状態はワークフローID・ノードIDごとに共有し、ブラウザーの再表示、CoreServiceの再起動、同じノードの設定変更でも維持します。コピーして別のノードIDになった場合はOFFから始まります。二つの候補値は型を変換せずに渡し、候補の型が異なる場合の出力型は `any` です。未指定の候補は `null` として扱います。

現在日時・乱数・RandomPickや、入力だけを変換するノードも候補値として接続できます。開始された後続が値を必要とした時点で評価し、同じ要求・同じ反復範囲の参照では結果を共有します。次の要求では改めて取得します。静的な定数として保存時に日時や乱数を固定せず、値の参照だけでToggleを反転しません。明示した開始信号は引き続き待ち、通信・ファイル書込みなどの一般処理を候補の参照だけで起動しません。

実行先は1台を選択してください。同時の切替は共有状態の比較更新で直列化し、保存結果が不明なときは自動で反転を再試行しません。画面は共有状態を定期確認し、取得できない場合はOFFと断定せず「?」を表示して押下を無効にします。切替信号から始まった後続処理には、その切替時に選んだ値を渡します。

トグルの値からIf-Start／IfNot-Startで定数や純粋な変換を選び、値 mergeへ合流させた構成も、別のボタンで開始した処理から参照できます。条件が選んだ一つの値を取得し、値参照による合流信号は発火しません。複数の枝が同時に値を供給する場合は曖昧な選択としてエラーにします。値を取得するために別のボタンを押したり、待受や一般の信号待ち処理を開始したりしません。

## DictionaryとKey-Value

Valuesの「Dictionary（辞書）」は、Arrayと同様に一括入力と追加一件を持ちます。「Key-Value配列／既存の辞書」へ `[{"A":1},{"B":2}]` または `{"A":1}` を入力し、「追加するKey-Value」へ `{"C":3}` を渡すと、一つの辞書になります。どちらも未接続なら空辞書 `{}` です。キーは文字列として大文字・小文字を区別し、`"01"` と `"1"` も別のキーです。

重複キーは既定でエラーになり、「重複キー」を上書きへ変えると後に入力した値を採用します。

辞書はForEach／Parallel ForEachへ直接入力できます。`item` は `{"A":1}` のような一組のKey-Valueです。入力時の並びをなるべく維持しますが、辞書の反復順は保証しません。「Key-ValueからKey取得」「Key-ValueからValue取得」を接続すると、キーと値をそれぞれ取り出せます。値の入れ子型やPathも保持します。これらの抽出ノードへ空辞書や複数項目を渡すとエラーになります。

複数項目の辞書からキーで選ぶ場合は、既存の「Keyから値を取得」へ辞書を直接接続します。

ForEach Endの各結果欄へKey-Value／Dictionaryを渡すと、その欄の結果は配列ではなく辞書になります。通常の数値・文字列・オブジェクトなどを渡す欄は配列です。Key-Valueの型が判明している空反復は空辞書を返します。結果キーの重複は既定でエラーとなり、Endの設定で上書きを選べます。並列時の上書きは完了順ではなく入力順の後の値を採用します。集約エラーになっても、完了済みのボディの副作用は再実行・巻き戻ししません。

C#の`Dictionary<TKey,TValue>`、Pythonの`dict[K,V]`／`typing.Dict[K,V]`はキー型・値型まで解析します。JavaScriptでは辞書を通常のObjectとして渡し、JSDocの`Record<string, T>`または`Object.<string, T>`から型を取得できます。辞書の値が混在して型を確定できない場合は`any`です。

```csharp
public static Dictionary<string, int> Run(Dictionary<string, int> values)
{
    values["C"] = 3;
    return values;
}
```

```python
def run(values: dict[str, int]) -> dict[str, int]:
    return {**values, "C": 3}
```

```javascript
/** @param {Record<string, number>} values
 * @returns {Record<string, number>} */
export function run(values) {
    return { ...values, C: 3 };
}
```

JSONでの保存・通信表現は通常のObjectです。C#／Pythonで整数・真偽値キーを明示した場合は、型情報に従って言語のキーへ復元します。整数キーの`"01"`など、変換後に別表記と衝突する値は拒否します。保存済みのC#／Pythonで辞書が単なるObjectとして解析されていた定義も、従来の契約を維持したまま実行できます。
