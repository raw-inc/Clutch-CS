## 受信・入力時の開始信号

### 値の要求時実行と保持

開始信号を接続していない一回で完了する処理ノードは、実際に起動した後続が不足しているデータを必要とした時点で実行します。C#／Python／JavaScriptスクリプトだけでなく、値変換やファイル操作にも適用します。編集中の表示・プレビュー・検証・保存のために処理を実行することはありません。開始信号や診断用の`result`を参照しただけで、未開始の処理を勝手に起動することもありません。

同じワークフロー実行内の同じ入力は一回の実行結果を共有し、ForEachの反復だけではリセットしません。日付取得のような入力の変わらない処理は反復中も同じ結果を使い、要素を入力に使う変換等は入力の違いを反映します。条件ゲートの信号は、その条件を供給した入力事象も区別します。同じ結果が複数箇所から参照されても、処理の失敗・結果不明を理由に暗黙再実行しません。合流から派生した後続も、元の要求に属する値と要求時評価の結果を引き継ぎます。

開始信号が別経路を先に到着しても、接続された同じ要求の値が処理中ならその完了を待ちます。並行する別要求の最新値で置き換えたり、値を得るために完了済みの副作用を再実行したりしません。

接続した必須値が「分岐が選択されなかったため未供給」である場合、その理由を型変換・計算・Concat・サブワークフロー境界の後続にも引き継ぎます。例えば個別送信先のIPv4生成をIf-Startで分岐させていれば、共通の受信パケットが別口から届いても、非選択の個別送信は `input.branchNotSelected` として対象外になります。通常入力と動的設定入力に共通で、ForEach／Parallel ForEachでは要素ごとに判定します。

ValueMergeは有効な候補を採用し、全候補の非選択が確定したときだけ後続にも非選択を伝えます。未到着の候補は待機のまま扱います。

これは値の欠落をすべて無視する機能ではありません。利用側へ明示した開始信号が届いた場合や、上流の障害・結果不明・通常の出力欠損では、必要な値を取得できなかったことを報告します。正常なJSON nullは未供給と区別し、Null → Defaultの既定値選択も維持します。非選択だけでワークフローを失敗にしたり、エディターのノード・タブをエラーとして強調したりはしません。

「開始」に信号を接続したノードは、その信号で実行した結果をコーディネーターの実行用メモリへ保持し、別の受信・実行からのデータ参照でも再実行しません。同じ要求の結果を待つ場合とは別に、独立した要求から保持値を参照する場合は、初回信号前・別の実行で処理中・保持値の確認不能時には値未供給として後続を実行しません。独立した処理の値更新を明示的な開始条件にするには、そのノードの処理完了を開始入力へ接続します。新しい信号で更新した値を、古い並行実行の遅延完了で上書きしません。

保持値は設定版を区別し、直近4版まで保持します。コーディネーターの再起動・交代後は未供給へ戻し、新しいStartSignalで更新します。過去の保存結果から副作用を自動再実行したり、未保存の新世代を見落として古い値を再利用したりしません。

ワークフローの明示取消は、ノード本体に加え、開始世代・完了値の共有確認待ちにも適用します。完了値の共有確認中に取り消しても、ノードの確定済みの成否は維持します。成功済みのノードには `value.retentionUnconfirmed` を付けます。取消・失敗などの理由がある場合は上書きせず、共有を確認できなかった旨を説明に追加します。確認の中断を理由に処理を再実行しません。配送済み要求の取消受付と、実行先での停止確認は引き続き別に扱います。

設定、明示的な状態保存、時間指定処理、ファイル補償などの耐久性が必要な操作は従来の永続保存を使用します。同じ保存先のロック取得はプロセス内で待機をまとめ、各待機者がロックファイルへ繰り返しアクセスすることを防ぎます。共有状態の比較更新はコーディネーターで順番に現在版を確認し、既に版が違う要求はピア間の保存準備・中止へ配送しません。成功する変更の永続保存と固定参加者への確認は省略しません。

同じノードの開始・完了値についても、読取りと比較更新の区間を実行間で直列化し、古い版からの比較更新の集中を抑えます。ノード本体はこの排他に含めません。共有同期用の履歴所有情報は一括取得し、履歴の件数分だけDBを開き直したりJSON保存全体を読み直したりしません。保存行の完全性確認と共有対象の選別は維持します。

同期取込みでも履歴の内容照合をまとめ、内容が同じ所有情報は再保存しません。通常参加中の同じピア実体から古い版情報を受け取った場合は、両端の現在版を再確認し、一致していれば全体同期を省きます。新規参加・再参加、未確認の同期や競合が残る場合は完全同期を維持します。現在版の照会に未対応のピアや、照会が確認できない場合も既存の同期方式へ戻ります。

完全同期の転送は最大8KiBの固定断片を4件まで同時に照会し、履歴が増えた際の往復待ちを重ねます。受信本文の保持は最大32KiBに限定し、応答が前後しても元の順序へ戻して保存します。同じスナップショット・送信実体・範囲と全体ハッシュの検証が完了するまで共有状態へ取り込みません。旧版も扱える読取り要求を使うため、混在更新中も新しい転送形式への一斉切替は不要です。

ForEach／Parallel ForEachの「要素の開始」(`start`)を接続すると、同じ値を使う処理でも要素ごとに実行できます。待受と反復の制御境界は要求時の通常処理として再起動しません。接続されたデータが未供給の場合に、Concat等が残りの値だけで処理を進めることもありません。

保持量は有限です。一件内の値共有は16,384種類の入力と出力ペイロード合計64MiB、信号による保持はノード・設定版ごとに1MiBまで、コーディネーター全体で4,096キー・値のペイロード合計64MiBまでです。超過時は理由を残して値を供給せず、既に終了した副作用の成否を未実行へ戻したり、値を取り直すために同じ副作用を繰り返したりしません。

### 実行時間と非同期の実行記録

通常入力は到着通知で即座に実行キューを起こし、周期的な巡回を待ちません。安全停止で保持している入力の再確認周期と、通常入力の開始は分離しています。Parallel ForEachは有限のワーカーを独立して開始し、ボディの同期計算も指定した並列枠で処理します。結果の集約順序は入力順を維持します。

Parallel ForEachの「要素の開始間隔 (ms)」（`startIntervalMs`）は、最初の要素の開始を基準とする開始時刻の刻みです。既定の0は間隔なしで、正の整数を指定すると一つの刻みにつき一要素を開始します。例えば間隔100ms・並列数3なら0、100、200msに開始し、350msに空き枠ができた場合は400ms、375msに別の枠が空いた場合は500msに次の要素を開始します。未使用の過去の刻みをまとめて消化しません。

間隔は一回のループ実行ごとに独立し、Array・Dictionaryのどちらにも適用されます。未開始の待機要素は並列数や実行件数へ加算せず、break・取消・失敗時は開始を止めて既に開始した処理の終了を待ちます。

API呼出しを分散する場合は、対象APIノードを要素処理の先頭に近づけてください。制御するのは要素の開始時刻であり、手前の処理時間や通信のばらつき、別のループ・ワークフローからの呼出しは合算しません。実際の開始はOSのタイマーや処理負荷によって遅れることがあります。稼働中の一回の設定は固定され、保存した間隔変更は次の実行から適用します。

ForEach Endの「今回の処理結果」は、一つ入力すると次の欄が増える可変入力です。各入力に対応する「まとめた処理結果」が独立した配列または辞書になり、配列の同じ添字は同じ要素の処理を表します。Key-Value／Dictionaryの入力は辞書、それ以外は配列です。既存の`value`は最初の結果として維持し、追加分は`value2`、`value3`のように番号を付けます。途中の欄を外しても後続の番号は変わりません。最大数は他の可変端子と同じ64組です。

`continue`へ開始・完了信号を接続すると、その要素で未開始の処理を省略して次の要素へ進みます。`break`では未開始の要素も止め、集約結果を反復外へ渡します。制御信号の接続は任意で、信号が届かない場合もボディの終了から自動で進みます。両方が同時に届いた場合はbreakを優先します。入れ子のbreakは対応するループだけを終了し、外側を終了した場合は内側でも新しい処理を開始しません。

既に開始した処理は、結果を確認してから次の要素や反復外へ進みます。Parallel ForEachのbreakも開始済み要素を待ち、その後の追加要素を止めます。開始済み処理の失敗・結果不明は正常終了に置き換えません。信号が届いた時点で結果の組が揃っていれば今回分を含め、未到着の値があればその要素を全結果配列から同時に省略します。遅れて届いた別経路の値や、別要素・別要求の値で空欄を埋めません。省略したノードは意図した未実行として表示します。

同じCoreService内のノードは、一件のワークフローが所有する実行器へ直接渡します。遠隔ノードは固定したピア起動実体と要求IDで重複を抑止し、確認した処理結果を先に返してから永続記録します。応答待ちの取消や記録の失敗によって処理を繰り返しません。異常終了後に未保存の結果を確認できない場合は結果不明として扱い、新しい実体への自動再送は行いません。設定・ワークフロー定義の保存確認は、この非同期化の対象外です。

非同期の要求記録は、進行中と保存待ちの予約枠が最大512件、メモリに保持する結果本文は合計64MiBまでです。保存済みの要求履歴は別に蓄積されます。一件の記録本文が4MiBを超える場合は、元の呼出しに実結果を返したうえで、再照会用記録の詳細省略を明示します。受付枠が満杯なら新しい処理を開始前に拒否します。管理状態の`runtimeReceipts`で進行中・保存待ち・保存問題を確認できます。

ワークフロー全体の診断結果は実行経路とは独立して追記し、最大256スロット・一件64KiBの結果または要約を残します。同じ結果を周期ごとに書き直しません。再起動後の履歴照会にも使用しますが、業務処理や保持値の自動再開には使用しません。保存不能は`executionHistoryProblem`で確認でき、正常停止では受付済み処理の終了後に残った結果の保存を試みます。

新方式の保持値共有は、通常参加中の全ピアが対応してから使用します。対応可否は起動実体ごとの参照専用照会で確認し、通常入力ごとには照会しません。生存通知の本文は旧Web クライアント／Updaterも読める形式を維持します。更新途中に旧ピアがいる間は従来の保存経路を維持します。新方式の使用後に旧ピアが戻った場合は、古い永続値へ自動で戻さず保持値の利用を停止します。明示離脱中は従来のローカル状態保存を使用します。

保持値の担当が同じCoreServiceであれば、現在の担当世代・参加状態・比較版・容量を確認してメモリを直接更新します。この内部更新だけのための通信や要求応答記録は作りません。別ピアが担当する場合は、固定した実体への共有要求を使用します。返却値の変更が保持値へ波及しないよう、値の所有権は分離します。

WindowsのUDP送信は、CoreServiceが別作業で観測したNIC情報を利用し、指定IPv4に加えて送信インターフェース索引をソケットへ固定します。OSのネットワーク変更通知で観測を失効させ、古すぎる観測は再確認します。送信だけのUDPソケットでは不要な受信タスクを開始しません。内部事象は対応ピア間で、既に届いた事象を最大32件・32KiBの組にまとめます。転送待ちは512件までとし、ローカル配信済み事象の再解析・再配信を省きます。

まとめるための時間待ちは追加せず、発生元・重複・容量の検査を維持します。

Windows上の有限外部コマンドは、標準出力・標準エラーの同期pipeで共通ThreadPoolを占有しないよう、専有する読取りhandleの到着済みbyteだけを取り出します。空のpipeでは取消可能な待機へ戻します。文字コード・BOM、出力量制限、取消時の実プロセス停止、継承されたpipeの終了待ち上限は維持します。生存通知の開始・状態照会も、呼出元の同期コンテキストが処理を進めることに依存しません。

Windowsの外部コマンド起動は、OS呼出しに入る前の待機を非同期化します。`Process.Start`内部の共通lockへ多数の実行スレッドが同時に滞留することを抑え、起動が済んだプロセスは並行して実行します。待機中の取消ではプロセスを開始しません。

C#スクリプトは解析時に実行用アセンブリまで準備し、有限キャッシュから再利用します。スクリプト本体は別プロセスで実行し、解析中には実行しません。RIDを指定したCoreServiceの発行ではReadyToRunを使い、初回実行のJIT負荷を減らします。([.NET ReadyToRun](https://learn.microsoft.com/en-us/dotnet/core/deploying/ready-to-run))

通常時の性能確認は`ForwardingLatencyProbeTests`、高負荷の確認は別の`ForwardingLoadTests`で実行します。固定した46ノード・59接続の試験ワークフローを4つの隔離CoreServiceへ配置し、宛先をループバックへ限定します。通常試験は前回ワークフロー完了後に入力し、負荷試験は約60Hzの連続入力と待ち時間なしの一斉入力を分けます。

送信漏れ・重複・別入力との混同・実行待ちの解放を検査し、遅延とCoreService自身のCPU累積時間・メモリ・スレッド数を記録します。CPU値は外部ワーカーを含まず、メモリの前後観測だけで長期間のリークがないと断定しません。

`CONTENTS_PROBE_ITERATIONS`で各経路の回数（1〜128）、`CONTENTS_PROBE_CORE`で比較するCoreService実行ファイルを指定できます。連続入力試験の間隔は`CONTENTS_PROBE_INTERVAL_MS`（既定17ms）で変更できます。測定値は`.work/workflow-latency`へ出力します。時間の閾値を通常の並列試験の成否条件にはせず、初回・中央値・p95・最大値を分けて確認してください。

本番ワークフローや実機宛先へ試験データを送る試験ではありません。

### 完了信号と成否

外部I/O・待機・実行完了を待つ一回で完了する処理（通信、ファイル・ディレクトリ操作、DB／状態保存、プロセス、スクリプト、媒体変換、AI、Delay、ForEachの反復全体）に「処理完了」(`$completed`)と「成否」(`$succeeded`)を提供します。If／IfNot、比較・論理・算術、値・コメント・Concat・変換、単純な振り分けには追加しません。遠隔配送やValueTask形式だけで非同期処理とは判定せず、ノードの完了待ち能力の宣言に従います。

If／IfNot本来の条件付き開始信号、待受の受信信号、信号合流の固有出力は維持します。処理完了は成功だけでなく確定した失敗・取消でも発火し、通常の成功値出力とは独立しています。結果不明や未実行を完了信号にはしません。成否は確認済み成功がtrue、確定失敗がfalseです。処理中・未確認のnullは画面上の状態表示に使い、開始時のnullを後続へ送る二段階の実行にはしません。取消・結果不明をfalseと断定することもありません。

ノードの成否欄は既存の状態観測を使い、表示のための実行や出力本文の取得をしません。他のワークフローの実行だけでキャンバスを再描画せず、未保存の草稿や別設定版へ古い成否を表示しません。ForEachの要素開始と反復全体の処理完了は別の信号です。

### 開始信号の合流

| ノード | 発火とリセット |
| --- | --- |
| StartSignal合流（都度） | 新しい入力信号ごとに後続を開始。他の入力を待ちません。 |
| StartSignal合流（先着1回） | 既定は同じ要求内の最初の入力で一回発火し、元のデータと反復範囲を維持します。非選択枝を待ち続けず、次の要求・要素では独立して判定します。 |
| StartSignal合流（全入力） | 全入力が揃うと一回発火し、全入力をリセットします。 |

先着1回の `scope` は既定が `execution`（同じ要求内）です。フォルダーが既存ならIf側、なければ作成成功側を先着へ接続し、その出力をForEach内の処理の開始へ渡す構成では、共通準備を待って各要素を一回ずつ処理します。別のOSC要求の信号や要素の値は混ぜません。反復内に先着を置いた場合も、その要素のEndへ収集できます。

先着の `scope = events`、都度、全入力は、別々のOSC受信・ワークフロー実行・ピアにまたがる信号を扱います。要求をまたぐ先着・全入力では、未発火の一巡中に同じ入力へ複数回来ても一回分にまとめます。接続した入力だけが待機対象で、追加用の空き口や定数は対象になりません。入力端子はConcatと同じように増え、最大64口です。

要求をまたぐ方式での合流の発火は新しいワークフロー実行の開始境界です。発火した要求の値は、その要求の処理中の結果も含めて後続へ引き継ぎます。たとえば同じ受信からファイル読み込みと開始信号を分岐させ、開始信号だけを都度合流へ通しても、後続は同じ受信の読み込み結果を待って使用します。値の借用では元の開始・完了信号を再発火させません。ForEachから信号を出すこともできますが、別実行へ進んだ処理を元のForEach Endへ収集する構成にはしません。

全入力合流などが別々の要求を待ち合わせる場合、引き継ぐのは今回の発火を成立させた要求の文脈です。異なる受信のデータを自動で一組にはしません。別の受信時の値も後で使う場合は、開始信号付きノードで値を保持し、その「処理完了」を合流へ接続します。合流状態の保存が確認できない場合は信号を出さず、処理を再送しません。設定版の違う到着状態も混ぜません。

合流から開始した後続も元の実行が追跡し、元入力の明示取消を値待ち・開始待ちを含む子実行へ配送します。後続の同時実行は16件までとし、待機中を含め一要求からの発火は16,384件までです。並列枠を待つ間も元の値供給処理は進め、上限による未開始を成功扱いしません。共有保存の版競合は返却された確認済み状態から再計算しますが、保存結果不明を競合として再送しません。

### 値の合流

PC候補もValueMergeへ接続できます。If-Start／IfNot-Startの開始信号を「PCを選択」または低負荷PC選択の`trigger`へ渡し、各PC候補の出力をValueMergeの入力へ接続します。ValueMergeの値出力を処理ノードの「実行PC」へ、必要なら受信信号をその処理の開始入力へ接続してください。実行中に最初に到着した一入力のPC候補（単一・複数どちらも可）を採用し、他の入力の候補を混合しません。

後着は下記の反復外・要素内の区分に従い、開始済みの処理の宛先は変更しません。

PC候補の条件は開始したワークフローの設定版で固定し、ピアの実体・優先度・負荷観測もそのワークフロー開始時の情報を使います。別のワークフロー実行の保持済みPC候補を流用しません。継続待受の実行先は引き続き開始前に確定する選択が必要です。開始信号を接続せず、設定時に複数のPC候補が同時に確定する場合は、入力番号の小さい候補を採用します。通常のJSON・Binary値とPC候補は一つのValueMergeへ混在させられません。

「値合流（Value Merge）」(`control.valueMerge`) は、複数のPCやポートから届く値を一つの後続へ流します。各受信ノードの値出力を `input1`、`input2` …へ接続してください。入力端子は1口から始まり、接続すると次の空き口が増えます（最大64口）。反復外で複数の受信を束ねる場合は、到着するたびに `value`（受信値）と `start`（到着時信号）を出力し、他の入力を待たずに後続を開始します。

一件の最初の値は、その一件の別経路の値や信号と合流できます。同じ実行中の追加到着と反復から外へ送り出す各要素は独立した後続へ渡し、先の値を上書きしません。同じ内容の別受信も一回ずつ処理します。

OSCのようにアドレスと複数の引数を一緒に扱う場合は、各受信ノードの `value`（パケット全体）を値合流へつなぎ、合流後に「OSCパケット解析」へ渡します。その解析結果からアドレス・引数を個別に配線してください。関連する項目を一つの受信値にまとめたまま合流することで、後続に時間のかかるノードがあっても、その一件の組を維持できます。

別々の合流ノードで項目ごとの最新値を集めたり、元の受信枝にある保持値を後から参照したりすると、異なる受信の値を選ぶ構成になるため、一件を構成するデータは合流後の `value` から取り出します。

文字列・数値・配列・Object・バイナリを変換せずに渡し、`false` と `null` も到着した値として扱います。接続元がすべて同じ型なら出力にもその型を表示し、異なる型を混在させた場合は `any` とします。待受の開始・終了、設定値の評価、保持値の再参照では発火しません。番号付き入力への定数指定はできません。

合流ノードの実行先は1台を選択します。受信側は複数PCに配置でき、後続の「入力元PC」は元の受信PCを維持します。反復外の合流や、ForEachから反復外へ送り出す合流では、元の要求内で複数の枝から届いた場合も到着ごとに別の実行として扱います。元入力の取消は開始済みの子実行へ伝わり、終了まで追跡します。

ForEach／ParallelForEachの同じ要素内で完結する枝を合流し、同じ要素のデータと組み合わせたりForEach Endへ収集したりする場合は、要素内の値選択として動作します。各要素で最初に届いた一つの値を採用し、その要素の後続を一度だけ開始します。例えば「seedがあるときは指定したvoice ID、ないときはRandomPick」を合流し、同じ要素の本文とともに音声生成へ渡せます。後着の値で選択済みの値を置き換えず、開始済みの枝の終了は反復が回収します。

入れ子・並列の要素や別のワークフロー要求の値は混ぜません。異なる反復の値を一つの要素内へ合流する配線や、反復完了結果をその反復の途中へ戻す配線は引き続き検証エラーです。

合流の後続へ別経路のデータが先に届いた場合、まだ合流事象の値がない先行評価は `input.eventPending`（合流待ち）として扱います。その後、同じ要求の合流事象から起動した処理が成功したのに、先行評価だけを理由にワークフロー全体を失敗にしません。合流待ちでない必須入力の不足や、実際に開始した処理の失敗・結果不明は区別して報告します。

### 待受からの開始信号

OSC（UDP/TCP）、HTTP、TCP、UDP、WebSocketなどの待受ノードノードは、右側に「受信・入力時」(`start`)を公開します。この出力を後続ノードの「開始」(`trigger`)へ接続すると、正常に受け付けた入力一件ごとに後続処理を起動できます。受信データは従来の出力から別途配線します。ファイル監視・タイマー・フックなども、それぞれの正常入力に同じ共通信号を供給します。

待受を開始しただけの時点、待受の正常終了、取消、失敗、不正な受信データでは信号を出しません。開始信号を明示配線したノードは、他のデータ入力が届いてもその信号を迂回して起動しません。既存の `result`・`source` 出力と結果経路は引き続き使えます。

### 次回発火デバッグ（experimental）

`/editor?experimental=true` で保存済みワークフローを開き、「次回発火デバッグ」から「次の1回を記録」を選択してください。[試験的な機能の常時有効化](../guides/web-client.md#試験的な機能を有効にする)でも同じ操作を利用できます。予約操作でワークフローを実行することはありません。予約時の参加CoreServiceへ準備を配布した後、次に受け付けた入力一件だけが記録対象になります。同時に別PCから入力が届いても採用するのは一件です。手動実行も対象ですが、待受の開始・正常終了だけでは予約を消費しません。

ノードの入力・出力の概要、接続元と入力端子、その経路の値の有無、成否・理由、実行IDと合流元の親実行IDを記録します。ForEachの反復や合流からの子実行も同じ記録へまとめ、未実行の枝と反復結果の集約を区別します。OSCなどの小さなObjectは構造を残し、バイナリは種類とバイト数だけを表示します。認証用の項目は伏せ字にし、大きな文字列・配列・Objectは省略します。

既定は無効です。取得が始まると次の入力への予約は自動解除されます。「記録だけ停止」はワークフロー本体を停止しません。通常の高頻度実行履歴とは別の一時メモリで、一件につき最大4MiB・4,096評価、CoreServiceごとに最大16予約を保持します。上限到達時は部分記録と明示して業務処理を続けます。予約は10分、記録は予約から30分までとし、所有CoreServiceの再起動でも失われます。参加実体が変わった場合は予約を選び直さず、状態を確認して再予約してください。

画面ではページごとに結果を確認でき、「デバッグJSONを保存」で要約済み記録を手元へ残せます。画面を閉じても予約・取得は継続し、同じ接続先から再度開くと直近の記録を表示します。通常traceやワークフローの保存設定は変更しません。

## ノードの動作契約と互換性を確認する

ノードの設定には、期待する動作を表す `contractVersion` を保存できます。カタログには現在の実装の `contractVersion` と、実装が明示的に対応する旧版の `compatibleContractVersions` を表示します。設定項目の型が一致していても、動作契約が未対応なら開始しません。

契約1は初回リリースの動作です。`contractVersion` のない定義は契約1として読み、読込時にプロパティを追記したり、保存済みの内容ハッシュを変更したりしません。新しく配置するノードにはカタログの契約版を記録します。

エディターの **動作契約** 欄で期待版と実装版を確認できます。版を変更しても設定や配線は自動変換しません。動作を確認し、必要な設定・配線を編集して、検証・保存・反映の順に進めてください。編集ロックとUndoは、契約版の変更にも適用されます。

ワークフロー操作の **互換性を確認** では、選択したピアの実装に対し、保存版・有効版・そのピアに保存された関連スナップショットを検査します。問題のあるノード、要求版と実装版、確認する設定キー、理由を表示します。未保存の草稿はエディターの検証を使用してください。スナップショットはページ単位で確認し、続きや省略がある場合は画面に表示します。別ピアの実装と保存内容は、そのピアを選択して確認します。

互換性を確認できない定義の開始・反映やスナップショット復元は拒否します。状態を利用するノードの契約版が変わる場合は、状態スナップショットの互換性も検査します。設定の自動移行や状態値の自動変換は行いません。CLIからの確認は [管理CLIの互換性照会](command-line.md#動作契約とスナップショットの互換性確認) を参照してください。

## 日時処理の担当交代と対象PCの復帰

日時実行（`scheduling.timer`）の `timeZoneId` は、日時取得ノードと同じく `UTC`、`Asia/Tokyo`、`Tokyo Standard Time` などを指定できます。新規配置の既定はUTCです。空欄・未指定の既存ノードは従来のクラスター共通タイムゾーンを引き継ぐため、更新だけで予定時刻を変更しません。ブラウザーの表示用タイムゾーンとは独立しています。

オフセットのない指定日時・開始終了時刻、日次／曜日の時刻、追加日・除外日は選択した地域で解釈します。`Z` や `+09:00` を付けた日時はその絶対時刻を維持します。夏時間で存在しない時刻・二通りに解釈できる時刻は拒否し、別時刻へ暗黙補正しません。明示ゾーンがある予定は、クラスター共通ゾーン変更だけでは受付位置をリセットしません。地域の定義は実行PCのタイムゾーンデータを使います。

`scheduling.timer` は、同じ時間指定の基準時刻と受付済み位置を共有します。優先PCが替わっても、完了済みの一回指定を発生させ直しません。表示・遅延方針・そのモードで使わない設定の変更でも、予定位置を維持します。全予定が除外される場合や保持上限で拒否した回も記録します。

予定時刻に対象PCが不在の場合、`missed` の `delay` は復帰を待ち、`skip` は実行を見送り、`within` は `toleranceMilliseconds` の範囲で待ちます。待つのは取得時に固定した対象PCです。取得時から動いていた実体が後で失われた場合に、別実体へ暗黙に送り直すことはありません。同じ対象へ未開始の予定が重なった場合は、古い回を見送り、最新回を残します。

取得済みの入力・設定・対象を保存し、まだ一度も配送を始めていない回だけを担当交代時に引き継ぎます。一部でも配送開始を許可した回は、元の担当を失うと結果不明として扱い、ワークフロー全体を再実行しません。取消指示も共有記録へ残します。全ピア停止を越えた待機の保証や、待機回だけを操作する専用画面はありません。

保持する未完了の日時入力は最大512件、本文合計128MiBです。上限に達した回は理由を付けて拒否し、通常の成功として扱いません。Dashboardの実行画面で、保持中の件数、結果の保存確認待ち、最後に確認した問題を確認できます。予定位置などの競合は関係する日時処理へ影響を限定します。配送許可や取消記録を巻き戻す危険があるため、異なる進行記録を通常の候補編集・削除で置き換えることはできません。

## 条件に応じて待受を正常終了する

継続入力ノードの `source` 出力には、入力を発生させた待受のIDとピアの起動IDを含めています。この値を `control.source.end` の `source` 入力へ接続すると、その待受に新規入力の受付終了を要求できます。

条件付きで終了する場合は、待受ノードの `source` を `control.condition` の `value` へ、判定する値を `comparison` へ接続します。条件ノードの `value` 出力から、成立時の `true` 経路を選んで `control.source.end` へつなぎます。待受を止めた後も、受け付け済みの入力とそこから始まった処理は継続します。

終了要求の受付結果と、待受ノードの `completed` 経路へ出る実際の終了結果は別です。

Dashboardの「実行とプロセス」でも、待受の受付終了と、受け付け済み処理を含む取消を選べます。一回で完了する処理は「実行中のワークフロー」または操作履歴から取り消し、元の実行結果を照会します。取消は元の実行IDと開始元ピアの起動IDで特定します。CLIの操作方法は[有限処理の取消](command-line.md#実行中の処理を取り消す)を参照してください。

## 共通フックから後続処理を始める

`control.hook` は、購読開始後に発行されたイベントを受け取り、通常の条件・変換・通信ノードへ渡します。`name`、`workflow`、`node`、`peer` で発生元を絞り込めます。未指定の条件は制限しません。`count` を指定すると、条件に合うイベントをその件数だけ受け取って正常終了します。接続中の別ピアで発生したイベントも同じ方法で購読できます。

| イベント名 | `value` に渡す内容 |
| --- | --- |
| `log.written` | 秘密情報・個人情報の保護を適用し、保存キューで受け付けたローカルログ。転送ログの再受信では再発行しません。 |
| `node.started` / `node.completed` | ノード実行IDと設定版。終了時は `result` に成否、経路、出力、理由を含みます。 |
| `workflow.started` / `workflow.completed` | 一件の実行IDと設定版。終了時は対象別結果を含む `report`、または省略を明示した `summary` を返します。 |
| `source.status` | 待受のID、ピアの起動ID、状態と終了結果。 |
| `peer.status` | 発行元ピア自身の状態変化。状態値は数値形式です。 |
| `peer.changed` | 発行元ピアから観測した相手の `previous` / `current`。相手を初めて観測した場合は `previous`、観測一覧から外れた場合は `current` がnullです。通信不能は `current.status` で区別します。 |
| `cluster.coordinatorChanged` | 観測元ピアが確認したコーディネーターの `previous` / `current`。 |
| `snapshot.capture.started` / `snapshot.capture.completed` | 取得操作IDと対象。終了時は保存結果とスナップショットID。保存内容そのものは含めません。 |
| `snapshot.restore.started` / `snapshot.restore.recovering` / `snapshot.restore.completed` | 復元操作IDと対象。終了時は対象別の適用・補償結果。 |
| `application.started` / `application.stopped` / `application.restarted` | 登録アプリケーションの起動・終了・再起動。専用の`process.lifecycle`では各事象の信号とPIDを出力します。[登録と監視設定](applications.md)を参照してください。 |
| `process.changed` | プロセス監視ノードが検出した状態変化。 |
| `control.publish` で設定した名前 | 発行ノードの `value` 入力。 |

`event` 出力には、事象ID、時刻、発生元と因果IDを含めます。項目名は `Id`、`Name`、`Time`、`PeerId`、`PeerInstanceId`、`WorkflowId`、`NodeId`、`CausationId` です。`value` は管理APIと同じcamelCaseの項目名と文字列の成否を使います。例えば、ログ本文は `/message`、ノードの成否は `/result/outcome` で取り出せます。

各購読先とピア間の送信キューは256件まで保持します。遅い購読先を待って通常処理を止めず、上限を超えた配信は欠落として数えます。一件の通知が32 KiBを超える場合は値を省略し、`event.DetailReason` に `event.dataOmitted` を示します。省略後も上限を超える通知は受け付けません。購読数、配信の欠落数、値の省略数と最後の問題はDashboardの「実行とプロセス」と `status` で確認できます。

フックが作るログやイベントには、既に通った購読ノードを引き継ぎます。同じ事象から同じフックへ戻る経路を再実行せず、一つの連鎖は最大32段階とします。同じ事象IDの再到着も直近4096件の範囲で除外します。切断中のイベントの履歴再生や、すべての購読先への到達保証はありません。必要な操作結果は、元の操作IDで別途照会してください。

## C#の継続待受

`C# 継続待受`（`script.csharp-source`）は、単発のC#スクリプトと同じ入出力解析・個別引数入力・NuGet構成を使い、`public static IAsyncEnumerable<T> Run(...)`の各要素を値と信号として後続へ渡します。`T`を出力型として推論し、`byte[]`はBinaryとして渡します。同名の`Run`を複数定義したり、`Task<IAsyncEnumerable<T>>`を返したりする入口は受け付けません。

`CancellationToken`引数は最大一つで、入力欄には出さずワークフローの停止を通知します。非同期イテレーターでは`[EnumeratorCancellation]`を付け、通信・Delayへtokenを渡してください。例えば次はUTF-8のUDP文字列を受信するたびに後続を開始します。

```csharp
using System.Net;
using System.Net.Sockets;
using System.Text;

public static async IAsyncEnumerable<string> Run(
    int port,
    [EnumeratorCancellation] CancellationToken cancellationToken = default)
{
    using var receiver = new UdpClient(new IPEndPoint(IPAddress.Any, port));
    while (!cancellationToken.IsCancellationRequested)
    {
        var packet = await receiver.ReceiveAsync(cancellationToken);
        yield return Encoding.UTF8.GetString(packet.Buffer);
    }
}
```

コードと引数・パッケージ構成は待受開始時に固定します。各`yield return`は別の一件の実行へ値を渡すため、後続が処理中でも受信を継続できます。受渡し先が詰まった場合は有限pipeで待ち、親プロセス内へ無制限の出力キューを作りません。`maxBytes`は一要素のJSONフレーム（BinaryのBase64表現とメタデータを含む）の上限です。

ワークフローの通常停止でも取消tokenを通知し、イテレーターの`finally`・`using`を終了します。3秒の猶予で終了しないコードは所有する子プロセスを停止し、結果不明として記録します。強制停止では外部副作用の取消や`finally`の実行を保証できません。例外と出力量超過はノード失敗として記録し、暗黙の再実行は行いません。待受の共通設定で期間を指定しない場合、単発C#の30秒期限は適用せず、列挙の終了またはワークフロー停止まで待ち受けます。
