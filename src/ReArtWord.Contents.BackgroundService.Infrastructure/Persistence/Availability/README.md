# 保存できない場合と切断中の動作

[関連する設定・開発資料](../../../../docs/reference/cluster-operations.md#用途別保存と保存不能時の扱い)

このディレクトリは、保存先の障害や切断中に使う候補値を管理します。

`AvailabilityService` は、用途ごとの設定に従って、未保存の変更を一時的に使うかどうかを管理します。既定では、保存に失敗した場合は `KeepConfirmed`、切断中は `LastConfirmedReadOnly` を使い、最後に確認できた状態を維持します。

## 対象

- `Configuration`：ワークフローとクラスター共通の運用設定。
- `Runtime`：通常の状態の get/set。

重複抑止、強い CAS、操作記録、ピアの識別情報、外部のファイル・通信・プロセス操作には適用しません。これらは、通常の保存・実行結果を確認できることが必要です。

## 未保存の変更を使う

`UseUnsaved` を選んだ場合、保存処理は失敗後に保存済みの版を読み直し、変更されていないことを確認します。競合と復元中の保護も確認してから、一時的に変更内容を使用します。自動反映・手動反映・影響確認の方針は、元の設定に従います。

保存結果の `PersistenceOutcome` と、実際に使用した結果の `AdoptionOutcome` は別々に返します。未保存の変更を使用できても、保存済みにはなりません。通常の保存へ戻すときは、スナップショットと反映まで成功した後に、未保存状態を解除します。

状態 API では、保存済みの版 `SavedRevision`、現在有効な版 `EffectiveRevision`、再起動時に復元できる版 `RecoveryRevision`、未反映候補の版 `CandidateRevision` を区別します。`IsUnsaved` は現在有効な版、`CandidateIsUnsaved` は候補が未保存かどうかを示します。画面は変更通知と `GetStates` で同じ状態を表示します。保存できなかった有効値は再起動で失われ、最後に確認できた復元用の版へ戻ります。

## 代替保存先を使う

代替保存先には、設定した SQLite または JSON を使います。書き込み後に読み直してハッシュを照合し、一致した内容だけを使用します。候補を置く二つの保存枠と、使用する枠を示す情報を分け、新しい候補で現在の復元用データを上書きしない構成です。

代替保存先への書き込みは、クラスター内での共有完了とは別です。元の保存先の版が変わっていた場合は、古い代替候補を自動で復元しません。

## 切断中の状態操作

`AvailableNodeStateStore` の通常の get/set では、切断中の動作を `Unavailable`、`LastConfirmedReadOnly`、`LocalUnconfirmed` から指定できます。`LocalUnconfirmed` は一時的なローカル候補です。再接続時に、元の確認済みの版を使って CAS できる、競合のない値だけを統合します。

競合と、書き込み結果が `Unknown` の操作は保持し、自動で再実行しません。`Detached` による永続的なローカル変更は別のサービスが管理します。

## 保持上限

既定の上限は 256 件・1 MiB です。未保存の変更を持つ候補は、空きを作るために自動削除しません。空きが足りない場合は `CacheCapacity` を返します。
